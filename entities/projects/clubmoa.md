# 동아리모아 — 동아리 지원·운영 플랫폼

## 한눈에 보기

- **기간:** 2025-01~2025-03
- **구성:** 4명 백엔드 팀 프로젝트
- **기술:** React, Spring Boot (Java 17), MySQL, Redis, Spring Security, JPA, GCS
- **핵심 주제:** 동아리별 역할을 데이터로 모델링하고, 서비스 요구에 맞는 세션 인증·리소스 단위 RBAC를 설계

## 문제 맥락

동아리 지원·모집은 지원자와 운영자 모두에게 상태 확인·권한 위임·구성원 관리가 필요한 흐름이다. 특히 “특정 동아리의 회장만 그 동아리 임원 권한을 위임한다”는 규칙은 전역 역할만으로 표현할 수 없다. 즉, 사용자의 권한은 사용자 단독 속성이 아니라 **사용자–동아리–역할 관계**로 관리돼야 했다.

## 핵심 설계와 구현

### 1. 도메인과 지원 흐름

- 사용자·동아리·지원서·동아리별 역할 관계의 ERD와 API 구조를 설계했다.
- 지원서 생성·목록·상세·수정·삭제와 지원 상태 조회를 구현해 중복 지원과 사용자 혼선을 줄였다.
- 관리자 측에서는 지원서 조회·승인, 구성원 목록, 역할 부여, 탈퇴·강퇴 흐름을 구현했다.
- 승인과 역할 부여를 하나의 트랜잭션으로 묶어, 승인만 됐는데 역할이 누락되는 불일치를 막았다.
- 첨부 파일은 GCS에 업로드하고 URL을 DB에 저장했다.

### 2. JWT 대신 Redis 세션을 선택한 이유

JWT의 무상태 확장성은 장점이지만, 이 서비스에는 로그아웃·강제 탈퇴·권한 변경을 즉시 반영해야 하는 운영 시나리오가 있었다. 서버에서 세션을 즉시 제거할 수 있고, Redis 공용 세션 저장소로 확장성을 보완할 수 있어 세션 방식을 선택했다. HttpOnly 쿠키 기반 접근은 프런트엔드의 토큰 보관에 따른 XSS 노출도 줄이는 방향이었다.

### 3. 리소스 단위 RBAC

- 사용자–동아리–역할 관계 테이블을 별도 스키마로 두었다.
- Spring Security의 메서드 단위 인가와 표현식 기반 검증을 결합했다.
- 요청한 동아리에 대해 현재 사용자가 회장인지 확인하는 커스텀 인가를 만들어, 회장만 임원 권한을 위임하게 했다.
- 전역 `ADMIN` 같은 단순 권한이 아니라, **어느 동아리에서 어떤 역할인가**를 기준으로 접근을 결정했다.

## 제품 흐름 UI 근거 (2026-07-13)

로컬 React 프론트엔드에 가상 동아리·회원·지원자 데이터를 넣어 계정 진입 → 동아리 탐색 → 지원서 작성 → 운영자의 합격/불합격 처리 → 멤버 역할 관리 → 1:1 채팅 화면을 확인했다. 이는 지원·운영의 화면 흐름을 설명하는 근거이며, 저장·승인 반영·권한 변경 API와 실제 WebSocket 메시지 전달까지 검증한 결과는 아니다.

## 결과와 배운 점

- 동아리 지원·승인·운영의 핵심 기능을 완료하고 AWS 배포 흐름을 검증했다.
- 인증 방식은 “JWT가 최신이므로”가 아니라 즉시 차단·권한 변경 같은 운영 요구로 결정해야 함을 확인했다.
- 복잡한 인가 정책은 도메인 관계를 데이터로 모델링하고, 재사용 가능한 인가 규칙으로 분리할 때 유지보수하기 쉬움을 경험했다.
