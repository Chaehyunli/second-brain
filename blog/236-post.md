# [네트워크] 네트워크 애플리케이션의 원리 및 서비스

> 원문: https://ch010104.tistory.com/236

## 본문

1. 네트워크 애플리케이션의 기본 원리      애플리케이션 생성의 핵심  서로 다른 종단 시스템(End systems)에서 실행되며 네트워크를 통해 통신하는 프로그램을 작성하는 것이 핵심입니다. 라우터나 스위치 같은 네트워크 코어 장치를 위한 소프트웨어는 작성할 필요가 없습니다. 이는 코어 장치들이 사용자 애플리케이션을 실행하지 않고 패킷 전달 역할만 수행하기 때문입니다.   주요 학습 목표  애플리케이션 계층 프로토콜의 개념 및 구현 방식을 이해합니다. 전송 계층(Transport Layer)이 제공하는 서비스 모델을 파악합니다. 클라이언트-서버 및 P2P(Peer-to-Peer) 통신 패러다임을 학습합니다.    2. 네트워크 애플리케이션 아키텍처  클라이언트-서버(Client-Server) 패러다임  서버(Server): 항상 켜져 있는 호스트로, 고정된 IP 주소를 가집니다. 대규모 서비스를 위해 주로 데이터 센터에 위치합니다. 클라이언트(Client): 서버와 통신하며, 연결이 간헐적일 수 있습니다. 유동 IP 주소를 가질 수 있으며, 클라이언트끼리는 직접 통신하지 않습니다. (예: HTTP, IMAP, FTP)   P2P(Peer-to-Peer) 아키텍처  항상 켜져 있는 고정 서버 없이, 임의의 종단 시스템(피어)끼리 직접 통신합니다. 자가 확장성(Self-scalability): 새로운 피어가 참여할 때마다 서비스 수요뿐만 아니라 서비스 공급 능력(대역폭, 자원 등)도 함께 증가합니다. 피어들의 접속이 유동적이고 IP 주소가 변하기 때문에 관리 구조가 복잡합니다. (예: P2P 파일 공유)    3. 프로세스 간 통신과 소켓(Socket)  프로세스(Process)의 개념  호스트 내에서 실행되는 프로그램을 의미합니다. 동일 호스트 내: 운영체제가 제공하는 프로세스 간 통신(IPC) 기능을 사용합니다. 서로 다른 호스트: 네트워크를 통해 메시지를 교환하며 통신합니다.   소켓(Socket)의 역할  애플리케이션 프로세스와 전송 프로토콜 사이의 인터페이스로, 일종의 "문(Door)" 역할을 합니다. 프로세스는 소켓을 통해 메시지를 내보내거나 들이며, 전송 인프라가 상대방 소켓까지 데이터를 전달해 줄 것이라고 신뢰하고 동작합니다.       프로세스 식별(Addressing)  메시지 수신을 위해 고유한 식별자가 필요합니다. 식별자 구성: 해당 호스트를 찾는 IP 주소와 호스트 내 특정 프로세스를 지정하는 포트 번호(Port number)가 합쳐져야 합니다. 주요 포트 예시: HTTP(80), 메일/SMTP(25).    4. 애플리케이션 계층 프로토콜의 정의  프로토콜 규정 사항  메시지 타입: 요청(Request)이나 응답(Response)과 같은 메시지의 종류를 정의합니다. 메시지 문법(Syntax): 메시지에 포함되는 필드의 종류와 각 필드를 구분하는 방식을 정합니다. 메시지 의미(Semantics): 각 필드에 담긴 정보가 무엇을 뜻하는지 정의합니다. 규칙: 프로세스가 메시지를 언제, 어떤 방식으로 전송하고 응답해야 하는지에 대한 절차를 규정합니다.   프로토콜의 종류  공공 프로토콜(Open protocols): RFC 표준 등에 정의되어 누구나 접근 가능하며, 서로 다른 소프트웨어 간의 상호 운용성을 보장합니다. (예: HTTP, SMTP) 독점 프로토콜(Proprietary protocols): 특정 업체가 소유하며 외부로 공개되지 않는 경우가 많습니다. (예: Skype)    5. 애플리케이션이 요구하는 전송 서비스  데이터 무결성(Data integrity): 파일 전송이나 금융 거래처럼 데이터 손실이 절대 용납되지 않는 서비스(100% 신뢰성 요구)와 오디오/비디오처럼 일부 손실을 견딜 수 있는 서비스가 있습니다. 타이밍(Timing): 인터넷 전화, 실시간 게임 등은 사용자 경험을 위해 매우 낮은 지연 시간을 필수적으로 요구합니다. 처리량(Throughput): 멀티미디어 스트리밍은 최소한의 대역폭 보장이 필요하지만, 남는 자원을 유연하게 사용하는 '탄력적 앱(Elastic apps)'도 존재합니다. 보안(Security): 데이터의 기밀성(암호화), 무결성, 종단 간 인증 등을 요구합니다.    6. 인터넷 전송 프로토콜 서비스 비교 (TCP vs UDP)    TCP(Transmission Control Protocol) 서비스  신뢰성: 데이터의 정확한 전달을 보장합니다. 흐름 제어: 수신자가 처리할 수 있는 속도에 맞춰 송신량을 조절합니다. 혼잡 제어: 네트워크가 과부하 상태일 때 송신 속도를 억제하여 전체 망을 보호합니다. 연결 지향: 데이터 전송 전 클라이언트와 서버 간에 사전 연결 설정 과정이 필요합니다. 한계: 지연 시간 보장, 최소 처리량 보장, 기본 보안 기능을 제공하지 않습니다.   UDP(User Datagram Protocol) 서비스  비신뢰적인 데이터 전송 방식으로, 간단하고 빠릅니다. 신뢰성 보장, 흐름 및 혼잡 제어, 타이밍 및 처리량 보장, 연결 설정 과정이 모두 없습니다.   보안 이슈와 TLS  기본 TCP와 UDP 소켓은 암호화를 제공하지 않아 데이터가 평문으로 노출될 위험이 있습니다. 이를 해결하기 위해 애플리케이션 계층에서 TLS(Transport Layer Security)를 구현하여 암호화, 데이터 무결성, 엔드포인트 인증 기능을 보완하여 사용합니다.    7. 웹(Web)과 HTTP의 개요  웹 페이지 구성 요소:  웹 페이지는 여러 개의 객체(Object)로 구성됩니다. 객체는 HTML 파일, JPEG 이미지, Java 애플릿, 오디오 파일 등 다양한 형태를 가질 수 있습니다. 대부분의 웹 페이지는 기본 HTML 파일과 이를 참조하는 여러 객체로 이루어지며, 각 객체는 URL(Uniform Resource Locator)을 통해 주소가 지정됩니다. URL 구성: 호스트 이름(Host name)과 경로 이름(Path name)으로 나뉩니다 (예: www.someschool.edu/someDept/pic.gif).   HTTP(Hypertext Transfer Protocol):  웹의 애플리케이션 계층 프로토콜로, 클라이언트-서버 모델을 따릅니다. 클라이언트(브라우저): HTTP 프로토콜을 사용하여 웹 객체를 요청하고 수신하여 화면에 표시합니다. 서버(웹 서버): 클라이언트의 요청에 응답하여 객체를 전송합니다.      8. HTTP 프로토콜의 특성  TCP 사용:  HTTP는 전송 계층 프로토콜로 TCP를 사용합니다. 클라이언트는 서버의 80번 포트로 TCP 연결(소켓 생성)을 시도하고, 서버가 이를 수락하면 메시지를 교환합니다.   비상태 유지(Stateless):  서버는 과거의 클라이언트 요청에 대한 정보를 유지하지 않습니다. 상태를 유지하는 프로토콜은 과거 이력을 관리해야 하므로 복잡하며, 서버나 클라이언트 장애 시 상태 정보의 불일치가 발생할 수 있어 복구 과정이 까다롭습니다.    9. HTTP 연결 방식: 비지속 연결 vs 지속 연결  비지속 연결(Non-persistent HTTP):  한 번의 TCP 연결을 통해 최대 하나의 객체만 전송하고 연결을 종료합니다. 여러 객체를 다운로드하려면 매번 새로운 연결을 맺어야 합니다.   지속 연결(Persistent HTTP):  서버가 응답을 보낸 후에도 TCP 연결을 유지합니다. 동일한 클라이언트와 서버 간의 후속 HTTP 메시지는 이미 열려 있는 연결을 통해 전송됩니다. 한 번의 연결로 여러 객체를 전송할 수 있어 효율적입니다.    10. 비지속 연결의 동작 과정 및 응답 시간     동작 예시:  클라이언트가 서버로 TCP 연결을 시작합니다(1a). 서버가 연결을 수락합니다(1b). 클라이언트가 HTTP 요청 메시지를 보냅니다(2). 서버가 요청된 객체를 포함한 응답 메시지를 보냅니다(3). 서버가 TCP 연결을 닫습니다(4). 클라이언트가 HTML 파일을 수신하고 참조된 객체(예: 이미지 10개)를 확인하면, 각 객체에 대해 위 과정을 반복합니다(5~6).   응답 시간(Response Time) 분석:  RTT(Round Trip Time): 작은 패킷이 클라이언트에서 서버로 갔다가 다시 돌아오는 데 걸리는 시간입니다. 총 응답 시간: 1 RTT(TCP 연결 설정) + 1 RTT(HTTP 요청 및 응답 초기 수신) + 객체 전송 시간 = 2 RTT + 전송 시간이 소요됩니다.      11. 지속 연결의 장점 및 상태 유지(Cookies)    지속 연결(HTTP 1.1)의 개선점:  비지속 연결은 객체당 2 RTT가 필요하고 각 연결마다 운영체제 오버헤드가 발생하지만, 지속 연결은 이를 줄여줍니다. 참조된 모든 객체를 가져오는 데 단 1 RTT 정도면 충분할 수도 있어 응답 시간을 절반 가까이 단축할 수 있습니다.   쿠키(Cookies)를 이용한 상태 유지:  HTTP는 기본적으로 비상태 프로토콜이지만, 웹사이트는 사용자 상태를 유지하기 위해 쿠키를 사용합니다. 쿠키의 4가지 구성 요소:  HTTP 응답 메시지의 쿠키 헤더 라인. HTTP 요청 메시지의 쿠키 헤더 라인. 사용자의 브라우저가 관리하고 호스트에 저장하는 쿠키 파일. 웹사이트의 백엔드 데이터베이스.   활용 사례: 사용자 인증, 장바구니, 추천 시스템, 사용자 세션 상태 유지 등에 사용됩니다
