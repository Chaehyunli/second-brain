# [스프링 DB 2편 - 데이터 접근 활용 기술] 3. 데이터 접근 기술 - 테스트

## 학습 목표 및 맥락

데이터 접근 기술은 실제 데이터베이스에 데이터를 정상적으로 저장·조회하는지 검증해야 한다. 이 강의에서는 기존 ItemRepositoryTest를 실제 H2 DB와 연결해 실행하고, 테스트 데이터가 서로 영향을 주지 않도록 만드는 과정을 다룬다.

테스트 코드는 src/test에 있으므로 테스트 실행 시 src/test/resources/application.properties가 우선 적용된다. 기존 테스트 설정에는 DB 연결 정보가 없으므로 다음처럼 추가한다.

## 원문 기반 학습 정리

### 1. 테스트 - 데이터베이스 연동

데이터 접근 기술은 실제 데이터베이스에 데이터를 정상적으로 저장·조회하는지 검증해야 한다. 이 강의에서는 기존 ItemRepositoryTest를 실제 H2 DB와 연결해 실행하고, 테스트 데이터가 서로 영향을 주지 않도록 만드는 과정을 다룬다.

테스트 코드는 src/test에 있으므로 테스트 실행 시 src/test/resources/application.properties가 우선 적용된다. 기존 테스트 설정에는 DB 연결 정보가 없으므로 다음처럼 추가한다.

### main - application.properties

src/main/resources/application.properties

```java
spring.profiles.active=local
spring.datasource.url=jdbc:h2:tcp://localhost/~/test
spring.datasource.username=sa
logging.level.org.springframework.jdbc=debug
```

### test - application.properties

src/test/resources/application.properties

```java
spring.profiles.active=test
spring.datasource.url=jdbc:h2:tcp://localhost/~/test
spring.datasource.username=sa
logging.level.org.springframework.jdbc=debug
```

현재 애플리케이션 시작 설정은 JdbcTemplateV3Config를 사용하도록 구성되어 있으므로, 테스트도 MemoryItemRepository가 아닌 JdbcTemplateItemRepositoryV3을 통해 실제 DB에 접근한다. 시작 클래스의 전체 소스는 아래 임베디드 DB 직접 구성 절에서 원문 전체 코드 블록으로 한 번만 제공한다.

H2 서버가 실행된 상태에서 ItemRepositoryTest 전체를 실행한다. updateItem()과 save()는 성공하지만 findItems()는 예상보다 많은 데이터가 조회되어 실패할 수 있다.

```text
@Test
void findItems() {
    //given
    Item item1 = new Item("itemA-1", 10000, 10);
    Item item2 = new Item("itemA-2", 20000, 20);
    Item item3 = new Item("itemB-1", 30000, 30);
    itemRepository.save(item1);
    itemRepository.save(item2);
    itemRepository.save(item3);

    test(null, null, item1, item2, item3);
}
```

이 테스트는 세 상품을 저장하고 세 상품을 조회할 것을 기대한다. 하지만 로컬 서버를 실행하면서 저장한 데이터가 H2 DB에 남아 있으면 추가 행까지 함께 조회된다. TestDataInit은 local 프로필에서만 동작하므로 원인이 아니다. H2 콘솔에서 다음 쿼리로 남아 있는 데이터를 확인할 수 있다.

```sql
SELECT * FROM ITEM;
```

### 2. 테스트 - 데이터베이스 분리

애플리케이션 서버와 테스트가 같은 DB를 사용하면 로컬 실행 데이터가 테스트 결과를 오염시킨다. 가장 단순한 해결책은 테스트 전용 DB를 별도로 운영하는 것이다.

```text
jdbc:h2:tcp://localhost/~/test      local에서 접근하는 서버 전용 데이터베이스
jdbc:h2:tcp://localhost/~/testcase  test 케이스에서 사용하는 전용 데이터베이스
```

H2 서버를 재시작한 뒤 최초 한 번 jdbc:h2:~/testcase로 접속하면 ~/testcase.mv.db 파일이 생성된다. 이후에는 jdbc:h2:tcp://localhost/~/testcase로 접속한다. testcase DB에도 item 테이블을 생성해야 한다.

### sql/schema.sql

```sql
drop table if exists item CASCADE;

create table item
(
    id        bigint generated by default as identity,
    item_name varchar(10),
    price     integer,
    quantity  integer,
    primary key (id)
);
```

main 설정은 그대로 두고 테스트 설정만 변경한다.

### main - application.properties

src/main/resources/application.properties

```text
spring.profiles.active=local
spring.datasource.url=jdbc:h2:tcp://localhost/~/test
spring.datasource.username=sa
```

### test - application.properties

src/test/resources/application.properties

```text
spring.profiles.active=test
spring.datasource.url=jdbc:h2:tcp://localhost/~/testcase
spring.datasource.username=sa
```

테스트 전용 DB를 만들면 로컬 서버의 데이터는 분리된다. 그러나 findItems()를 두 번 실행하거나, save()가 먼저 실행된 뒤 findItems()를 실행하면 여전히 실패할 수 있다. 테스트가 직접 저장한 데이터가 testcase DB에 계속 남기 때문이다.

테스트마다 DELETE SQL을 실행할 수도 있지만, 테스트 중 예외가 발생하거나 프로세스가 종료되면 정리 코드가 실행되지 않을 수 있다. 따라서 테스트에서 중요한 원칙인 격리와 반복 실행 가능성을 완전히 보장하지 못한다.

테스트는 다른 테스트와 격리해야 한다.

테스트는 반복해서 실행할 수 있어야 한다.

### 3. 테스트 - 데이터 롤백

트랜잭션을 사용하면 테스트가 끝난 뒤 데이터 변경을 롤백하여 원래 상태로 되돌릴 수 있다. 테스트 중 데이터 저장 후 예외가 발생해도 커밋되지 않았으므로 데이터가 남지 않는다.

```text
1. 트랜잭션 시작
2. 테스트 A 실행
3. 트랜잭션 롤백
4. 트랜잭션 시작
5. 테스트 B 실행
6. 트랜잭션 롤백
```

JUnit의 @BeforeEach와 @AfterEach를 사용하면 각 테스트 전후에 이 과정을 적용할 수 있다.

이 코드는 기존 ItemRepositoryTest의 일부를 바꾸는 방식이므로, 전체 원본 클래스가 제공되지 않은 상태에서 조각 코드로 재작성하지 않는다. 직접 적용할 때는 전체 ItemRepositoryTest 클래스에서 트랜잭션 매니저 필드·@BeforeEach·@AfterEach를 추가한다.

PlatformTransactionManager는 스프링 부트가 적절한 구현체를 자동 등록하므로 주입받아 사용한다.

@BeforeEach: 각 테스트 직전에 실행된다. 여기서 트랜잭션을 시작하면 테스트 전체가 트랜잭션 범위 안에서 동작한다.

transactionManager.getTransaction(new DefaultTransactionDefinition()): 새 트랜잭션을 시작한다.

@AfterEach: 각 테스트 직후에 실행된다.

transactionManager.rollback(status): 테스트가 바꾼 데이터를 트랜잭션 시작 전 상태로 되돌린다.

처음 한 번은 테스트 전용 DB의 기존 데이터를 정리한 뒤 실행한다.

```sql
delete from item;
SELECT * FROM ITEM;
```

이후 ItemRepositoryTest를 반복 실행해도 성공한다.

### 4. 테스트 - @Transactional

스프링은 테스트에 @Transactional을 붙이면 트랜잭션을 적용하고, 테스트 종료 시 자동 롤백하는 기능을 제공한다. 따라서 기존 전체 ItemRepositoryTest에서 수동 트랜잭션 필드·@BeforeEach·롤백 호출을 주석 처리한 뒤, 아래 애너테이션을 테스트 클래스 전체에 적용한다.

애플리케이션 로직에 붙은 @Transactional은 로직이 정상 수행되면 기본적으로 커밋한다. 반면 테스트 클래스 또는 테스트 메서드에 직접 붙은 @Transactional은 테스트가 끝나면 스프링 테스트가 롤백한다.

### @Transactional 테스트 동작 방식

테스트 트랜잭션 안에서 INSERT와 SELECT가 같은 커넥션으로 실행되고, 테스트 종료 시 롤백으로 저장 데이터가 제거되는 전체 흐름을 보충한다.

테스트 클래스 또는 메서드의 @Transactional을 확인한다.

테스트 실행 전에 트랜잭션을 시작한다.

테스트·서비스·리포지토리가 같은 트랜잭션에 참여한다.

JdbcTemplate이 같은 트랜잭션의 커넥션으로 INSERT·SELECT를 실행한다.

assertThat()으로 저장·조회 결과를 검증한다.

테스트 종료 후 트랜잭션을 강제로 롤백한다.

따라서 테스트 안에서는 방금 저장한 item1, item2, item3을 조회할 수 있지만, 테스트가 종료되면 DB에서는 모두 제거된다. 테스트에서 시작한 트랜잭션이 서비스·리포지토리의 트랜잭션까지 전파되어 참여하며, 같은 트랜잭션은 같은 커넥션을 사용한다.

### 강제로 커밋하기 - @Commit

일반적인 테스트에서는 자동 롤백이 맞지만, 저장 결과를 실제 DB에서 확인해야 하는 경우에는 전체 ItemRepositoryTest 클래스 또는 특정 테스트 메서드에 @Commit을 추가한다. @Rollback(value = false)도 같은 목적에 사용할 수 있다.

@Commit을 사용하면 테스트 데이터가 남으므로 디버깅·수동 확인 등 제한된 경우에만 사용한다.

### 5. 테스트 - 임베디드 모드 DB

테스트만을 위해 별도 H2 서버와 DB 파일을 설치·운영하는 것은 번거롭다. H2는 자바로 구현되어 JVM 메모리 안에서 실행되는 임베디드 모드를 제공한다. 애플리케이션이 종료되면 DB와 데이터도 함께 사라진다.

테스트 프로필일 때만 메모리 DB를 사용하도록 DataSource를 직접 빈 등록할 수 있다.

### ItemServiceApplication - 임베디드 DB 직접 구성

```java
package hello.itemservice;

@Slf4j
//@Import(MemoryConfig.class)
//@Import(JdbcTemplateV1Config.class)
//@Import(JdbcTemplateV2Config.class)
@Import(JdbcTemplateV3Config.class)
@SpringBootApplication(scanBasePackages = "hello.itemservice.web")
public class ItemServiceApplication {

    public static void main(String[] args) {
        SpringApplication.run(ItemServiceApplication.class, args);
    }

    @Bean
    @Profile("local")
    public TestDataInit testDataInit(ItemRepository itemRepository) {
        return new TestDataInit(itemRepository);
    }

    @Bean
    @Profile("test")
    public DataSource dataSource() {
        log.info("메모리 데이터베이스 초기화");
        DriverManagerDataSource dataSource = new DriverManagerDataSource();
        dataSource.setDriverClassName("org.h2.Driver");
        dataSource.setUrl("jdbc:h2:mem:db;DB_CLOSE_DELAY=-1");
        dataSource.setUsername("sa");
        dataSource.setPassword("");
        return dataSource;
    }
}
```

@Profile("test"): 테스트에서만 이 DataSource 빈을 등록한다.

jdbc:h2:mem:db: H2를 메모리 모드로 실행한다.

DB_CLOSE_DELAY=-1: 마지막 DB 커넥션이 끊겨도 JVM이 종료될 때까지 DB를 유지한다.

H2 서버를 종료해도 테스트는 메모리 DB에 접속한다. 다만 처음 실행하면 다음 오류가 발생한다.

```java
org.springframework.jdbc.BadSqlGrammarException: PreparedStatementCallback;
bad SQL grammar []; nested exception is
org.h2.jdbc.JdbcSQLSyntaxErrorException: Table "ITEM" not found; SQL
statement:
insert into item (item_name, price, quantity) values (?, ?, ?) [42102-200]
```

가장 아래의 Table "ITEM" not found가 근본 원인이다. 메모리 DB는 새로 생성됐지만 item 테이블은 아직 생성되지 않았기 때문이다.

### 6. 테스트 - 스키마 초기화

메모리 DB는 애플리케이션 종료 시 사라지므로 실행할 때마다 테이블도 생성해야 한다. 스프링 부트는 기본 SQL 스크립트를 실행하여 DB를 초기화하는 기능을 제공한다.

다음 위치와 파일명으로 스키마 파일을 만든다.

src/test/resources/schema.sql

```sql
drop table if exists item CASCADE;

create table item
(
    id        bigint generated by default as identity,
    item_name varchar(10),
    price     integer,
    quantity  integer,
    primary key (id)
);
```

테스트 리소스에 있는 schema.sql은 테스트 시작 시 실행된다. SQL 스크립트 실행 여부를 확인하려면 테스트 설정에 JDBC 로그를 추가한다.

```java
#schema.sql
logging.level.org.springframework.jdbc=debug
```

```sql
..init.ScriptUtils     : 0 returned as update count for SQL: drop table if
exists item CASCADE
..init.ScriptUtils     : 0 returned as update count for SQL: create table item
( id bigint generated by default as identity, item_name varchar(10), price
integer, quantity integer, primary key (id) )
```

> 원문 코드가 길어 이 노트에서는 앞부분만 보존했습니다. 전체는 원문에서 확인합니다.

이후 ItemRepositoryTest는 메모리 DB와 초기화된 item 테이블을 사용해 정상 수행된다.

### 7. 테스트 - 스프링 부트와 임베디드 모드

스프링 부트는 별도 DB 접속 정보가 없고 임베디드 DB 의존성이 있으면 임베디드 DataSource를 자동 구성한다. 따라서 직접 만든 테스트용 dataSource() 빈을 다음처럼 전체 클래스에서 주석 처리하고, 테스트용 외부 DB 설정도 제거하면 된다.

### ItemServiceApplication - 테스트용 DataSource 주석 처리

```java
package hello.itemservice;

@Slf4j
//@Import(MemoryConfig.class)
//@Import(JdbcTemplateV1Config.class)
//@Import(JdbcTemplateV2Config.class)
@Import(JdbcTemplateV3Config.class)
@SpringBootApplication(scanBasePackages = "hello.itemservice.web")
public class ItemServiceApplication {

    public static void main(String[] args) {
        SpringApplication.run(ItemServiceApplication.class, args);
    }

    @Bean
    @Profile("local")
    public TestDataInit testDataInit(ItemRepository itemRepository) {
        return new TestDataInit(itemRepository);
    }

/*
    @Bean
    @Profile("test")
    public DataSource dataSource() {
        log.info("메모리 데이터베이스 초기화");
        DriverManagerDataSource dataSource = new DriverManagerDataSource();
        dataSource.setDriverClassName("org.h2.Driver");
        dataSource.setUrl("jdbc:h2:mem:db;DB_CLOSE_DELAY=-1");
        dataSource.setUsername("sa");
        dataSource.setPassword("");
        return dataSource;
    }
*/
}
```

### test - application.properties

```java
spring.profiles.active=test
#spring.datasource.url=jdbc:h2:tcp://localhost/~/testcase
#spring.datasource.username=sa
#jdbcTemplate sql log
logging.level.org.springframework.jdbc=debug
```

스프링 부트가 자동 생성한 URL에는 여러 DataSource가 같은 DB를 공유하는 일을 막기 위해 임의 이름이 붙을 수 있다.

```text
conn0: url=jdbc:h2:mem:d8fb3a29-caf7-4b37-9b6c-b0eed9985454
```

기본 DB 이름을 jdbc:h2:mem:testdb로 고정하려면 다음 설정을 추가한다.

```text
spring.datasource.generate-unique-name=false
```

스프링 부트 3.x에서 테스트 트랜잭션 시작·종료 로그가 보이지 않으면 다음처럼 로그 레벨을 조정한다.

```java
logging.level.org.springframework.test.context.transaction=trace
```

테스트 설정과 schema.sql은 반드시 src/test/resources에 둔다. src/main/resources의 로컬 실행 설정과 분리해야 테스트가 독립적으로 동작한다.
