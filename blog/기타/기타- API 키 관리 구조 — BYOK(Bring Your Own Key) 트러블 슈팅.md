## 원인·해결 근거

### 문제

BYOK(사용자가 직접 LLM API 키를 등록)로 서버 운영자가 LLM 비용을 부담하지 않게 했지만, 이 구조 자체가 온보딩 진입장벽과 키 저장 보안 신뢰 확보라는 리스크를 안고 있음.

핵심 문제: CREDENTIAL_ENCRYPTION_KEY를 가진 서버(=운영자)는 DB에 저장된 모든 사용자 키를 복호화할 수 있음. 위협 경로가 두 개인데,

DB가 통째로 유출되는 경우 — 마스터키까지 같이 새면(.env 관리 실수 등) 저장된 암호문이 사실상 평문급으로 노출됨

운영자가 직접 열람하는 경우 — 악의가 없어도, "볼 수 있는 힘"이 기술적으로 존재한다는 사실 자체가 문제임

비유하자면 손님이 금고에 귀중품을 맡겼는데, 그 금고를 여는 마스터키를 가게 주인이 그대로 쥐고 있는 셈임. 주인이 "안 훔친다"고 약속해도, 훔칠 수 있는 가능성 자체가 열려 있다는 게 문제임. 게다가 여긴 남의 돈이 실제로 걸린 API 키라 — 유출되면 사용자 명의로 LLM 비용이 청구되는 실질적 금전 피해로 이어짐.

### 검토했던 대안

이 문제를 풀려고 처음엔 두 가지 대안을 검토함.

완전 클라이언트 사이드 직접 호출 — 서버가 키를 아예 안 봄. 이론상 제일 깔끔한데, 실제로 붙여보면 두 가지 벽에 부딪힘. 하나는 provider마다 인증 헤더·응답 포맷이 달라서(Anthropic/OpenAI/Upstage/Google) provider별 SDK를 프런트에 전부 새로 이식해야 함. 다른 하나는 CORS — Anthropic API 같은 경우 브라우저에서 직접 호출하려면 별도의 위험 신호용 헤더를 붙여야 열리는 등, 애초에 브라우저에서 직접 부르라고 설계된 API가 아님.

서버 무저장(요청마다 프런트가 키를 전달) — DB엔 저장 안 하지만, 요청을 처리하는 그 순간엔 서버 프로세스 메모리에 평문이 존재함. "저장 안 함"과 "노출 안 함"은 다른 얘기라, 로깅·에러 트레이스에 body가 잘못 찍히기라도 하면 그대로 새어나갈 수 있음. 즉 이것만으론 zero-knowledge가 안 됨.

localStorage에 저장하는 것도 검토했지만, 이건 해결이 아니라 리스크 이전이라고 판단함. localStorage는 만료 개념이 없어서 한 번 넣으면 사실상 무기한 남아있고, 써드파티 스크립트 하나에 취약점이 있거나 의존성 패키지 하나가 오염되면 그 스크립트가 localStorage.getItem() 한 줄로 전체 사용자 키를 통째로 긁어갈 수 있음 — 서버 신뢰 문제를 브라우저 신뢰 문제로 옮긴 것뿐임.

두 대안 다 보안·편의성 중 하나를 포기해야 하는 방식이라 고민하던 중, 외부 조언을 받음.

### 외부 조언 — 신뢰 경계를 먼저 정하기

BYOK 구조는 보안성 · 편의성 · zero-knowledge 세 가지를 동시에 완벽히 만족시킬 수 없음. 그래서 기술 선택보다 신뢰 경계를 어디에 둘지를 먼저 정하는 게 설계의 출발점.

왜 세 개를 동시에 못 잡는지 풀어보면: 보안성을 극한까지 올리면(서버가 아무것도 모름) 매번 사용자가 개입해야 해서 편의성이 떨어지고, 편의성을 올리면(서버가 뭔가 캐시/보관) zero-knowledge가 깨짐. 기존에 검토한 2가지 대안은 결국 이 삼각형에서 한 꼭짓점을 포기하는 방식이었음 — 완전 클라이언트 호출은 편의성(개발 난이도 포함)을, 서버 무저장은 zero-knowledge를 어중간하게 포기한 셈. 이 조언은 "누가 무엇을 알아야 하는가"라는 경계선을 먼저 그으면 셋 다 가져가는 제3의 길이 있다는 걸 알려줌.

### 용어 정리

🔐BYOK (Bring Your Own Key) 사용자가 자신의 API 키를 직접 발급받아 서비스에 등록해서 쓰는 방식. 운영자가 자체 LLM 요금제를 붙여서 비용을 대신 내주는 SaaS형 구조와 대비되는 개념 — 비용은 안 내는 대신, "남의 비밀키를 안전하게 보관"해야 하는 책임을 떠안음.

🌐Web Crypto API 브라우저(JS)에 내장된 표준 암호화 API(crypto.subtle). crypto.randomUUID()처럼 이미 흔히 쓰는 것들과 같은 계열의 브라우저 내장 기능이라 별도 라이브러리가 필요 없음. 암호화 연산이 서버로 안 넘어가고 클라이언트 안에서 끝남 — 브라우저 안에 딸린 작은 실험실 같은 거라, 재료(패스프레이즈)를 넣으면 그 실험실 안에서만 처리되고 결과물(암호문)만 밖으로 나감.

🔁PBKDF2 짧고 약한 패스프레이즈에 해시 함수를 수십만 번 반복 적용해서 일부러 느리게 계산되도록 만드는 키 유도 함수. 자물쇠 다이얼을 일부러 뻑뻑하게 만드는 것과 비슷함 — 정상 사용자는 조금 더 기다리면 되지만(반복 횟수 600,000회 기준 체감 100~300ms), 무차별대입 공격자는 그 뻑뻑함이 반복 횟수만큼 곱해져서 비용이 감당 안 됨. 600,000회는 OWASP가 권장하는 기준치임.

🧱 Argon2 PBKDF2보다 새로운 알고리즘으로 2015년 Password Hashing Competition 우승작. 시간뿐 아니라 메모리도 많이 쓰게 설계해서 GPU/ASIC 병렬 무차별대입 공격에 더 강함. 최신 비밀번호 관리 서비스들이 즐겨 쓰지만, Web Crypto API 표준엔 아직 없어서 브라우저에서 쓰려면 별도 WASM 라이브러리를 새 의존성으로 얹어야 함.

🔒AES-GCM API 키를 암호화하는 대칭키 방식. GCM의 "G"는 Galois(갈루아 필드) 연산을 뜻하는데, 이 덕분에 암호화와 동시에 위변조 탐지(인증 태그)까지 됨 — 편지를 봉투에 넣는 걸 넘어서 "뜯으면 티 나는 봉인 스티커"까지 붙이는 셈. 저장된 암호문이 중간에 조작되면 복호화 시점에 바로 예외가 남.

🧭Zero-knowledge (이 맥락에서) 서버가 사용자의 비밀을 알 방법이 구조적으로 없는 상태. "그냥 암호화해서 저장"과는 다름 — 마스터키를 서버가 갖고 있으면 언제든 복호화할 수 있으니 그건 zero-knowledge가 아님. 패스프레이즈 자체를 서버가 저장·전송받지 않아야만, 즉 복호화에 필요한 재료 자체가 서버에 없어야만 수학적으로 zero-knowledge가 성립함. 기존 Fernet 방식은 이 기준에서 탈락이었음.

### 채택한 방향: 클라이언트 측 zero-knowledge 암호화

핵심 결정:

서버가 평문 API 키를 영구 보관/복호화하지 못하게 구조를 바꿈 — 저장 시점은 물론 호출 시점에도 서버가 스스로 복호화할 방법이 없게. Bitwarden·1Password 같은 비밀번호 관리 서비스도 정확히 이런 원리로 운영됨.

암호화 파라미터

KDF: PBKDF2-SHA256, 600,000회 반복(Argon2는 WASM 의존성 비용 대비 이득이 크지 않다고 판단해 기각)

AES-GCM 256bit, salt(16byte)·iv(12byte)는 암호화마다 새로 생성. salt/iv/반복 횟수는 비밀이 아니라 그대로 DB에 저장해도 안전함(복호화 재료지, 복호화 결과가 아니므로)

유도된 키는 원칙적으로 devtools로도 못 꺼내게(extractable: false) 만들되, 세션 캐시용 사본만 예외적으로 export 가능하게 둠(아래 "전체 흐름 파이프라인" 참고)

### 전체 흐름 파이프라인

이 구조는 등록할 때 한 번 도는 파이프라인과, 실제로 LLM을 호출할 때마다 도는 파이프라인이 따로 있음. 단계별로 나눠서 보면 이렇게 됨.

### 1) 등록 파이프라인

Step 1 · 입력

패스프레이즈 + API 키(평문)를 입력함.

Step 2 · 사전 검증

```text
POST /me/llm-credential/verify { provider, api_key(평문) }
```

provider에 핑을 날려 키가 유효한지 확인함(저장은 안 함). 실패하면 여기서 멈추고 "키가 유효하지 않습니다" 피드백. 이 단계를 통과해야만 다음으로 넘어감 — 실패한 키가 애초에 암호화·저장되는 경로 자체를 차단함.

Step 3 · 로컬 암호화

통과하면 그때 PBKDF2로 키를 유도하고, 그 키로 API 키를 AES-GCM 암호화함.

Step 4 · 저장

```text
POST /me/llm-credential
{ provider, ciphertext, salt, iv, kdf_iterations, masked_key }
```

서버는 이 값들을 그대로 저장함. 이 과정에서 서버는 평문도 패스프레이즈도 한 번도 본 적이 없음.

### 2) 호출 파이프라인 (스케줄 생성 / 재생성 / 후보 교체 — LLM을 실제로 호출해야 하는 3개 지점이 전부 같은 패턴을 탐)

Step 1 · 암호문 재료 확보

```text
GET /me/llm-credential
→ { ciphertext, salt, iv, kdf_iterations, masked_key }
```

브라우저가 로컬에서 복호화하려면 이 값들이 애초에 손에 있어야 함 — 조회 API가 마스킹된 표시값뿐 아니라 암호문·salt·iv·반복 횟수까지 같이 내려주는 이유임.

Step 2 · 세션 캐시 확인

sessionStorage에 캐시된 유도키가 있는지 봄. 브라우저 탭이 개인 사물함 같은 거라

탭 안에서 새로고침해도 유지되고, 탭·창을 닫으면 자동으로 비워지고, 다른 탭과는 공유 안 됨. 별도 로직 없이sessionStorage의 기본 스코프만으로 원하는 UX(새로고침엔 재입력 안 물어보고, 새 탭/창에서만 물어보는 것)를 얻음.

Step 3 · 필요 시 재입력

캐시가 없으면 패스프레이즈 입력 모달을 띄우고, 입력받은 값으로 그때 키를 유도해 sessionStorage에 저장함.

이 캐시본만 extractable: true로 유도해야 해서(export 가능해야 저장 가능) devtools 방어를 이 지점에서 일부 포기하는 트레이드오프가 있음

어차피 이 페이지에 XSS가 터지면 캐시된 키를 굳이 밖으로 꺼내지 않아도 그 자리에서 바로 복호화를 시켜버릴 수 있으므로, XSS 앞에서는 둘 다 뚫린다고 보고 감수함.

Step 4 · 요청 전송

```text
POST .../generate (또는 /regenerate, /candidates/{id}/preview)
{ ..., api_key(평문) }
```

로컬에서 복호화한 평문을 그 요청 하나에만 실어 전송함.

Step 5 · 서버는 쓰고 버림

서버(프록시)는 파이프라인이 provider를 호출하는 순간에만 평문을 쓰고, 응답을 준 다음엔 즉시 버림.

DB에도, Redis 같은 캐시에도 안 남김.

지연 영향: 패스프레이즈 입력 시 PBKDF2 유도(세션당 1회, 100~300ms) 외엔 요청마다 추가되는 지연은 거의 없음. 캐시된 키로 하는 AES-GCM 복호화 자체는 서브밀리초 수준이라, 기존 서버 측 Fernet 복호화와 비용 차이가 없음.

### 트레이드오프

패스프레이즈 분실 = 복구 불가능:

패스프레이즈를 잃으면 저장된 키도 영구히 복구 불가능함. 서버가 패스프레이즈를 아예 모르니, 복구해준다는 건 zero-knowledge 자체를 배신하는 셈 — "등록된 키 삭제 후 재등록"만 안내 가능함.

새 탭/창에서는 재입력 필요:

sessionStorage가 탭 단위로 스코프되다 보니, 같은 작업을 다른 탭이나 창에서 이어가려면 패스프레이즈를 다시 입력해야 함.

편의성을 더 올리려면(예: 오래 유지되는 저장소에 캐시) 유출 시 노출 시간이 늘어나는 대가가 따르므로, 지금은 "탭이 살아있는 동안만" 정도로 선을 그음.
