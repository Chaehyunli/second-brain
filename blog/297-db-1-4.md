# [스프링 DB 1편 - 데이터 접근 핵심 원리] 4. 스프링과 문제 해결 - 트랜잭션

> 원문: https://ch010104.tistory.com/297

## 본문

1. 애플리케이션 구조와 기존 방식의 문제점 1) 표준적인 3계층 애플리케이션 구조 가장 단순하면서 많이 사용하는 방법은 역할에 따라 애플리케이션을 3가지 계층으로 나누는 것이다.   2) 순수한 서비스 계층의 중요성  가장 중요한 계층: 핵심 비즈니스 로직이 들어있는 서비스 계층이다. UI(웹) 관련 부분이 변경되거나 데이터 저장 기술이 변경되어도 비즈니스 로직은 최대한 영향 없이 유지되어야 한다. 보호의 목적:  프레젠테이션 계층은 웹, 서블릿, HTTP 관련 기술을 전담하여 서비스 계층을 보호한다. (예: HTTP API -> gRPC 변경 시 프레젠테이션 계층만 변경) 데이터 접근 계층은 JDBC, JPA 등 구체적인 데이터 접근 기술을 인터페이스 뒤로 숨겨 서비스 계층을 보호한다. 서비스 계층은 인터페이스에만 의존해야 비즈니스 코드의 변경 없이 JdbcRepository에서 JpaRepository로 기술을 변경할 수 있다.   결론: 서비스 계층은 특정 구현 기술에 직접 의존하지 않고 순수 자바 코드로 가급적 비즈니스 로직만 구현해야 유지보수와 테스트가 쉬워진다.  3) 기존 코드 분석과 문제점의 발생 [1] 트랜잭션 적용 전: MemberServiceV1 비즈니스 로직만 존재하여 매우 깔끔하고 순수한 상태이지만, 몇 가지 한계가 존재한다. package hello.jdbc.service; import hello.jdbc.domain.Member; import hello.jdbc.repository.MemberRepositoryV1; import lombok.RequiredArgsConstructor; import java.sql.SQLException; @RequiredArgsConstructor public class MemberServiceV1 { private final MemberRepositoryV1 memberRepository; public void accountTransfer(String fromId, String toId, int money) throws SQLException { Member fromMember = memberRepository.findById(fromId); Member toMember = memberRepository.findById(toId); memberRepository.update(fromId, fromMember.getMoney() - money); memberRepository.update(toId, toMember.getMoney() + money); } }  V1의 한계점:  SQLException이라는 JDBC 기술 예외에 의존한다. (이는 리포지토리 레이어에서 올라온 예외이므로 결국 서비스가 예외 기술에 누수되고 있음을 나타낸다.) MemberRepositoryV1이라는 구체 클래스에 직접 의존하고 있다. (인터페이스 도입이 필요함)    [2] 트랜잭션 적용 후: MemberServiceV2 트랜잭션의 성격 상 비즈니스 로직의 원자성을 보장하기 위해 트랜잭션 시작과 종료는 서비스 계층에서 수행되어야 한다. 아래는 커넥션을 동기화하기 위해 파라미터로 넘기는 전통적인 트랜잭션 처리 방식의 코드이다. package hello.jdbc.service; import hello.jdbc.domain.Member; import hello.jdbc.repository.MemberRepositoryV2; import lombok.RequiredArgsConstructor; import lombok.extern.slf4j.Slf4j; import javax.sql.DataSource; import java.sql.Connection; import java.sql.SQLException; @Slf4j @RequiredArgsConstructor public class MemberServiceV2 { private final DataSource dataSource; private final MemberRepositoryV2 memberRepository; public void accountTransfer(String fromId, String toId, int money) throws SQLException { Connection con = dataSource.getConnection(); try { con.setAutoCommit(false); // 트랜잭션 시작 // 비즈니스 로직 수행 bizLogic(con, fromId, toId, money); con.commit(); // 성공 시 커밋 } catch (Exception e) { con.rollback(); // 실패 시 롤백 throw new IllegalStateException(e); } finally { release(con); } } private void bizLogic(Connection con, String fromId, String toId, int money) throws SQLException { Member fromMember = memberRepository.findById(con, fromId); Member toMember = memberRepository.findById(con, toId); memberRepository.update(con, fromId, fromMember.getMoney() - money); memberRepository.update(con, toId, toMember.getMoney() + money); } private void release(Connection con) { if (con != null) { try { con.setAutoCommit(true); // 커넥션 풀을 고려하여 기본 상태로 복구 con.close(); } catch (Exception e) { log.info("connection close error", e); } } } }  V2의 극명한 한계점:  서비스 계층의 기술 누수: 트랜잭션을 사용하기 위해 javax.sql.DataSource, java.sql.Connection, java.sql.SQLException 등 JDBC 전용 기술이 서비스 코드를 완전히 잠식하였다. 유지보수 극악화: 향후 JDBC에서 JPA나 MyBatis 등 다른 데이터 저장 기술로 전환하면 트랜잭션 시작/종료 메커니즘 자체가 달라지므로 서비스 계층 코드를 대대적으로 수정해야 한다. 코드 중복 및 복잡성: 비즈니스 로직보다 트랜잭션을 설정하고 관리하기 위한 제어용 코드(try-catch-finally)가 더 길고 어지럽다.    4) 해결해야 할 3대 문제점 요약 ① 트랜잭션 문제 (Transaction Issues)  구현 기술의 서비스 계층 누수: 트랜잭션을 열고 닫기 위해 JDBC 커넥션 객체가 서비스 코드로 침범함. 서비스 계층은 순수해야 함. 트랜잭션 동기화 문제: 같은 트랜잭션을 한 커넥션 내에서 유지해야 하므로, 리포지토리의 모든 시그니처 메서드 파라미터로 Connection을 계속 넘겨주어야 함. 똑같은 쿼리 기능도 트랜잭션용 메서드와 비트랜잭션용 메서드로 이중 분리해야 하는 문제 발생. 반복적인 트랜잭션 적용 코드: 각 비즈니스 메서드마다 상투적인 try, catch, finally 롤백/커밋 로직이 지속적으로 중복됨.  ② 예외 누수 문제 (Exception Leak)  데이터 접근 기술 계층의 JDBC 구체 기술 예외인 SQLException(체크 예외)이 서비스 계층까지 전파된다. 서비스는 결국 throws SQLException을 선언할 수밖에 없게 되며, 향후 데이터 접근 기술을 변경할 때 다른 예외 타입으로의 코드 수정이 불가피해진다.  ③ JDBC 반복 문제 (JDBC Boilerplate)  리포지토리 영역에서 매번 커넥션을 열고, PreparedStatement를 바인딩하고, 결과를 매핑하며, finally에서 리소스를 역순으로 해제하는 과정이 극도로 반복된다.  2. 트랜잭션 추상화 (Transaction Abstraction) 데이터 접근 기술마다 트랜잭션을 시작하고 종료하는 코드가 전부 다르다.  JDBC: con.setAutoCommit(false) / con.commit() / con.rollback() JPA: tx.begin() / tx.commit() / tx.rollback()  만약 서비스 계층이 JDBC 트랜잭션에 직접 의존하면 기술 변경 시 서비스 코드의 수정이 유발된다. 이를 극복하기 위해 트랜잭션 추상화 인터페이스를 설계하여 의존성을 단절해야 한다. 1) 개념적인 트랜잭션 인터페이스 구성 public interface TxManager { void begin(); void commit(); void rollback(); } 서비스는 이 개념적인 인터페이스에만 의존(DIP 만족)하고, 실제 구현체인 JdbcTxManager 혹은 JpaTxManager는 스프링 컨테이너가 런타임에 외부 주입(DI)하여 OCP(개방-폐쇄 원칙)를 달성한다.   2) 스프링의 트랜잭션 추상화: PlatformTransactionManager   스프링은 이미 이러한 추상화 인터페이스를 완벽하게 정의하여 제공하고 있다. 개발자는 새로운 인터페이스를 만들 필요 없이 스프링의 표준 기술을 적용하면 된다.  핵심 인터페이스: org.springframework.transaction.PlatformTransactionManager  package org.springframework.transaction; public interface PlatformTransactionManager extends TransactionManager { TransactionStatus getTransaction(@Nullable TransactionDefinition definition) throws TransactionException; void commit(TransactionStatus status) throws TransactionException; void rollback(TransactionStatus status) throws TransactionException; }  getTransaction(): 트랜잭션을 시작한다. 이미 기존에 진행 중인 트랜잭션이 존재한다면 해당 트랜잭션에 참여(Propagation)할 수도 있기 때문에 이름이 start()가 아니라 getTransaction()이다. commit(): 주어진 상태 정보를 기준으로 트랜잭션을 성공 처리(커밋)한다. rollback(): 에러 상황에서 트랜잭션을 취소(롤백)한다.   참고: 스프링 5.3부터는 JDBC 트랜잭션 관리용으로 기존의 DataSourceTransactionManager를 상속받아 기능을 약간 확장한 JdbcTransactionManager를 기본으로 제공한다. 두 기술의 기능 차이는 거의 없으므로 동일한 기술로 이해해도 무방하다.  3. 트랜잭션 동기화 (Transaction Synchronization) 스프링이 제공하는 트랜잭션 매니저는 크게 트랜잭션 추상화와 리소스 동기화의 2가지 역할을 한다. 1) 커넥션을 매개변수로 전달할 때의 단점 하나의 트랜잭션 내부에서 여러 데이터베이스 작업을 처리하려면 동일한 커넥션을 유지해야 한다. 이전에는 서비스에서 생성한 커넥션을 리포지토리 메서드의 파라미터로 직접 전달했다.  단점: 코드가 난잡해지고, 커넥션을 받는 메서드와 받지 않는 메서드가 중복 작성되어 유지보수가 불가능해진다.  2) 트랜잭션 동기화 매니저 (TransactionSynchronizationManager) 스프링은 커넥션 파라미터 없이도 안전하게 동기화를 유지할 수 있도록 트랜잭션 동기화 매니저를 제공한다.  핵심 기술: 내부적으로 자바의 쓰레드 로컬(ThreadLocal)을 사용하여 멀티쓰레드 환경에서 각 쓰레드별로 독립적인 저장소를 부여한다. 이를 통해 각 쓰레드 요청마다 할당된 전용 커넥션을 다른 쓰레드의 간섭 없이 보관하고 조회할 수 있다. 클래스 경로: org.springframework.transaction.support.TransactionSynchronizationManager    3) 동기화 동작 메커니즘 흐름  트랜잭션 시작: 서비스 계층에서 트랜잭션 매니저의 getTransaction()을 호출하여 트랜잭션을 시작한다. 커넥션 획득 및 수동 커밋 설정: 트랜잭션 매니저는 주입받은 데이터소스(DataSource)를 통해 커넥션을 획득한 후 con.setAutoCommit(false)를 설정하여 실제 물리 데이터베이스 트랜잭션을 시작한다. 보관: 트랜잭션 매니저는 생성하고 트랜잭션 처리가 완료된 커넥션을 트랜잭션 동기화 매니저에 보관한다. 리포지토리의 리소스 획득: 리포지토리는 DB 작업을 할 때 파라미터로 커넥션을 전달받지 않는다. 대신 트랜잭션 동기화 매니저로부터 보관되어 있는 커넥션을 꺼내어 SQL을 수행한다. 종료 및 해제: 비즈니스 완료 후 서비스가 커밋 혹은 롤백을 호출하면, 트랜잭션 매니저는 동기화 매니저에서 해당 커넥션을 획득하여 물리 커밋/롤백을 처리하고, 수동 커밋 설정을 원복한 뒤 커넥션을 정상적으로 해제(또는 풀 반환)한다.  4. 트랜잭션 문제 해결 - 트랜잭션 매니저 적용 실습 (V3) 이제 본격적으로 트랜잭션 매니저와 동기화 기술을 소스코드 수준에 적용해 본다. 1) 리포지토리 개선: MemberRepositoryV3 커넥션 파라미터를 완전히 제거하는 대신 스프링이 제공하는 DataSourceUtils 유틸리티 클래스를 사용해 물리 커넥션을 조회하고 반환한다. package hello.jdbc.repository; import hello.jdbc.domain.Member; import lombok.extern.slf4j.Slf4j; import org.springframework.jdbc.datasource.DataSourceUtils; import org.springframework.jdbc.support.JdbcUtils; import javax.sql.DataSource; import java.sql.*; import java.util.NoSuchElementException; /** * 트랜잭션 - 트랜잭션 매니저 도입 버전 * DataSourceUtils.getConnection() * DataSourceUtils.releaseConnection() */ @Slf4j public class MemberRepositoryV3 { private final DataSource dataSource; public MemberRepositoryV3(DataSource dataSource) { this.dataSource = dataSource; } public Member save(Member member) throws SQLException { String sql = "insert into member (member_id, money) values(?, ?)"; Connection con = null; PreparedStatement pstmt = null; try { con = getConnection(); pstmt = con.prepareStatement(sql); pstmt.setString(1, member.getMemberId()); pstmt.setInt(2, member.getMoney()); pstmt.executeUpdate(); return member; } catch (SQLException e) { log.error("db error", e); throw e; } finally { close(con, pstmt, null); } } public Member findById(String memberId) throws SQLException { String sql = "select * from member where member_id=?"; Connection con = null; PreparedStatement pstmt = null; ResultSet rs = null; try { con = getConnection(); pstmt = con.prepareStatement(sql); pstmt.setString(1, memberId); rs = pstmt.executeQuery(); if (rs.next()) { Member member = new Member(); member.setMemberId(rs.getString("member_id")); member.setMoney(rs.getInt("money")); return member; } else { throw new NoSuchElementException("member not found memberId=" + memberId); } } catch (SQLException e) { log.error("db error", e); throw e; } finally { close(con, pstmt, rs); } } public void update(String memberId, int money) throws SQLException { String sql = "update member set money=? where member_id=?"; Connection con = null; PreparedStatement pstmt = null; try { con = getConnection(); pstmt = con.prepareStatement(sql); pstmt.setInt(1, money); pstmt.setString(2, memberId); pstmt.executeUpdate(); } catch (SQLException e) { log.error("db error", e); throw e; } finally { close(con, pstmt, null); } } public void delete(String memberId) throws SQLException { String sql = "delete from member where member_id=?"; Connection con = null; PreparedStatement pstmt = null; try { con = getConnection(); pstmt = con.prepareStatement(sql); pstmt.setString(1, memberId); pstmt.executeUpdate(); } catch (SQLException e) { log.error("db error", e); throw e; } finally { close(con, pstmt, null); } } private void close(Connection con, Statement stmt, ResultSet rs) { JdbcUtils.closeResultSet(rs); JdbcUtils.closeStatement(stmt); // ★ 주의! 트랜잭션 동기화를 유지하려면 DataSourceUtils를 사용하여 커넥션을 반환해야 한다. DataSourceUtils.releaseConnection(con, dataSource); } private Connection getConnection() throws SQLException { // ★ 주의! 트랜잭션 동기화를 사용하려면 DataSourceUtils를 통해 커넥션을 획득해야 한다. Connection con = DataSourceUtils.getConnection(dataSource); log.info("get connection={} class={}", con, con.getClass()); return con; } }  DataSourceUtils.getConnection() 핵심 원리:  트랜잭션 동기화 매니저가 관리하는 쓰레드 로컬 커넥션이 존재할 경우: 해당 커넥션을 획득하여 반환함으로써 하나의 트랜잭션 범위 안에서 같은 커넥션을 동기화하여 사용할 수 있게 해준다. 동기화 매니저가 관리하는 커넥션이 없을 경우: 새로운 커넥션을 생성해서 반환한다.
