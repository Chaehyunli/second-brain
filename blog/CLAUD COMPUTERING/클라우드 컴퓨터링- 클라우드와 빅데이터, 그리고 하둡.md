# [클라우드 컴퓨터링] 클라우드와 빅데이터, 그리고 하둡

## 적용 목적과 전제조건

## 구현 절차·검증·주의점

### 1. 클라우드와 빅데이터: 문제와 해결책의 공존

클라우드 컴퓨팅과 빅데이터는 서로를 필요로 하는 공생 관계에 있음

빅데이터의 생성원: - 소셜 미디어 플랫폼부터 사물 인터넷(IoT) 기기까지, 수많은 클라우드 기반 서비스들은 끊임없이 방대한 양의 데이터를 생성

빅데이터의 해결책: - 동시에 클라우드는 빅데이터를 저장하고, 필요에 따라 분석 클러스터를 유연하게 생성하여 처리 - 이를 통해 과거 대기업만 가능했던 고급 분석 기술의 '상용화'와 '민주화'가 이루어짐

- 초기 클라우드는 중소기업을 중심으로 성장 - 지난 몇 년간 보안과 규정 준수에 집중 투자하며 대기업도 신뢰하고 사용할 수 있는 "엔터프라이즈 레디(Enterprise Ready)" 환경으로 발전

클라우드 비용의 역설 (A Trillion Dollar Paradox)

- 초기 비용 없이 빠르게 시작할 수 있는 장점이 있지만, 기업이 성장함에 따라 "pay as you go(사용한 만큼 지불)" 모델이 오히려 막대한 비용 부담으로 작용하는 역설이 발생 - 성장을 위해 사용한 클라우드가 오히려 기업 가치를 깎아내리는 것

- 사례: 드롭박스(Dropbox)의 클라우드 송환(Repatriation)

문제: 드롭박스는 초기에 AWS를 기반으로 빠르게 성장했지만, 막대한 스토리지 비용으로 수익성이 악화

해결: 핵심 인프라를 자체 데이터센터로 이전하는 과감한 결정을 내림

결과: 2년간 약 7,500만 달러의 비용을 절감하고 수익성을 크게 개선

이는 데이터 엔지니어에게 클라우드가 만병통치약이 아니며, 비즈니스 성장 단계에 맞춰 클라우드와 자체 인프라(On-premise) 사이의 최적의 균형점을 찾는 지속적인 비용 최적화가 중요함을 시사

### 2. 데이터 가치 창출의 주역: 데이터 엔지니어 vs. 사이언티스트

데이터에서 가치를 창출하는 과정은 데이터 엔지니어와 데이터 사이언티스트의 유기적인 협력을 통해 이루어짐

데이터 엔지니어 (Data Engineer): - "데이터의 길을 만드는 건축가" - 원시 데이터(Raw Data)를 분석에 사용할 수 있도록 신뢰할 수 있고 확장 가능한 데이터 파이프라인을 설계, 구축, 유지보수 - "이 데이터를 어떻게 안정적으로, 대규모로, 빠르게 처리할 것인가?"를 고민

데이터 사이언티스트 (Data Scientist): - "정제된 데이터로 미래를 예측하는 전략가" - 통계와 머신러닝 모델을 사용해 데이터를 분석하고 비즈니스 인사이트를 도출 - "이 데이터로 무엇을 알 수 있고, 무엇을 예측할 수 있는가?"에 답을 찾음

- 이 전체 과정을 데이터 엔지니어링 생명주기(Data Engineering Lifecycle) 라고 함 - 원시 데이터의 생성(Generation)부터 수집(Ingestion), 저장(Storage), 변환(Transformation), 서빙(Serving)을 거쳐 분석(Analytics) 및 머신러닝(Machine learning)에 활용되는 전 과정을 포함

### 3. 빅데이터 처리의 핵심 전략: 병렬화와 추상화

- 방대한 양의 데이터를 하나의 컴퓨터로 처리하는 것은 비효율적 - 이를 해결하기 위한 핵심 전략은 분할 정복(Divide and Conquer)

분할 정복:

- 크고 복잡한 문제를 여러 개의 작고 관리하기 쉬운 하위 문제로 나눈 뒤, 각 문제의 답을 구해 다시 합쳐 원래 문제의 답을 찾는 방식

- 하지만 작업을 병렬로 처리하는 것은 다음과 같은 새로운 과제들을 만듬

작업을 어떻게 나누고 할당할 것인가?

작업자(서버)가 실패하거나 응답이 없으면 어떻게 대처할 것인가?

개별 결과들을 어떻게 취합할 것인가?

이러한 문제를 해결하기 위해 다양한 프로그래밍 모델과 디자인 패턴이 개발.

프로그래밍 모델 (소통 방식):

공유 메모리 (Shared Memory): 모든 작업자가 하나의 공유된 공간의 데이터에 접근하는 방식.

메시지 패싱 (Message Passing): 작업자들이 필요할 때마다 서로에게 메시지(데이터)를 직접 전달하는 방식

디자인 패턴 (일 나누는 방식):

마스터-슬레이브 (Master-Slaves): - 중앙 관리자(마스터)가 작업자(슬레이브)에게 일을 할당하고 결과를 취합.

생산자-소비자 (Producer-Consumer): - 한쪽(생산자)은 계속해서 작업을 만들어 공유 공간에 놓고, 다른 쪽(소비자)은 작업을 가져가 처리

공유 작업 큐(Shared work queues): - 작업이 큐에 뜨면, 놀고 있는 작업자가 먼저 와서 작업을 시작하는 방식 - 모두가 공평하고 효율적으로 일하게 됨

- 개발자가 복잡한 시스템 내부를 신경 쓰지 않도록 올바른 수준의 추상화(Abstraction) 를 제공하는 것이 주요 목적!! - 전체 데이터센터를 마치 하나의 거대한 컴퓨터처럼 다룰 수 있게 하는 것

### 4. 대규모 분산 시스템의 "4가지 대원칙 (Big Ideas)"

효율적인 빅데이터 처리를 위해 다음과 같은 핵심 원칙들이 정립

스케일 업 대신 스케일 아웃 (Scale out, not up): - 한 대의 고성능 컴퓨터를 만드는 것(Scale up)보다, 여러 대의 평범한 컴퓨터를 수평적으로 연결해 처리 용량을 늘리는 것(Scale out)이 비용과 확장성 면에서 더 효과적

데이터가 있는 곳으로 처리를 이동 (Move processing to the data): - 클러스터 내 네트워크 대역폭은 한정되어 있으므로, 수십 TB의 데이터를 옮기는 대신, 처리할 코드(프로그램)를 데이터가 저장된 서버로 보내 실행하는 것이 훨씬 효율적

임의 접근 대신 순차 처리 (Process data sequentially, avoid random access): - 디스크에서 흩어져 있는 데이터를 찾는 '탐색(Seek)' 작업은 매우 느림 - 반면, 데이터를 처음부터 끝까지 순서대로 읽는 '스캔(Scan)'은 훨씬 빠름 - 빅데이터 시스템은 가능한 모든 처리를 순차적으로 수행하도록 설계

끊김 없는 확장성 (Seamless scalability): - 시스템 용량을 늘려야 할 때, 복잡한 재설계 없이 단순히 서버를 추가하는 것만으로 간단히 확장이 가능해야 함

### 5. 하둡: 빅데이터 시대를 연 표준 플랫폼

- 아파치 하둡(Apache Hadoop)은 앞서 설명한 "4가지 대원칙"을 구현한 오픈소스 프레임워크 - 빅데이터 저장 및 처리 분야의 사실상 표준(de facto standard)으로 자리 잡았음

하둡의 탄생: - 2003년과 2004년에 구글이 발표한 GFS(Google File System) 와 맵리듀스(MapReduce) 논문에서 영감을 받아 시작

HDFS (Hadoop Distributed File System): 대용량 파일을 여러 서버에 분산하여 저장하는 파일 시스템

YARN (Yet Another Resource Negotiator): 클러스터의 자원을 관리하고 작업 스케줄링을 담당

MapReduce: 대용량 데이터를 분산 병렬 처리하는 프로그래밍 모델

그 외: Hive(SQL 질의), Pig(스크립팅), Sqoop(데이터 수집) 등 다양한 도구들이 하둡 위에서 동작하며 생태계를 구성

하둡 생태계 (Hadoop Ecosystem): - 하둡은 단일 프로그램이 아니라, 여러 핵심 모듈과 관련 프로젝트들이 모인 거대한 생태계
