## 데이터베이스와 DBMS

- **데이터베이스(DB)**: 여러 사용자와 프로그램이 접근할 수 있도록 데이터를 구조·관계·규칙과 함께 저장·관리하는 모음이다. 단순 파일 저장소와 달리 데이터 간 관계와 제약을 포함한다.
- **DBMS**: DB의 데이터를 저장·조회·수정·삭제하는 소프트웨어다. 즉 DB는 저장 대상, DBMS는 이를 운영하는 시스템이라는 역할 분리가 핵심이다.

| DBMS 핵심 기능 | 역할 |
| --- | --- |
| 저장·구조화 | 테이블 등 정의된 구조에 데이터를 저장 |
| 검색·조회 | SQL로 필요한 데이터를 탐색 |
| 동시성 제어 | 여러 사용자의 동시 접근에서 데이터 충돌을 관리 |
| 보안·백업 | 접근 권한을 제어하고 장애 시 복구 |

### 관계형 DBMS와 NoSQL

| 구분 | 관계형 DBMS(RDBMS) | NoSQL DBMS |
| --- | --- | --- |
| 구조 | 테이블과 사전 정의 스키마 | 문서·키-값·그래프 등 유연한 구조 |
| 예 | PostgreSQL, MySQL, Oracle | MongoDB, Redis, Cassandra |
| 강점 | 관계 표현과 일관성 | 대용량·비정형 처리와 확장성 |

**ERD(Entity-Relationship Diagram)**는 테이블(엔티티)과 관계를 구현 전에 설계하는 그림이다. 개발자·기획자·분석가가 같은 데이터 구조를 논의하는 공용 언어가 된다.

## PostgreSQL 대규모 운영 사례

원문은 OpenAI가 PostgreSQL 중심의 단일 프라이머리 구조를 최적화해 대규모 서비스를 운영한 사례를 소개한다. 이는 “무조건 전면 샤딩”보다 워크로드별로 검증된 기술을 조합하는 선택의 사례다.

| 관측 지표 | 원문의 의미 |
| --- | --- |
| 월간 사용자 8억 명 이상 | ChatGPT/API 규모의 운영 맥락 |
| 읽기 복제본 약 50대 | 지역별 읽기 트래픽 분산 |
| 최근 1년 DB 규모 10배 이상 | 빠른 성장에 대한 운영 대응 |
| 쓰기 프라이머리 1대 | 모든 쓰기의 단일 진입점 |

- 프라이머리는 `Azure PostgreSQL Flexible Server` 1대로 쓰기를 처리하고, 읽기는 지역 복제본으로 오프로드한다.
- 원문은 초당 수백만 쿼리와 낮은 두 자릿수 ms의 `p99` 지연시간을 목표로 언급한다.
- 쓰기 확장이 필요한 워크로드는 `Azure CosmosDB`로 이동하는 **polyglot persistence** 전략을 사용한다. 하나의 DB가 모든 문제를 해결하지 않는다는 뜻이다.

| 문제 | 왜 문제인가 | 대응 |
| --- | --- | --- |
| 단일 프라이머리 쓰기 한계 | 모든 `INSERT`/`UPDATE`가 한 노드에 집중 | 샤딩 가능한 워크로드를 CosmosDB로 이동 |
| MVCC 쓰기 증폭 | `UPDATE` 때 새 로우 버전이 만들어져 정리 비용 증가 | 애플리케이션 쓰기 최적화와 `vacuum` 관리 |
| 스키마 변경 | 큰 테이블 재작성·잠금 가능 | 경량 변경 위주, 5초 타임아웃 |
| Connection Storm | 연결 한도 소진 시 서비스 장애 | Kubernetes 환경의 `PgBouncer` 풀링 |
| 복제본 증가 | 프라이머리가 각 복제본에 WAL을 직접 전송 | 계단식 복제(cascading replication) 검토 |

### MVCC와 WAL

- **MVCC**는 여러 트랜잭션이 서로를 덜 방해하도록 데이터의 여러 버전을 유지하는 방식이다. 대신 이전 버전이 누적되므로 `vacuum`이 필요하다.
- **WAL(Write-Ahead Logging)**은 데이터 파일보다 변경 로그를 먼저 기록한다. 커밋 시 로그를 안전하게 기록한 뒤, 체크포인트에서 데이터 파일에 반영한다. 장애 시 로그를 재실행(Redo)하고 미커밋 변경은 취소(Undo)하는 기반이 된다.

## 벡터·그래프 DB와 확장성의 한계

### TigerVector 사례

원문은 `TigerGraph`에 벡터 검색을 결합한 TigerVector를 소개한다. 노드에 임베딩 속성을 두고 전용 인덱스와 MPP 그래프 엔진을 통합하여, “벡터 유사 항목을 찾은 뒤 그래프 관계를 탐색”하는 복합 질의를 `GSQL`에서 수행하는 방향이다. 원문에 따르면 2024년 12월 TigerGraph v4.2에 반영되고 SIGMOD 2025 산업 트랙에도 채택되었다.

- **MPP(Massively Parallel Processing)**: 여러 독립 노드가 데이터를 나눠 동시에 처리하는 구조다.
- **Shared Nothing**: 노드별 메모리·디스크를 독립적으로 사용한다.
- 대규모 DW/분석 플랫폼에서 scale-out에 유리하지만, 분산 환경의 인덱스·통신 비용도 함께 고려해야 한다.

### 반증 사례: 코어를 늘려도 항상 빨라지지 않는다

원문은 Argonne 국립연구소 등이 Polaris·Aurora에서 `Qdrant`, `Milvus`, `Weaviate`를 최대 256 워커까지 평가한 사례를 제시한다. 데이터셋은 임베딩 8,800만 개, 약 843.56GB 규모로 소개된다.

| 결과 | 원문 수치 | 해석 |
| --- | --- | --- |
| 코어 추가 시 처리량 감소 | 최대 30.67% | 자원 증설이 자동 성능 향상을 뜻하지 않음 |
| 워커 16→256 확장 | 실제 5.46배(이상적 16배) | 선형 확장과 큰 차이 |
| Milvus 쓰기 증폭 | 95GB→266GB, 2.8배 | 대규모 저장 비용이 중요 |

원문의 결론은 기술을 설계된 환경(클라우드)과 실제 배치 환경(HPC)의 차이 없이 적용하면 병목이 생길 수 있다는 점이다.

## 트랜잭션: ACID, 격리, 합의

| ACID | 의미 |
| --- | --- |
| Atomicity | 작업 전체가 모두 성공하거나 모두 실패 |
| Consistency | 전후 데이터 규칙·일관성 유지 |
| Isolation | 동시 실행 트랜잭션의 간섭 제어 |
| Durability | 커밋된 결과의 영속성 |

### WAL과 Consensus의 역할 차이

| 구분 | WAL | Consensus |
| --- | --- | --- |
| 주 적용 범위 | 단일 DBMS·노드 중심 | 분산 DB·여러 노드 |
| 목적 | 복구·트랜잭션 보장 | 노드 간 동일 상태 보장 |
| 핵심 원리 | 로그 선기록 후 데이터 반영 | 과반 합의 뒤 커밋 |
| 사례 | PostgreSQL, Oracle, SQL Server | Spanner, Aurora, CockroachDB |

**Consensus**는 리더가 로그를 제안하고 팔로워 다수의 동의 뒤 커밋하는 방식이다. 강한 일관성과 장애 대응에 유리하지만 네트워크 지연이 비용이 된다.

### Isolation level과 이상 현상

| 수준 | Dirty Read | Non-repeatable Read | Phantom Read |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 허용 | 허용 | 허용 |
| READ COMMITTED | 차단 | 허용 | 허용 |
| REPEATABLE READ | 차단 | 차단 | 구현별 차이 |
| SERIALIZABLE | 차단 | 차단 | 차단 |

- **Dirty Read**: 미커밋 값을 읽음.
- **Non-repeatable Read**: 같은 행을 다시 읽을 때 다른 트랜잭션의 수정·삭제로 값이 달라짐.
- **Phantom Read**: 같은 조건의 범위 조회에서 다른 트랜잭션의 삽입·삭제로 행 수가 달라짐.
- PostgreSQL의 `REPEATABLE READ`는 스냅샷 격리 성격이며, 완전 직렬성은 `SERIALIZABLE`(SSI)을 사용한다는 설명이 원문에 있다.

## 관계형 모델링과 정규화

### 핵심 구성

| 개념 | 설명 |
| --- | --- |
| 테이블/관계 | 행과 열로 이루어진 2차원 구조 |
| PK | 행을 고유 식별, NULL·중복 불가 |
| FK | 다른 테이블 PK를 참조해 관계·참조 무결성 표현 |
| UK | 중복 불가, NULL은 허용 가능한 키 |

- 1:1, 1:N, N:M이 기본 카디널리티다.
- N:M은 직접 구현하지 않고 **교차 테이블**로 두 개의 1:N으로 분해한다.
- `ON DELETE CASCADE`, `SET NULL`, `RESTRICT`, `NO ACTION`은 삭제 시 참조 무결성 동작을 선택하는 옵션이다.

### 정규화

- **1NF**: 한 셀에는 원자값 하나만 둔다. 반복 그룹을 제거한다.
- **2NF**: 복합키 일부에만 종속되는 비키 속성을 분리한다.
- **3NF**: 비키 속성 사이의 이행적 종속을 분리한다.
- **BCNF**: 모든 결정자가 후보키가 되도록 더 엄격히 분해한다.

실무에서는 3NF까지 우선 적용하고, 읽기 성능 요구가 명확할 때 의도적 반정규화를 검토한다. 정규화는 중복·갱신 이상을 줄이지만 테이블과 `JOIN`이 늘어날 수 있다.

## SQL과 물리 설계 핵심

### SQL 논리 실행 순서

`FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`

따라서 `WHERE`에서는 같은 `SELECT`에서 정의한 별칭을 일반적으로 사용할 수 없고, `ORDER BY`에서는 사용할 수 있다.

### 물리 설계 체크 포인트

1. 금액은 `NUMERIC(p,s)`처럼 고정 소수 타입을 사용한다.
2. 글로벌 시간은 `TIMESTAMPTZ`와 일관된 타임존 정책을 고려한다.
3. `WHERE`·`JOIN`·`ORDER BY`에 자주 등장하는 컬럼은 인덱스를 검토한다.
4. PostgreSQL에서는 `B-Tree`, JSON/배열·전문검색의 `GIN`, 공간·복합 타입의 `GiST`를 용도에 맞게 선택한다.
5. 대량 테이블 DDL은 재작성·잠금 위험이 있으므로 온라인 변경 전략을 검토한다.

### 낙관적·비관적 잠금

| 구분 | 낙관적 잠금 | 비관적 잠금 |
| --- | --- | --- |
| 가정 | 충돌이 드묾 | 충돌이 잦음 |
| 방식 | 종료 시 버전 비교, 충돌 시 재시도 | 시작 시 잠금 획득 |
| 구현 예 | `version`, `updated_at` | `SELECT ... FOR UPDATE` |
| 적합 | 읽기 중심·낮은 갱신 | 이체·좌석 예매 등 고충돌 |

## 스키마·DDL·DML 주의점

- 멀티 테넌시는 테넌트별 독립 DB(Silo), 단일 DB+`tenant_id`(Pool), 단일 DB+테넌트별 schema(Bridge) 같은 패턴으로 나뉜다. 원문은 PostgreSQL에서 Bridge 모델의 논리 격리·운영 효율을 강조한다.
- `CREATE TABLE`에서는 PK, FK, `NOT NULL`, `UNIQUE`, `CHECK`, 기본값을 먼저 설계한다.
- `UPDATE`와 `DELETE`는 `WHERE` 누락 시 전체 행을 변경·삭제하므로 가장 큰 실행 위험이다.
- `NULL`은 `= NULL`이 아니라 `IS NULL`/`IS NOT NULL`로 검사한다. 값 대체에는 `COALESCE`, 조건 분기에는 `CASE`를 사용한다.
- PostgreSQL의 `CREATE INDEX CONCURRENTLY`는 운영 중 잠금을 줄이기 위한 선택지이나, 운영 절차와 실패 시 정리 방안까지 함께 계획해야 한다.
