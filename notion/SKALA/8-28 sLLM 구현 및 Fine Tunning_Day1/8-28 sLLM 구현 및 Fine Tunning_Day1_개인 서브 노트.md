### 1. 이해관계자 가치 (Pain Point)
#### 범용 LLM이 회사 업무에서 부딪히는 한계
- 범용 LLM(ChatGPT, Claude 등)은 넓은 일반 지식은 갖고 있지만, 회사마다 다른 사내 규정·업무 프로세스·전문 용어 같은 고유한 Knowledge Asset은 애초에 학습 데이터에 없다
- "우리 회사 재택근무 규정이 뭐야?" 같은 질문을 던지면 모델은 일반론적인 답만 하거나, 아예 존재하지 않는 규정을 지어내는 Hallucination 문제가 생긴다
#### 상용 LLM을 사내망에 배치해도 남는 문제
- VPC나 전용 인스턴스로 격리해도 모델의 데이터 활용 정책 자체는 벤더 정책에 의존한다
- "학습에 사용하지 않는다"는 계약 조항이 있어도 기술적으로 완전히 감사하긴 어렵다
- 금융·의료·공공 같은 규제 산업은 이 불확실성 자체를 리스크로 보기 때문에 완전히 내부에서 통제 가능한 구조를 요구하는 경우가 많다
#### sLLM이 필요한 이유
- 완전히 사내에서 운용되기 때문에 데이터가 외부로 나갈 구조 자체가 없음 → 계약이 아니라 아키텍처로 보안을 보증
- 특정 도메인(HR 규정, 설비 매뉴얼 등)에 Fine-Tuning으로 깊게 특화시킬 수 있어서, 범용 LLM보다 좁지만 훨씬 정확한 답변을 줄 수 있음
#### 이해관계자별로 다른 가치
- 규제 산업의 보안 담당자 → "데이터가 외부로 나가지 않는다"는 구조적 보증 자체가 가치
- HR팀 같은 실무 담당자 → "사내 규정을 정확히 반영한 챗봇"이 실질적인 업무 효율화 가치

### 2. Knowledge Asset과 sLLM 활용
#### RAG로 사내 문서를 활용하는 흐름
- 사내 규정 문서를 의미 단위(청크)로 쪼갠다
- 각 청크를 `BGE-M3` 임베딩 모델로 벡터화해서 `FAISS` 인덱스에 저장해둔다
- 사용자가 질문을 하면 그 질문도 똑같이 임베딩해서 FAISS에서 의미적으로 가장 가까운 청크를 검색한다
- 검색된 청크를 Context로 붙여서 Base Qwen2.5-1.5B-Instruct에 넘기면, 모델은 원래 모르던 사내 규정을 Context 안에서 읽고 답변을 생성한다
#### 핵심 포인트
- Base 모델 자체는 전혀 재학습되지 않음 — 모델 파라미터는 그대로고, 검색으로 가져온 외부 지식을 프롬프트에 얹어주는 것뿐
- 범용 모델이 모든 회사 지식을 갖고 있지 않아도, 검색 파이프라인만 잘 구성하면 특정 업무 질문에 대응할 수 있다는 걸 오늘 확인함

### 3. Mini Knowledge Base 구성도
```javascript
[Knowledge Documents]  (사내 규정 문서)
        │  문서 청크 분할
        ▼
[BGE-M3 Embedding]  → 각 청크를 벡터로 변환
        │
        ▼
[FAISS Index]  → Embedding Vector 저장 (벡터 DB)

──────────────── 질의 시점 ────────────────

[사용자 질문]
        │  BGE-M3로 동일하게 임베딩
        ▼
[FAISS Semantic Search]  → 질문과 유사한 청크 검색
        │
        ▼
[검색된 Knowledge Chunk]
        │  질문 + Context로 결합
        ▼
[Base Qwen2.5-1.5B-Instruct]  → 답변 생성
```
#### 흐름 정리
- 색인 단계(위): Knowledge Documents가 미리 Embedding → FAISS Index로 저장
- 질의 단계(아래): 질문이 들어올 때마다 같은 임베딩 과정을 거쳐 Semantic Search로 관련 지식을 찾아 Qwen에 전달
- 색인과 질의가 분리되어 있다는 게 오늘 정리하면서 다시 명확해진 부분

### 4. PEFT(LoRA) 적용 전‧후 Parameter 비교
#### 처음에 잘못 이해했던 지점
- LoRA를 "15억 개 파라미터 중 일부를 골라서 학습시키는 것"으로 이해하고 있었는데, 정확한 그림은 그게 아님
- Base 모델의 기존 파라미터는 하나도 손대지 않고 전부 그대로 동결(Frozen)해두고, `q_proj`, `v_proj` 같은 어텐션 투영층 옆에 완전히 새로운 저랭크(low-rank) 행렬 A, B를 추가로 얹는 것
- 즉 "15억 개 중 일부를 고른다"가 아니라 "15억 개는 그대로 둔 채로, 새 파라미터를 추가한다"가 정확한 이해
#### 숫자로 보면
- 어텐션의 Linear Layer 하나가 1536×1536 크기라면 원래 파라미터는 1536×1536 = 2,359,296개
- LoRA로 대신 표현하면 r=8 기준 A(8×1536) + B(1536×8) = 24,576개만 새로 추가됨 → 원래 파라미터의 1%를 조금 넘는 수준
- `model.print_trainable_parameters()` 실행 시 강의 예시 기준 trainable 4.2M / 전체 1.3B, 비율 0.32%
- 이 숫자는 "1.5B 중 학습 대상으로 선택된 개수"가 아니라 "동결된 원본 위에 새로 추가한 슬롯의 개수"
- 오늘 `peft_lora_parameter_compare_cache.ipynb`를 직접 돌려서 확인한 수치(`target_modules=["q_proj","v_proj"]`, r=8 기준): LoRA 적용 전 전체 파라미터 1,543,714,304개(학습 가능 비율 100%) → 적용 후 전체 파라미터 1,544,803,840개, 학습 대상 파라미터 1,089,536개, 학습 가능 비율 0.0705%
- 강의 예시(0.32%)보다 실제 내 수치(0.0705%)가 더 낮게 나왔는데, target_modules나 r 같은 설정값이 조금만 달라도 실제 학습 대상 규모가 꽤 크게 바뀌는 것을 직접 확인함
#### 구조 생성 시점 vs 값 학습 시점
- LoRA를 붙이자마자 trainable parameter 숫자가 바로 나오는데, 그렇다고 이미 학습이 끝난 건 아님
- `target_modules`와 `r`을 정하는 순간 A, B의 크기(구조)는 즉시 확정됨 → `print_trainable_parameters()`는 이 구조가 만든 슬롯 개수를 세는 것
- 슬롯 안에 의미 있는 값이 채워지는 건 forward → loss 계산 → backward → optimizer step을 반복하는 학습 과정 동안
- 구조가 생기는 시점과 값이 채워지는 시점은 완전히 다른 단계
#### target_modules와 r이 결정하는 것
- LoRA에서 실제로 결정하는 건 두 가지 — 어디에 붙일지(target_modules), 얼마나 크게 만들지(r)
- 오늘 돌려본 예제는 `q_proj`, `v_proj` 두 층에만 적용했지만, 대상 범위가 넓어지거나 r이 커질수록 trainable parameter는 그만큼 늘어나는 구조
- 이 조합이 학습 용량과 비용 사이의 트레이드오프를 정함

### 5. SFT 적용 방향 및 다음 실습과의 연결
#### SFT란
- (질문, 정답) 쌍을 모델에게 직접 학습시켜서 "이런 질문엔 이렇게 답해라"는 응답 패턴 자체를 가중치에 새겨 넣는 방식
#### RAG vs SFT
- RAG: 모델을 전혀 건드리지 않고 질문마다 관련 문서를 찾아 Context로 붙여주는 방식 → 문서만 최신으로 유지하면 됨
- SFT: 모델 내부에 규정 지식과 응답 스타일을 아예 학습시켜 넣음 → 문서 없이도 일관된 답변 가능하지만, 규정이 바뀌면 재학습 필요
#### 다음 실습과의 연결
- 오늘은 Knowledge를 검색해서 붙여주는 방식(RAG)까지만 다뤄봤고, 모델 가중치 자체를 바꾸는 학습은 아직 하지 않았다
- 다음 실습에서는 오늘 확인한 `hr_sft_train.jsonl` / `hr_sft_validation.jsonl`로 LoRA SFT 학습을 직접 돌리고, 학습이 끝난 후에는 `hr_eval.jsonl`로 Base 모델과 Fine-tuned 모델을 같은 질문으로 비교 평가하게 될 예정
- 이때 Keyword Score(규정 핵심 키워드 반영 여부)와 Token F1(정답과 겹치는 정도) 지표로 Fine-tuned 모델이 Base보다 얼마나 나아지는지를 숫자로 확인하게 되면, 오늘 개념으로만 배운 SFT의 효과를 실제로 검증하는 셈이 된다

### 느낀 점
#### 검색이 정확해도 답이 틀릴 수 있다는 걸 직접 봤다
- knowledge_asset_demo_faiss_bge_m3.ipynb 13절에서 다섯 개 질문을 하나씩 대조해보다가 어긋나는 답변을 발견했다. "수료율이 70%라면 교육비 지원을 받을 수 있나요?"라는 질문에, 검색된 근거 문서(HR-EDU-004, "수료율 80% 미만이면 제외 대상", score 0.6913으로 1순위 검색됨)에는 분명히 제외 대상이라고 나와 있는데, 모델은 "지원받을 수 있습니다. 다만 금액은 적게 지급될 것"이라고 반대로 답했다.
- 이 사례를 보면서 문제가 검색 단계인지 답변 생성 단계인지가 명확해졌다. 검색은 정확했고, 모델이 검색된 조건문을 답변 생성 단계에서 제대로 반영하지 못한 게 문제였다. RAG는 관련 문서를 찾아주는 것까지는 잘하지만, 그 안의 조건(숫자, "\~미만" 같은 표현)을 정확히 적용하는 건 별개의 문제라는 걸 체감했다.
#### LoRA 적용 후 파라미터가 오히려 늘어난다는 게 처음엔 안 믿겼다
- peft_lora_parameter_compare_cache.ipynb에서 LoRA 적용 전 전체 파라미터는 1,543,714,304개였는데 적용 후엔 1,544,803,840개로 오히려 늘어났다. 처음엔 "일부만 학습한다면서 왜 전체 개수가 늘어나지?" 싶었는데, 9절에서 실제 학습 대상 파라미터 이름을 보니 전부 lora_A, lora_B라는 새로 생긴 이름들이었다. 기존 파라미터를 고치는 게 아니라 완전히 새로운 파라미터를 얹은 거니까 전체 개수가 느는 게 당연했다.
- 늘어난 부분(1,089,536개) 대비 전체(1,544,803,840개) 비율을 계산하니 0.0705%였다. 강의 예시(0.32%)보다도 낮은 값인데, 같은 target_modules(q_proj, v_proj)라도 세부 설정에 따라 실제 비율이 꽤 달라질 수 있다는 걸 숫자로 확인했다.
#### v_proj의 LoRA 행렬이 비대칭이라는 걸 발견했다
- 9절 출력에서 q_proj는 lora_A, lora_B가 각각 12,288개로 대칭인데, v_proj는 lora_A가 12,288개, lora_B는 2,048개(shape \[256, 8\])로 비대칭이었다. 처음엔 오류인가 싶었는데, Qwen이 Grouped Query Attention 구조라 v_proj의 출력 차원(256) 자체가 q_proj(1536)보다 작기 때문이었다. LoRA 행렬 크기가 그 레이어의 원래 출력 차원을 그대로 따라간다는 걸 실제 숫자로 확인한 셈이다.
### 트러블슈팅
#### RAG 답변이 근거 문서와 어긋난 사례
- 증상: "수료율이 70%라면 교육비 지원을 받을 수 있나요?"라는 질문에, 검색된 근거 문서(HR-EDU-004, 수료율 80% 미만 제외)에는 명확히 제외 대상이라고 나와 있는데, 모델은 "지원받을 수 있습니다"라고 반대로 답했다.
- 원인 추정: 검색 자체는 정확했다(관련 문서가 score 0.6913으로 top-2 안에 잡힘). 문제는 모델이 그 조건문을 답변 생성 단계에서 정확히 반영하지 못한 것 — score가 더 낮았던(0.4828) 지원한도 문서 쪽 논리로 답을 만들어냈다.
- 해결/의미: 코드 에러가 아니라 "고치는" 조치는 없었지만, RAG가 만능이 아니라는 걸 확인하는 계기가 됐다. 실제 서비스라면 조건부 규정에는 근거 문장을 답변에 그대로 인용하게 하거나, 애매한 답변은 사람이 검토하는 장치가 필요할 것 같다.
#### 최초 실행 시 모델 다운로드로 인한 대기
- 증상: peft_lora_parameter_compare_cache.ipynb를 처음 돌렸을 때 Hugging Face 캐시에 Qwen2.5-1.5B-Instruct가 없어서("캐시에서 아직 찾을 수 없습니다" 출력) 3GB 가까운 safetensors 파일을 새로 받아야 했다. "unauthenticated requests" 경고도 함께 떴다.
- 원인: HF_TOKEN을 설정하지 않은 상태로 처음 실행해서 그런 것 — Traceback 없이 경고 문구만 뜨고 다운로드가 계속 진행되는 걸 보고 에러가 아니라는 걸 확인하고 넘어갔다.
- 해결: 다운로드가 끝날 때까지 기다렸고, 이후 knowledge_asset_demo 노트북 실행 시에는 캐시가 이미 존재해서("캐시 디렉토리 존재 여부 → True") 바로 로드됐다.
