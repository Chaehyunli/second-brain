### 가상화 (Virtualization)
물리적인 하드웨어를 소프트웨어로 추상화하여 하나의 컴퓨터를 독립된 여러 대의 컴퓨터처럼 사용할 수 있게 해주는 기술임.

전통적인 물리 서버는 하나의 머신에 Application + OS가 단일로 구동되는 구조였음. 문제는 실제 평균 사용률이 약 6%에 불과해 자원이 심하게 낭비된다는 점이었음. 가상화를 적용하면 동일한 하드웨어 위에 VMware 같은 가상화 레이어를 올려 여러 VM을 동시에 실행할 수 있어, 비싼 서버(High End: 수억\~수십억, Mid-Range: 수억)를 훨씬 효율적으로 활용할 수 있게 됨.
---
#### 가상화를 위한 Hypervisor
물리 서버 위에서 여러 개의 VM(Virtual Machine)을 생성·실행·관리하는 소프트웨어 계층임. 한 컴퓨터의 자원을 나눠 여러 개의 '독립된 컴퓨터'처럼 운영할 수 있게 해주는 가상화 엔진임.
#### 주요 역할
- 물리 하드웨어(CPU, Memory, Disk, NIC 등) 관리
- VM 생성 / 삭제 / Snapshot / Migration 관리
- 각 VM에 적절한 자원 할당
- VM 간 자원 충돌 방지
- VM이 요청하는 하드웨어 명령 중재 및 스케줄
#### Hypervisor 유형

| 구분 | Type-1 (Native / Bare-metal) | Type-2 (Hosted) |
| --- | --- | --- |
| 구조 | Hardware → Hypervisor → Guest OS | Hardware → Host OS → Hypervisor → Guest OS |
| 특징 | OS 오버헤드 없음, 높은 성능·안정성 | 기존 운영체제 위에서 동작 |
| 용도 | 클라우드 IDC, 데이터 센터용 VM 전용 서버 | 데스크탑 테스트/개발용 |
| 솔루션 | VMware ESXi, Hyper-V, KVM, Xen | VMware Workstation, Oracle VirtualBox, Parallels Desktop |

#### \[참고\] Windows Hypervisor: Hyper-V
Hyper-V는 Type-1 방식이지만 구조가 ESXi와 다름. ESXi는 하이퍼바이저 안에 OS 커널 기능과 관리 도구가 내장된 "완전체" 방식인 반면, Hyper-V는 하이퍼바이저가 순수 가상화만 담당하고 별도의 Root Partition(Windows)이 OS 커널 기능과 관리 도구(WSL)를 제공하는 "분리형" 방식임.

- Microsoft는 Windows OS를 Root Partition으로 분리해 관리 권한을 부여함
- Windows는 Host OS로, WSL은 VM 관리 도구로써 제공됨
하이퍼바이저는 실제 하드웨어를 직접 노출하지 않고, 이를 추상화한 **"가상 하드웨어(virtual hardware)"** 를 각 Guest OS에 제공하는 방식으로 동작함.
---
#### VM 구조의 문제점

VM은 물리 서버를 서비스화하여 동적 할당을 지원하지만, 애플리케이션의 설치 및 운영 방식은 기존 전통적인 물리 서버 환경과 동일한 구조임. 즉 VM이 하드웨어 문제는 해결했지만, 앱 배포·운영 단계의 문제는 여전히 남아있음.
#### VM 구조의 고질적 문제 3가지

| 문제 | 내용 |
| --- | --- |
| 거대한 이미지 크기 | VM 이미지는 OS, 가상 하드웨어 등 전체를 포함 → 수 GB \~ 수십 GB |
| 느린 시작 시간 | 부팅 시 Hypervisor → OS → M/W → Appl 단계적 실행 → 수십 초 \~ 수분 소요 |
| VM 간 환경 불일치 | VM은 OS까지만 제공, Appl 실행 환경 구성은 별도 필요 → 환경 불일치 문제 발생 |
---
#### 작은 실행 단위: 컨테이너화 도입

VM의 문제를 해결하기 위해 컨테이너 방식이 도입됨. 핵심 아이디어는 두 가지임.
- Linux Kernel 환경으로 OS 환경을 통합 → 모든 컨테이너가 Host OS의 커널을 공유함
- 애플리케이션과 실행 환경을 통합한 이미지로 생성·관리 → 배포 단위에서 OS 이미지 제거
VM 방식에서는 각 VM이 Guest OS를 따로 가져야 하므로 "Host OS는 Don't Care"(뭐든 상관없음)인 반면, Docker 컨테이너 방식에서는 Host OS가 반드시 Linux Kernel이어야 하고 컨테이너들이 이를 공유함.
---
#### 컨테이너를 통한 VM 문제 해결
VM의 세 가지 고질적 문제가 컨테이너를 통해 어떻게 해결되는지 정리하면 다음과 같음.

| 문제 | VM | 컨테이너 |
| --- | --- | --- |
| 이미지 크기 | OS, 가상 하드웨어 포함 → 수 GB \~ 수십 GB | Appl 실행에 필요한 파일/라이브러리만 포함 → 수십 MB \~ 수백 MB |
| 시작 시간 | 수십 초 \~ 수분 | Kernel 공유, 별도 부팅 없음 → 프로세스 실행 수준 (밀리초 \~ 초) |
| 환경 불일치 | Appl 환경 구성 별도 필요 | 의존 파일/라이브러리를 이미지로 포함 → 동일 Linux Kernel에서 동일 실행 |
컨테이너는 실제로 다수의 Linux 프로세스로 동작함. 운송업에서 표준화된 컨테이너 박스가 어떤 배에도 실을 수 있듯이, 소프트웨어 컨테이너도 어떤 환경에서나 동일하게 실행됨.
---
#### VM 대비 높은 개발 집적도

컨테이너는 VM보다 훨씬 높은 집적도를 제공함. 같은 하드웨어 1대 기준으로 VM은 4\~6개 수준인 반면, 컨테이너는 20\~30개까지 운영 가능함. 슬라이드의 예시에서도 4 VM / 1 Hardware와 16 Container / 1 Hardware를 대등한 수준으로 표현하고 있으며, 이는 컨테이너 방식이 자원 효율 면에서 압도적임을 보여줌.
---
#### 컨테이너 특징 및 VM과의 비교
#### VM의 한계 vs 컨테이너 도입 후 변화
| 비교 항목 | 기존 VM의 한계 | 컨테이너 도입 후 변화 |
| --- | --- | --- |
| 이식성 (Portability) | 환경마다 OS 패키지·라이브러리 버전이 달라 "내 PC에선 되는데 서버에선 에러" 발생 | 앱과 의존성 라이브러리를 단일 패키지로 묶어 로컬·클라우드 어디서든 100% 동일 실행 |
| 이미지 크기 | Guest OS 전체 포함 → 수 GB \~ 수십 GB | OS 커널 제외, 앱 구동에 필요한 파일만 → 수십 MB \~ 수백 MB |
| 기동 속도 | OS 부팅 및 가상 하드웨어 초기화 → 수십 초 \~ 수분 | 프로세스 실행 수준 → 수 밀리초 \~ 수 초 |
| 자원 효율 & 집적도 | VM마다 OS 구동을 위한 고정 CPU/메모리 오버헤드 발생 | 호스트 커널 공유, 필요한 리소스만 소비 |
#### 상세 비교: 가상 서버 vs 컨테이너
| 항목 | 가상 서버 | 컨테이너 |
| --- | --- | --- |
| 가상화 | 서버 가상화, VM 간 격리 | 호스트 자원 공유, 네임스페이스로 앱 간 격리 |
| 이미지화 | OS + 가상 디바이스 포함, 크기 큼 | 필요한 앱과 bin/lib만 포함, 크기 매우 작음 |
| 플랫폼간 이식성 | 동일 하이퍼바이저 간 only | 이기종 물리, 가상, 클라우드 간 이식 가능 |
| 이기종 OS 사용 | 가능 | 불가능 (Host OS와 동일한 OS 계열이어야 함) |
| 부팅시간 | 수십 초 \~ 수분 | 수 밀리초 \~ 수초 |
| 개발 환경 구축 | 수작업으로 앱 설치/삭제, 하루 이상 소요 | 수분 \~ 수십분 |
| 직접도 | 물리 서버당 4\~6 VM | 물리 서버당 20\~30 컨테이너 |
| 앱 확장성 | Low (수작업 요소 많음) | High (완전 자동화 가능) |
| OS Cost | VM 당 | Host 당 |
| 베어메탈 대비 성능 | 50\~80% | 98% |

#### 컨테이너 빌드 방법
Docker는 이미지를 만들기 위해 **Dockerfile**에 DSL(Domain-Specific Language)로 이미지 생성 레이어를 기술함. Dockerfile은 "무엇을 이미지화해야 하는가"를 선언적으로 정의하는 파일임.

```docker
# 베이스 이미지 설정: 가볍고 절약된 용량의 Python 3.10 공식 리눅스(Alpine Linux) 환경을 가져옵니다.
FROM python:3.10-alpine

# OS 패키지 관리자(apk)를 통해 실행 및 패키지 빌드에 필요한 리눅스 도구들을 설치합니다.
# --no-cache: 용량 절약을 위해 임시 패키지 캐시 파일을 저장하지 않고 설치합니다.
# bash, curl, jq: 도커 컨테이너 내부 조작, HTTP 요청 테스트, JSON 데이터 처리를 위한 유틸리티
# gcc, musl-dev, linux-headers: psutil 등 C 언어 기반 컴파일이 필요한 라이브러리 빌드용 도구
RUN apk add --no-cache bash curl gcc musl-dev linux-headers jq

# Python 패키지 관리자(pip)를 이용해 파이썬 웹 프레임워크 및 필요한 라이브러리를 설치합니다.
# fastapi: 웹 애플리케이션 프레임워크
# uvicorn: FastAPI를 실행할 비동기 웹 서버 (ASGI)
# psutil: 시스템 모니터링(CPU, 메모리 등) 라이브러리
# python-multipart: 파일 업로드 및 폼 데이터 처리를 위한 패키지
# prometheus-client: 모니터링 도구(Prometheus) 메트릭 수집용 라이브러리
RUN pip install fastapi uvicorn psutil python-multipart prometheus-client

# 호스트 컴퓨터의 fastserver.py 파일을 컨테이너 내부의 fastserver.py 위치로 복사합니다.
COPY fastserver.py fastserver.py

# 컨테이너가 시작될 때 기본으로 실행할 명령어입니다. (fastserver.py 실행)
CMD ["python3", "fastserver.py"]
```
각 `RUN` 명령은 이미지의 레이어 하나를 생성함. `FROM`으로 베이스 이미지를 지정하고, `RUN`으로 필요한 패키지를 설치하며, `COPY`로 애플리케이션 파일을 이미지 안에 넣고, `CMD`로 컨테이너 실행 시 기본 명령을 정의함.

### 컨테이너로 MariaDB 실행하기
MariaDB를 Docker 컨테이너로 로컬에서 실행하는 실습임. 컨테이너 간 통신을 위해 먼저 Docker 네트워크를 생성하고, 그 위에 MariaDB 컨테이너를 띄우는 순서로 진행함.
#### 실행 명령 흐름
```bash
# 1. skala 네트워크가 없으면 생성 (이미 있으면 스킵)
> docker network inspect skala >/dev/null 2>&1 || \
  docker network create --driver bridge skala

# 2. MariaDB 컨테이너 실행
> docker run -d \
  --name mariadb \
  -e MYSQL_ROOT_PASSWORD=password \
  -e MYSQL_DATABASE=skala \
  -e MYSQL_USER=user \
  -e MYSQL_PASSWORD=password \
  --network skala \
  -p 3306:3306 \
  mariadb:latest

# 3. 컨테이너 실행 확인
> docker ps
```
각 옵션의 의미를 정리하면 다음과 같음.
| 옵션 | 설명 |
| --- | --- |
| `-d` | 백그라운드(detached) 모드로 실행 |
| `--name mariadb` | 컨테이너 이름 지정 |
| `-e MYSQL_ROOT_PASSWORD` | root 계정 비밀번호 환경변수 주입 |
| `-e MYSQL_DATABASE` | 초기 생성할 데이터베이스 이름 |
| `-e MYSQL_USER / PASSWORD` | 일반 사용자 계정 생성 |
| `--network skala` | 앞서 만든 bridge 네트워크에 연결 |
| `-p 3306:3306` | 호스트 포트 → 컨테이너 포트 포워딩 |

### 컨테이너 내부 접속 및 DB 조작
컨테이너가 실행된 후 내부 bash 셸로 진입해 MariaDB에 직접 접속하는 방법임.
```bash
# 컨테이너 내부 bash 진입
> docker exec -it mariadb /bin/bash

# MariaDB 접속 (root 계정, 비밀번호 입력 프롬프트)
# mariadb -u root -p
```
접속 후 데이터베이스 조작 흐름은 아래와 같음.
```sql
-- DB 목록 확인 (information_schema, mysql, performance_schema, skala, sys 등 확인)
MariaDB [(none)]> SHOW DATABASES;

-- 사용할 DB 선택
MariaDB [(none)]> USE skala;

-- 테이블 생성
MariaDB [skala]> CREATE TABLE key_values (
  id INT AUTO_INCREMENT PRIMARY KEY,
  key_column VARCHAR(255) NOT NULL UNIQUE,
  value_column TEXT NOT NULL
);

-- 테이블 확인
MariaDB [skala]> SHOW TABLES;

-- 데이터 삽입
MariaDB [skala]> INSERT INTO key_value (key_column, value_column)
VALUES ('example_key', 'example_value');

-- 데이터 조회
MariaDB [skala]> SELECT * FROM key_value;
-- 결과: id=1, key_column=example_key, value_column=example_value

-- 종료
MariaDB [skala]> exit
```
`docker exec -it` 명령은 실행 중인 컨테이너 안에서 대화형 프로세스를 실행하는 명령임. `-i`는 stdin 유지, `-t`는 pseudo TTY 할당을 의미함.

### 컨테이너 삭제하기
실행 중인 컨테이너를 종료하고 이미지를 정리하는 방법임.
```bash
# 실행 중인 컨테이너 확인
> docker ps

# 컨테이너 정지 (CONTAINER ID 또는 NAMES로 지정)
> docker stop be913f24c917

# 중지된 컨테이너 포함 전체 이미지 정리
> docker image prune -a
# → "Are you sure you want to continue? [y/N]" → y 입력 시 이미지 삭제

# 실행 중이 아닌 컨테이너까지 포함해서 보려면
> docker ps -a
```
`docker image prune -a`는 현재 실행 중이지 않은 컨테이너에서 사용하는 이미지까지 모두 제거함. 주의해서 사용해야 하며, 실습 종료 후 디스크 정리 시 활용함.

### CLI 명령어로 환경 Clear 하기
실습 환경을 깨끗하게 초기화할 때 사용하는 명령 모음임.
#### 기동 중인 컨테이너 중지 및 삭제
```bash
# 실행 중인 컨테이너 확인
> docker ps

# 컨테이너 정지 (CONTAINER ID 또는 NAMES 둘 다 사용 가능)
> docker stop {{CONTAINER ID or NAMES}}
# 예) docker stop 75432fbccc9b

# 컨테이너 삭제
> docker rm 75432fbccc9b
```
#### 이미지, 네트워크, 디스크 전체 클리어
```bash
# 사용하지 않는 컨테이너 리소스 일괄 삭제
# (stop된 컨테이너, 미사용 network, 빌드 캐시, 미실행 이미지 포함)
> docker system prune -a

# 미사용 볼륨 강제 삭제
> docker volume prune -f
```
`docker system prune -a`는 한 번에 정지된 컨테이너, 사용하지 않는 네트워크, 댕글링 이미지, 빌드 캐시를 모두 제거하는 강력한 초기화 명령임. 실습 환경 리셋 시 유용하지만, 필요한 이미지까지 삭제될 수 있으므로 주의가 필요함.

### 컨테이너 이미지 라이프사이클

컨테이너 이미지는 두 가지 경로로 생성·사용됨.
경로 1 — Registry에서 가져오는 흐름 (상단 빨간 박스)
경로 2 — 직접 빌드하는 흐름 (하단 파란 박스)
직접 만든 이미지는 `Push`를 통해 Registry에 올릴 수 있고, 이후 다른 환경에서 Pull하여 재사용할 수 있음. 이 두 흐름이 순환 구조를 이룸.

### Image Registry
이미지를 저장·제공하는 서버임. 공개 레지스트리인 Docker Hub 외에 **Private Registry**를 별도 구축하여 사용하는 것도 일반적임. 본 과정에서는 Docker Hub 대신 Harbor 기반의 Private Registry를 사용함.
- Private Registry URL: `https://skala-registry.skala-ai.com/`
Harbor는 프로젝트(Project) 단위로 이미지 저장소(Repository)를 관리하며, Private/Public 접근 수준을 설정할 수 있음.
#### 이미지 이름(Image Reference) 구조

- Registry: 여러 이미지를 저장·제공하는 전체 서비스/서버
- Repository: Registry 안에서 특정 이미지 계열을 관리하는 개별 저장소 단위

### \[참고\] Docker Hub 이미지 이름 규칙
Docker Hub에 저장되는 이미지는 실제로 `docker.io/library/nginx:latest` 처럼 전체 경로를 가짐. 단, registry 이름과 project 이름이 없는 경우 Docker가 내장 default(`docker.io/library`)에서 검색하므로 `nginx:latest`만 입력해도 동작함.
podman이나 buildah 같은 다른 컨테이너 도구는 `/etc/containers/registries.conf`에 등록된 레지스트리 목록에서 순서대로 검색함.
```plain text
unqualified-search-registries = ["docker.io","quay.io","registry.fedoraproject.org"]
```

### 컨테이너 이미지 레이어 구조
컨테이너 이미지는 여러 개의 읽기 전용 레이어로 구성됨. Dockerfile의 각 명령(RUN, COPY 등)이 레이어 하나를 생성함.

```docker
FROM ubuntu:22.04

RUN apt-get update && \
    apt-get install -y --no-install-recommends nginx && \

COPY ./src /var/www/html

CMD ["nginx", "-g", "daemon off;"]
```
레이어 공유의 실용적 의미:

- 이미지 A와 B가 레이어 1\~3을 공유하는 경우, 이미지 A를 삭제해도 레이어 1\~3은 삭제되지 않음 (이미지 B가 여전히 참조 중이므로)
- 이미지 C(레이어 5, 6, 7)를 이미 다운로드한 경우, 이미지 D(레이어 5, 6, 8)는 레이어 8만 추가로 다운로드하면 됨. 이미지 E(레이어 5, 7, 8)도 마찬가지로 중복 다운로드 없이 처리됨

### 이미지 검색하기
#### Docker Hub 개요
Docker는 `https://registry.hub.docker.com`을 통해 이미지를 공유하는 생태계를 구축함. 유명 리눅스 배포판과 오픈소스 프로젝트(Redis, Nginx 등) 이미지를 모두 Docker Hub에서 구할 수 있으며, 이미지 관련 명령은 기본적으로 Docker Hub를 이용하도록 설정되어 있음.
#### CLI로 이미지 검색
```bash
docker search <이미지 이름>

# 예)
$ docker search ubuntu
```
검색 결과에서 `ubuntu`, `centos`, `redis`처럼 OS나 프로그램 이름을 가진 것이 **공식 이미지**이며, 나머지는 사용자들이 만들어 공개한 이미지임.
### Docker Hub UI에서 검색
`https://hub.docker.com`에서 이미지를 검색한 뒤, 해당 이미지의 Tags 탭에서 버전을 확인할 수 있음. Private Registry는 Harbor UI(`https://skala-registry.skala-ai.com/`)에서 동일하게 확인 가능함.
---
#### 이미지 내려받기
```bash
docker pull <이미지 이름>:<태그>

# 예)
$ docker pull ubuntu
```
주요 규칙:
- 태그를 생략하면 `latest`(최신 버전)가 default로 적용됨. **명시적으로 버전 태그를 지정하는 것을 권고함**
- `ubuntu:14.04`, `ubuntu:12.10`처럼 버전 지정 가능
- `pyrasis/ubuntu`처럼 `/` 앞에 사용자명을 붙이면 해당 사용자가 올린 이미지를 받음 (공식 이미지는 사용자명 없음)
- 호스트 OS의 배포판과 컨테이너 이미지의 배포판 종류가 달라도 됨. 즉 CentOS 호스트에서 Ubuntu 컨테이너를 실행하는 것도 가능함

`docker images ubuntu`처럼 이미지 이름을 지정하면 이름은 같지만 태그가 다른 이미지들을 한번에 출력할 수 있음.

### 컨테이너 실행하기
```bash
docker run <옵션> <이미지 이름> <실행할 파일>

# 예) ubuntu 이미지로 bash 셸 실행
$ docker run -it --name hello ubuntu:latest /bin/bash
```
주요 옵션:
| 옵션 | 설명 |
| --- | --- |
| `-i` | interactive — stdin 유지 (입력 가능) |
| `-t` | pseudo-tty — 터미널 할당 (출력 가능) |
| `--name` | 컨테이너 이름 지정. 미지정 시 Docker가 자동 생성 |
컨테이너 안에서 `cd`, `ls` 등으로 내부 파일시스템을 둘러볼 수 있음. `exit`를 입력하면 bash 셸이 종료되고, `/bin/bash`를 실행한 컨테이너였으므로 **bash 종료 = 컨테이너 정지(stop)** 됨.
---
### 컨테이너 목록 확인하기
```bash
# 실행 중인 컨테이너만 확인
$ docker ps

# 정지된 컨테이너 포함 전체 확인
$ docker ps -a   (또는 --all)
```
- `a` 옵션을 사용하면 STATUS가 `Exited`인 정지된 컨테이너도 함께 출력됨. 옵션 없이 사용하면 `Up` 상태인 실행 중인 컨테이너만 출력됨.

### 컨테이너 시작하기
```bash
docker start <컨테이너 이름>   (또는 컨테이너 ID)

# 예)
$ docker start hello
```
정지된 컨테이너를 다시 시작할 때 사용함. 컨테이너 이름 대신 컨테이너 ID를 사용해도 동일하게 동작함. 시작 후 `docker ps`로 STATUS가 `Up`으로 바뀐 것을 확인할 수 있음.

OS 재부팅처럼 컨테이너를 stop 후 start하는 동작임. 컨테이너 이름 대신 컨테이너 ID를 사용해도 됨.

### 외부에서 컨테이너 안의 명령 실행하기
```bash
docker exec <컨테이너 이름> <명령> <매개 변수>

# 예) 컨테이너 내부에서 echo 명령 실행
$ docker exec hello echo "Hello World"
Hello World
```
컨테이너 내부로 직접 진입하지 않고, 외부 호스트에서 컨테이너 안의 명령을 바로 실행하는 방법임.
- 컨테이너가 실행 중인 상태에서만 사용 가능하며, **정지된 상태에서는 사용할 수 없음**
- 컨테이너 이름 대신 컨테이너 ID를 사용해도 됨
---
### 외부에서 컨테이너 내 shell 프로세스 실행
```bash
docker exec -it <컨테이너 이름> /bin/bash   # 또는 /bin/sh

# 예)
$ docker exec -it hello /bin/bash
# ls
```
컨테이너 내부 shell에 대화형으로 접속하고자 할 때 사용함. `-i`(interactive)와 `-t`(pseudo-tty)를 함께 사용하면 Bash 셸에 입력 및 출력이 가능해짐.
`docker run -it`이 컨테이너를 새로 생성하면서 bash를 실행하는 것이라면, `docker exec -it`은 이미 실행 중인 컨테이너에 추가로 bash 프로세스를 붙이는 것임. 실행 중인 컨테이너를 건드리지 않고 내부를 살펴볼 때 주로 사용함.

### 컨테이너에 Volume 연결하기
```bash
docker run --name <컨테이너명> -v <호스트 경로>:<컨테이너 내부 경로> <이미지 명:버전> <명령>
```
호스트의 로컬 디렉토리를 컨테이너 내부 경로에 마운트하는 방법임. 컨테이너가 삭제되어도 호스트의 파일은 유지되므로 데이터 영속성을 확보할 수 있음.
```bash
# 1. 마운트할 디렉토리 및 파일 준비
$ mkdir -p ./data
$ echo "hello docker world" > ./data/info.txt

# 2. 컨테이너 실행 시 볼륨 마운트
$ docker run -it --name hello -v $(pwd)/data:/app/data ubuntu:latest /bin/bash

# 3. 컨테이너 내부에서 확인
# cd /app/data
# ls
# cat info.txt
hello docker world
# touch add.txt   # 컨테이너 안에서 파일 생성
# exit

# 4. 호스트에서 확인 → 컨테이너가 만든 add.txt도 함께 보임
$ ls ./data/
add.txt  info.txt

# 5. 정리
$ docker stop hello && docker rm hello
```
Volume 마운트의 핵심은 **컨테이너 내부와 호스트가 동일한 실제 디렉토리를 공유**한다는 점임. 컨테이너 안에서 파일을 생성하면 호스트에도 즉시 반영되고, 반대도 동일함. DB 데이터, 로그 파일, 설정 파일 등을 영속적으로 관리할 때 필수적으로 사용함.

### docker 운영 환경 명령어 정리
| 명령어 | 설명 |
| --- | --- |
| `docker container prune` | 중지된 모든 컨테이너를 제거 |
| `docker image prune` | 태그가 없는 모든 이미지 파기. `-a` 옵션은 모든 이미지 파기 |
| `docker system prune` | 사용하지 않는 모든 데이터 삭제 (이미지, 컨테이너, 볼륨, 네트워크 등) |
| `docker container stats` (= `docker stats`) | 컨테이너 사용 현황 실시간 출력 (CPU, MEM, NET I/O 등) |
| `docker network list` (= `docker network ls`) | 생성된 network 정보 검색. 상세 정보는 `inspect` 사용 |
`docker stats`는 실행 중인 컨테이너들의 CPU 사용률, 메모리 사용량, 네트워크 I/O, 블록 I/O를 실시간으로 모니터링할 때 유용함.

### Dockerfile이란?
Dockerfile은 컨테이너 이미지 빌드 절차 명세서임. 이미지를 생성하기 위한 명령어/지시문의 집합으로, Docker는 Dockerfile의 지시문을 읽어 이미지를 자동으로 생성함.

---
### Dockerfile 작성 예시 (nginx 서버 이미지)
ubuntu:latest를 베이스로 nginx를 설치하는 기본 예시임.
```docker
# 베이스 이미지 설정: 가장 최신 버전의 우분투(Ubuntu) 리눅스 환경을 기반으로 시작합니다.
FROM ubuntu:latest

# 작성자 정보: 이미지 관리자의 이름과 이메일을 명시합니다. (참고: 최신 도커 버전에서는 LABEL maintainer="..." 사용을 더 권장합니다)
MAINTAINER Foo Bar [이메일 주소 삭제]

# 우분투 패키지 목록 업데이트: 최신 패키지 정보를 다운로드합니다.
RUN apt-get update

# Nginx 웹 서버 설치: -y 옵션을 주어 설치 중간에 나오는 확인(Yes/No) 물음에 자동으로 Yes를 응답합니다.
RUN apt-get install -y nginx

# Nginx 설정 수정: 컨테이너가 백그라운드가 아닌 데몬 모드 off(포그라운드)로 실행되도록 설정을 추가합니다. 
# (도커 컨테이너는 메인 프로세스가 포그라운드에서 계속 실행되어야 종료되지 않고 유지됩니다)
RUN echo "\ndaemon off;" >> /etc/nginx/nginx.conf

# 권한 변경: Nginx가 사용하는 라이브러리 폴더의 소유자를 웹 서버 기본 계정(www-data)으로 변경합니다.
RUN chown -R www-data:www-data /var/lib/nginx

# 익명 볼륨 설정: 지정한 3개 경로(/data, Nginx 설정, 로그)를 마운트 지점으로 지정합니다.
```

```plain text
# Comment (주석)
```

### Dockerfile 명령어 전체 정리
| 명령어 | 설명 | 예시 |
| --- | --- | --- |
| `FROM` | 베이스 이미지 지정 | `FROM ubuntu:14.04` |
| `RUN` | 빌드 시 실행할 명령어 | `RUN ["mv", "1234", "5678"]` |
| `EXPOSE` | 컨테이너 외부에 노출할 포트 | `EXPOSE 80` |

| `ENTRYPOINT` | 컨테이너 실행 시 기본 명령어 (CMD와 달리 옵션을 넘길 수 있음) | `ENTRYPOINT ["python"]` |

| `ARG` | 빌드 시점에만 사용할 변수 정의 | `ARG NODE_VERSION=18` |
| `SHELL` | 사용할 쉘 타입 지정 | `SHELL ["/bin/sh", "-c"]` |

### FROM 명령어
```docker
FROM [--platform=<platform>] <image>[:<tag>] [AS <name>]
```
- 빌드 스테이지를 초기화하고 이후 명령어들의 베이스 이미지를 정의함
- `ARG`는 `FROM` 앞에 위치할 수 있는 유일한 지시어 → 베이스 이미지 버전 등을 변수화할 수 있음
- 하나의 Dockerfile 안에서 `FROM`을 여러 번 사용할 수 있음 → **Multi-stage Build**: 최종 이미지 용량 최적화 및 빌드 의존성 분리에 활용

```docker
# A. 기본 베이스 이미지 지정
FROM ubuntu:22.04

# B. ARG로 버전 유연화
ARG NODE_VERSION=18-alpine
```

### FROM 명령어: Multi-Stage Build
빌드 도구와 런타임 환경을 분리하여 최종 이미지 크기를 대폭 줄이는 패턴임.
```docker
# [Stage 1] Build Stage: Vue.js 소스코드 컴파일
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# [Stage 2] Production Stage: Nginx 배포 및 실행
FROM nginx:stable-alpine
WORKDIR /usr/share/nginx/html
RUN rm -rf ./*
# builder 스테이지에서 생성된 정적 빌드 파일(dist)만 복사
COPY --from=builder /app/dist .
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```
**\[Stage 1\] Vue.js 소스코드 컴파일 Stage**
- **`FROM node:22-alpine AS builder`**
	- Node.js 22버전(가벼운 Alpine 리눅스 기반) 환경을 불러오고, 이 빌드 단계를 `builder`라는 이름으로 부르겠다고 선언합니다.
- **`WORKDIR /app`**
	- 이후 실행될 작업들의 기본 경로를 `/app` 디렉토리로 지정합니다.
- **`COPY package*.json ./`**
	- 의존성 목록이 적힌 `package.json`과 `package-lock.json` 파일을 현재 작업 디렉토리(`/app`)로 복사해옵니다.
- **`RUN npm install`**
	- 복사한 파일 정보를 바탕으로 필요한 라이브러리/패키지들을 설치합니다.
- **`COPY . .`**
	- 내 컴퓨터의 모든 프로젝트 소스코드 파일들을 컨테이너 내부로 복사합니다.
- **`RUN npm run build`**
	- 작성된 Vue.js 소스코드를 브라우저가 읽을 수 있는 정적 파일(HTML, CSS, JS)로 변환(컴파일)합니다. 결과물은 `/app/dist` 폴더에 생성됩니다.
**\[Stage 2\] Nginx 배포 및 실행 Stage**
- **`FROM nginx:stable-alpine`**
	- 초경량 Nginx 웹 서버 환경을 새로 불러와 두 번째 스테이지를 시작합니다. (Stage 1에서 설치했던 무거운 Node.js와 소스코드는 이 시점에 모두 버려집니다)
- **`WORKDIR /usr/share/nginx/html`**
	- Nginx가 웹에 보여줄 HTML 파일들을 보관하는 기본 폴더 경로로 이동합니다.
- **`RUN rm -rf ./*`**
	- Nginx 이미지가 기본적으로 가지고 있던 기존의 샘플 HTML 파일들을 깨끗하게 전부 삭제합니다.
- **`COPY --from=builder /app/dist .`**
	- **(가장 핵심)** `builder`라고 명명했던 Stage 1에서 만들어진 `/app/dist` (빌드 결과물) 폴더 안의 파일들만 쏙 빼와서 현재 위치(Nginx의 html 폴더)로 복사합니다.
- **`EXPOSE 80`**
	- 이 컨테이너가 80번 포트(HTTP 기본 포트)를 사용한다는 점을 명시합니다.
- **`CMD ["nginx", "-g", "daemon off;"]`**
	- 컨테이너가 시작될 때 Nginx 웹 서버를 백그라운드가 아닌 포그라운드 모드로 실행하여 컨테이너가 종료되지 않고 계속 유지되도록 만듭니다.
장점:
- Node.js 개발 도구, 소스코드, node_modules이 최종 배포 이미지에 포함되지 않음
- 보안성 강화
- 이미지 크기가 수백 MB → 수십 MB로 축소

### RUN 명령어
```plain text
RUN <command>
```
이미지 빌드 시점에 실행되는 명령어임. 패키지 설치, 파일 생성, 권한 변경 등 이미지에 영구적으로 반영되어야 할 기초 환경을 구성할 때 사용함.
- RUN 명령어가 실행될 때마다 이미지 레이어가 하나씩 추가됨 → 불필요하게 많이 작성하면 이미지가 비대해짐
- 동일한 RUN 명령은 Docker가 기존 빌드된 레이어를 재사용(캐싱)하여 빠르게 처리함
	- 이전의 Multi-Stage 예시에 Stage 1 이후 Stage 2에서 에러가 나면, Stage 1은 캐싱이 되어 있기 때문에 다시 빌드 x(다시 빌드하게 하려면, 캐싱 x인 옵션 선택)
#### 두 가지 형식
```docker
# Shell 폼 (가장 대중적): &&로 묶어 단 하나의 레이어만 생성
RUN apt-get update && apt-get install -y \
    curl \
    git \
    && rm -rf /var/lib/apt/lists/*

# Exec 폼 (셸을 거치지 않고 바이너리 직접 실행)
RUN ["mkdir", "-p", "/var/www/html"]
```
→ `apt-get update && apt-get install -y` 이거는 앞의 `apt-get update`가 성공하면 뒤의 것을 실행하게 됨.
→ `RUN` 단위로 하나의 이미지로 빌드 되기 때문에 `&&`로 2개의 명령어를 하나의 이미지로 만들기 위해서 한 줄에서 처리하는 것임
마지막에 `rm -rf /var/lib/apt/lists/*`를 추가하는 것은 apt 캐시를 제거해 이미지 크기를 줄이는 관용적인 패턴임.

### \[실습\] Multi-Stage 실습하기 (Vue.js 프론트엔드)
```docker
# 빌드 스테이지
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 배포 스테이지
FROM nginx:alpine
RUN rm /etc/nginx/conf.d/default.conf
COPY default.conf /etc/nginx/conf.d/
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```
`default.conf` (nginx가 Vue.js 정적 파일을 서빙하고 Spring Boot API를 프록시하는 설정):
```plain text
server {
    listen80;

    location / {
        root/usr/share/nginx/html;
        indexindex.html;
        try_files$uri $uri/ /index.html;
        expires-1;
        add_headerCache-Control "no-store, no-cache, must-revalidate";
    }

    location /api {
        resolver127.0.0.11 valid=10s;
        set$backend "spring-backend:8080";
        proxy_passhttp://$backend;
        proxy_http_version1.1;
        proxy_set_headerHost $host;
    }
}
```
빌드 및 실행:
```bash
> docker buildx build --tag vue-frontend:1.0 .
> docker run -d --name vue-frontend -p 8080:80 vue-frontend:1.0

# 접속 확인
http://localhost:8080

# 종료
> docker stop vue-frontend
> docker rm vue-frontend
```
### **1. Dockerfile 키워드 및 옵션**
- **`FROM node:22-alpine AS builder`**
	- `node:22-alpine`: Node.js 22버전이 설치된 경량화된 Alpine Linux 이미지를 불러옵니다.
	- `AS builder`: 이 빌드 스테이지에 `builder`라는 별칭을 붙입니다. 나중에 다른 스테이지에서 이 이름을 참조해 파일만 가져올 수 있습니다.
- **`WORKDIR /app`**
	- 컨테이너 내부의 작업 디렉토리를 `/app`으로 변경합니다. 이후 명령어(`COPY`, `RUN` 등)는 모두 이 경로 기준으로 실행됩니다.
- **`COPY package*.json ./`**
	- `package*.json`: 와일드카드()를 써서 `package.json`과 `package-lock.json`을 동시에 선택합니다.
	- `./`: 현재 지정된 `WORKDIR`(`/app`)로 파일들을 복사합니다.
- **`RUN npm ci`**
	- `npm ci` (Clean Install): `package-lock.json`에 명시된 버전과 완전히 동일한 패키지를 엄격하게 설치합니다. (`npm install`보다 빌드 속도가 빠르고 결과가 안정적입니다)
- **`COPY . .`**
	- 첫 번째 `.`: 내 컴퓨터의 현재 폴더 전체
	- 두 번째 `.`: 컨테이너의 현재 작업 디렉토리 (`/app`)
- **`RUN npm run build`**
	- Vue 프로젝트의 빌드 스크립트를 실행하여 production용 정적 파일들을 `/app/dist` 폴더에 생성합니다.
- **`RUN rm /etc/nginx/conf.d/default.conf`**
	- `rm`: 파일 삭제 명령어입니다. Nginx가 기본적으로 가지고 있는 샘플 설정 파일을 지웁니다.
- **`COPY default.conf /etc/nginx/conf.d/`**
	- 내가 직접 만든 Custom Nginx 설정 파일(`default.conf`)을 Nginx 설정 폴더에 복사해 넣어 교체합니다.
- **`COPY --from=builder /app/dist /usr/share/nginx/html`**
	- `-from=builder`: 이전 스테이지(`builder`)의 컨테이너 내부를 가리킵니다.
	- `/app/dist`: 가져올 원본 파일 위치입니다.
	- `/usr/share/nginx/html`: 복사해 넣을 대상 위치(Nginx가 웹 페이지를 띄우는 기본 폴더)입니다.
- **`EXPOSE 80`**
	- 컨테이너가 80번 포트(HTTP)를 사용할 것임을 문서화/명시합니다. (실제 포트 개방은 실행 시 `p` 옵션이 담당합니다)
- **`CMD ["nginx", "-g", "daemon off;"]`**
	- `CMD`: 컨테이너가 시작될 때 자동으로 실행할 명령어를 정의합니다.
	- `g`: Nginx의 global 설정을 명령행에서 직접 주입할 때 씁니다.
	- `"daemon off;"`: Nginx를 백그라운드가 아닌 포그라운드(Foreground)로 띄워, 컨테이너가 종료되지 않고 계속 유지되도록 만듭니다.
### **2. Nginx 설정 (****`default.conf`****) 블록 및 옵션**
- **`server { ... }`**: 하나의 웹 사이트/서버에 대한 블록을 정의합니다.
- **`listen 80;`**: Nginx가 80번 포트에서 들어오는 요청을 감지합니다.
- **`location / { ... }`**: 루트 경로(`/`)로 들어오는 모든 웹 요청을 처리하는 블록입니다.
	- **`root /usr/share/nginx/html;`**: 클라이언트에게 보여줄 HTML/JS 파일들이 보관된 폴더 경로입니다.
	- **`index index.html;`**: 사용자가 주소 뒤에 파일명을 안 적었을 때 기본으로 열어줄 파일입니다.
	- **`try_files $uri $uri/ /index.html;`**:
		1. `$uri`: 요청한 파일이 존재하면 보여줌
		2. `$uri/`: 요청한 폴더가 존재하면 그 안의 index 파일을 보여줌
		3. `/index.html`: 둘 다 없으면 무조건 `index.html`로 튕겨서 Vue 라우터가 주소를 처리하게 함 (SPA 필수 설정)
	- **`expires -1;`**: 브라우저 캐시 만료 시간을 '이미 지남(-1)'으로 설정해 브라우저에 캐시를 남기지 않습니다.
	- **`add_header Cache-Control "no-store, no-cache, must-revalidate";`**: 브라우저/중계 서버가 이 응답을 절대 저장하지 못하도록 강제합니다.
	- **`add_header Pragma "no-cache";`**: 구형 HTTP/1.0 브라우저를 위한 호환용 캐시 방지 헤더입니다.
- **`location /api { ... }`**: `/api`로 시작하는 URL 요청을 백엔드로 중계해 주는 블록입니다.
	- **`resolver 127.0.0.11 valid=10s;`**: 도커 자체 내장 DNS 서버(`127.0.0.11`)를 사용해, 10초마다 도메인 주소의 IP를 갱신합니다.
	- **`set $backend "spring-backend:8080";`**: 백엔드 컨테이너의 이름을 변수로 지정하여, 컨테이너가 재시작되어도 Nginx가 오류로 죽지 않게 돕습니다.
	- **`proxy_pass http://$backend;`**: 해당 요청을 `$backend` 주소로 그대로 전달(프록시)합니다.
	- **`proxy_http_version 1.1;`**: 프록시 통신 간 HTTP 1.1 프로토콜을 사용합니다.
	- **`proxy_set_header Host $host;`**: 클라이언트가 요청 시 사용한 원본 `Host` 헤더 값을 백엔드에 보존해서 전달합니다.
### **3. 터미널 명령어 옵션**
- **`docker buildx build --tag vue-frontend:1.0 .`**
	- `buildx build`: 도커의 고급 빌드 엔진인 BuildKit을 사용해 이미지를 빌드합니다.
	- `-tag` (또는 `t`): 생성할 이미지의 이름과 버전을 지정합니다. (`이미지명:태그명`)
	- `.`: Dockerfile이 위치한 현재 작업 경로를 지정합니다.
- **`docker run -d --name vue-frontend -p 8080:80 vue-frontend:1.0`**
	- `d` (`-detach`): 컨테이너를 백그라운드(비동기)에서 계속 실행시킵니다.
	- `-name`: 컨테이너에 고유한 이름을 부여합니다.
	- `p 8080:80` (`-publish`): `호스트포트:컨테이너포트` 형태로 연결합니다. 내 컴퓨터의 `8080` 포트로 접속하면 컨테이너 내부의 `80` 포트로 넘겨줍니다.
- **`docker stop vue-frontend`**
	- 실행 중인 컨테이너에 `SIGTERM` 신호를 보내 안전하게 정지시킵니다.
- **`docker rm vue-frontend`**
	- 정지 상태인 컨테이너를 도커 목록에서 완전히 삭제합니다.

### ARG 명령어
```plain text
ARG <name>[=<default value>]
```
`docker build` 명령어를 실행할 때 `--build-arg <varname>=<value>` 플래그로 외부에서 값을 주입할 수 있는 **빌드 시점 변수**를 정의함.
- ARG로 설정된 변수는 이미지가 빌드되는 동안에만 유효하며, 컨테이너 런타임에는 유지되지 않음 (런타임 변수는 `ENV` 사용)
- `FROM` 이전에 선언된 `ARG`는 스테이지 내부에서 사용하려면 스테이지 안에서 한 번 더 선언해야 함 (Multi-Stage 스코프 규칙)
#### 활용 예시
```docker
# A. 기본값 설정 및 활용
FROM alpine:latest
ARG USER_NAME=developer
RUN echo "안녕하세요, ${USER_NAME}님!"

# B. FROM 이전에 선언하여 이미지 버전 동적 제어
ARG TAG=18-alpine
FROM node:${TAG}
ARG TAG          # 스테이지 내에서 재사용하려면 재선언 필요
RUN echo "현재 빌드에 사용된 Node 버전 태그: ${TAG}"
```
#### \[실습\] ARG로 ubuntu 버전 동적 주입
```docker
ARG UBUNTU_VERSION=22.04

FROM ubuntu:${UBUNTU_VERSION}
RUN apt-get update && apt-get install -y curl lsb-release
# FROM 절 이후에서 위에서 선언한 ARG UBUNTU_VERSION=22.04를 사용하기 위해 다시 선언 필요
ARG UBUNTU_VERSION
RUN echo "현재 빌드에 사용된 ubuntu version: ${UBUNTU_VERSION}"
```
```bash
# 빌드 시 버전 오버라이드
> docker buildx build --tag linux-container:1.0 --build-arg UBUNTU_VERSION=24.04 .
> docker run -it --name linux-container linux-container:1.0 /bin/bash
# lsb_release -a
# → Ubuntu 24.04.4 LTS 확인
```

### CMD 명령어
```plain text
CMD ["executable", "param1", "param2"]
CMD executable param1 param2
```
컨테이너가 시작될 때(`docker run`) 실행할 기본 명령어와 인자를 지정하는 명령어임.
- Dockerfile 안에 CMD가 여러 개인 경우 가장 마지막 CMD 하나만 유효함
- `docker run <이미지> <새로운_명령어>` 형식으로 실행하면 Dockerfile의 CMD는 완전히 무시되고 사용자가 입력한 명령어가 대신 실행됨 (오버라이딩 가능)
	- docker run -it \<이미지이름\> /bin/bash 같은 경우를 말하는 것임
```docker
FROM nginx:alpine
# 컨테이너가 켜질 때 nginx가 포어그라운드로 실행되도록 설정
CMD ["nginx", "-g", "daemon off;"]
```
nginx를 컨테이너로 실행할 때 `daemon off;` 옵션이 필요한 이유는, 컨테이너는 포어그라운드 프로세스가 종료되면 함께 종료되기 때문임. nginx를 데몬(백그라운드)으로 실행하면 메인 프로세스가 사라져 컨테이너가 즉시 종료됨.
→ 포어그라운드로 켜야지 사용자에게 입력을 받을 수 있는 상태로 컨테이너가 뜸

### COPY 명령어
```plain text
COPY [--chown=<user>:<group>] <src>... <dest>
```
로컬 컴퓨터에 있는 파일이나 디렉토리를 컨테이너 내부 파일시스템으로 복사함.
- `<src>`는 `docker build`를 실행하는 디렉토리 기준의 상대 경로임. `../` 등으로 상위 디렉토리 파일은 가져올 수 없음
- `-from` 플래그를 지원하여 Multi-Stage Build에서 이전 스테이지 산출물을 다음 스테이지로 복사할 때 사용하는 핵심 명령어임
```docker
FROM node:18-alpine
WORKDIR /app

# 1. 특정 소유자 권한으로 package.json 복사
COPY --chown=node:node package.json .

# 2. 멀티 스테이지 환경에서 builder 스테이지의 dist 폴더 복사
COPY --from=builder /app/dist ./dist
```

### WORKDIR 명령어
```plain text
WORKDIR <container 내 작업 디렉토리>
```
이후에 나오는 `RUN`, `CMD`, `ENTRYPOINT`, `COPY`, `ADD` 명령어들이 실행될 컨테이너 내부의 기본 작업 경로를 설정함.
- 지정한 경로가 이미지 내부에 존재하지 않더라도 빌드 과정에서 자동으로 폴더를 생성함
- `ENV`로 정의한 환경변수를 경로에 사용할 수 있음
```docker
# 절대 경로 지정 (폴더 자동 생성)
WORKDIR /usr/src/app
COPY . .

# ENV + 상대경로 조합
ENV APP_ROOT=/var/www
WORKDIR $APP_ROOT       # /var/www 로 이동 (자동 생성)
WORKDIR html            # 상대 경로 → /var/www/html 로 이동
RUN pwd                 # /var/www/html 출력
```

### USER 명령어
```plain text
USER <user>[:<group>]
USER <uid>[:<gid>]
```
이 명령어 이후에 배치되는 `RUN`, `CMD`, `ENTRYPOINT` 등이 실행될 컨테이너 내부의 계정 권한을 변경함.
- 도커 컨테이너는 기본적으로 root 권한으로 실행되므로 보안에 취약함. 실무에서는 권한이 제한된 일반 사용자 계정으로 전환하기 위해 USER를 필수로 사용함 (최소 권한 원칙, Least Privilege)
- USER 명령어가 계정을 자동으로 생성하지는 않음. 반드시 `RUN useradd` 또는 `RUN adduser` 등으로 계정을 먼저 만들어야 함
```docker
FROM alpine:latest
WORKDIR /app

# 1. 컨테이너 내부에서 사용할 일반 유저 계정 생성
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# 2. 소스 복사 시 소유권을 appuser로 설정
COPY --chown=appuser:appgroup . .

# 3. root에서 일반 유저로 전환 (보안 조치)
USER appuser

# 이후 실행되는 프로세스는 appuser의 제한된 권한으로 동작
CMD ["node", "server.js"]
```

### ENV 명령어
```plain text
ENV <key>=<value>
ENV <key1>=<value1> <key2>=<value2> ...
```
컨테이너 내부 시스템 전체에서 참조할 환경변수를 정의함.
- ARG와 달리, ENV로 선언된 변수는 최종 완성된 이미지가 컨테이너로 실행되는 런타임 시점(`docker run`)까지 영구적으로 유지됨
	- ARG는 이미지를 빌드할 때(`docker build`)만 사용 가능함
- `docker run --env <key>=<value>` 플래그로 런타임에 덮어쓸 수 있어 유연한 설정 관리가 가능함
| 구분 | ARG | ENV |
| --- | --- | --- |
| 유효 시점 | 빌드 시점만 | 빌드 + 런타임 |
| 오버라이드 | `--build-arg` | `--env` |
| 주요 용도 | 베이스 이미지 버전, 빌드 옵션 | DB URL, 포트, 앱 설정 등 |

### ENV 명령어 활용 예시
Spring Boot 애플리케이션 이미지 빌드 시 ENV로 환경변수를 설정하고 다른 지시어에서 즉시 참조하는 패턴임.
```docker
FROM openjdk:17-slim

# 1. 런타임 및 빌드 시점에 모두 유지될 환경변수 정의
ENV APP_HOME=/opt/myapp \
    SPRING_PROFILES_ACTIVE=prod \
    JAVA_OPTS="-Xms512m -Xmx1024m"

# 2. ENV 변수를 다른 도커 지시어에서 즉시 참조
WORKDIR $APP_HOME

COPY target/*.jar app.jar

# 3. 자바 실행 시 환경변수($JAVA_OPTS)를 바인딩하여 기동
CMD ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
```
`JAVA_OPTS`처럼 런타임에서 `docker run --env JAVA_OPTS="-Xmx2048m"` 형태로 덮어쓸 수 있어, 같은 이미지를 환경(dev/staging/prod)별로 유연하게 운영할 수 있음.

### \[실습\] USER 명령어: Dockerfile.user 실습
기존 Dockerfile을 복사해 USER를 추가하는 실습임.
```bash
> cp Dockerfile Dockerfile.user
```
```docker
# Dockerfile.user (주요 추가 내용)
ARG UBUNTU_VERSION=22.04
FROM ubuntu:${UBUNTU_VERSION}
...
EXPOSE 8080/tcp
EXPOSE 80/tcp

WORKDIR /var/www/html
COPY index.html .

# skala 그룹 및 사용자 추가
RUN groupadd skala && \
    useradd --create-home --shell /bin/bash --gid skala skala

# nginx가 런타임에 쓰는 디렉토리 소유권을 skala로 변경
RUN chown -R skala:skala /var/lib/nginx /var/log/nginx /run

# skala 사용자로 전환
USER skala
```
빌드 및 실행 시 Permission denied 에러가 발생할 수 있음. nginx는 기본적으로 80번(privileged) 포트를 사용하는데, 일반 사용자는 1024 이하 포트를 바인딩할 수 없기 때문임. 이 경우 `USER skala`를 주석 처리(`# USER skala`)하여 root로 되돌리거나, 아래와 같이 nginx 포트를 8080으로 변경하는 추가 설정이 필요함.
```bash
> docker build --tag linux-container:1.0-USER -f Dockerfile.user .
> docker run -it --name linux-container -p 8888:80 linux-container:1.0
```

### \[참고\] USER skala로 에러 없이 실행하는 방법
nginx가 일반 사용자로 동작하려면 포트 변경과 디렉토리 권한 설정이 함께 필요함.
```docker
...
EXPOSE 8080/tcp
EXPOSE 80/tcp

WORKDIR /var/www/html
COPY index.html .

# skala 그룹 및 사용자 추가
RUN groupadd skala && \
    useradd --create-home --shell /bin/bash --gid skala skala

# nginx가 런타임에 쓰는 디렉토리 소유권 변경
RUN chown -R skala:skala /var/lib/nginx /var/log/nginx /run

# skala는 80번(privileged) 포트 바인딩 불가 → 기본 사이트 설정을 8080으로 변경
RUN sed -i \
    -e 's/listen 80 default_server;/listen 8080 default_server;/' \
    -e 's/listen\[::\]:80 default_server;/listen [::]:8080 default_server;/' \
    /etc/nginx/sites-enabled/default

USER skala
```
일반 사용자로 nginx를 실행할 때는 포트 번호뿐 아니라 프로세스가 접근하는 모든 디렉토리의 소유권까지 함께 설정해야 한다는 점이 핵심임.

### ENTRYPOINT 명령어
```plain text
ENTRYPOINT ["executable", "param1", "param2"]
ENTRYPOINT executable param1 param2
```
컨테이너가 시작될 때 무조건 실행되어야 하는 메인 프로세스를 설정함. 컨테이너가 어떤 역할을 하는 도구인지 본질을 정의하는 명령어임.
→ ENTRYPOINT 가 작성되어 있으면, CMD에 대한 명령을 모두 무시하고 덮어씌움
→ 특정 이미지에 대해서는 이 ENTRYPOINT를 실행하는 것을 강제하고 싶어서 이렇게 사용함
- `docker run` 뒤에 사용자가 입력한 값은 CMD를 대체하지 않고 ENTRYPOINT 뒤에 인자로 추가됨
- 강제로 바꾸려면 `-entrypoint` 플래그를 명시해야만 가능함
#### ENTRYPOINT와 CMD의 조합 패턴
ENTRYPOINT와 CMD를 함께 사용하면 "고정된 메인 명령 + 교체 가능한 기본 인자" 구조를 만들 수 있음.
```docker
FROM alpine:latest

# 실행할 메인 프로그램 고정
ENTRYPOINT ["ping"]

# 사용자가 아무것도 입력하지 않았을 때 적용될 기본 인자값
CMD ["-c", "3", "skala-fileserver.skala-ai.com"]

# 최종적으로 "ping -c 3 skala-fileserver.skala-ai.com" 의 명령어가 실행됨
```
```bash
# CMD에 적어둔 기본값이 그대로 붙어서 작동: ping -c 3 skala-fileserver.skala-ai.com
> docker run --rm check-ping

# 사용자가 입력한 google.com이 CMD를 밀어내고 ENTRYPOINT 뒤에 붙어서 실행
# 최종 실행: ping google.com
> docker run --rm check-ping google.com
```
빌드:
```bash
> docker build --tag check-ping -f Dockerfile.entrypoint .
```

### ENTRYPOINT vs CMD 비교
| 구분 | ENTRYPOINT | CMD |
| --- | --- | --- |
| 개념적 의미 | 컨테이너가 실행할 메인 명령(본질) | 컨테이너가 실행할 기본 인자(기본값) |
| docker run 뒤 인자 입력 | 입력한 값이 ENTRYPOINT 뒤에 매개변수로 추가됨 | Dockerfile의 CMD 내용은 완전히 무시되고 대체됨 |
| 강제 오버라이딩 방법 | `--entrypoint` 플래그를 명시해야만 가능 | 플래그 없이 이미지 이름 뒤에 명령어 입력 시 자동 대체 |
| 가장 흔한 실무 형태 | `ENTRYPOINT ["nginx"]`, `ENTRYPOINT ["python"]` | `CMD ["--help"]`, `CMD ["app.py"]` |

### \[검토\] ENTRYPOINT + CMD 조합 출력 결과 예측
```docker
FROM python:3.10-alpine
ENTRYPOINT ["echo", "This"]
CMD ["is", "the default command"]
```
```bash
# 실행 1: CMD 기본값 그대로 사용
> docker run --rm test-image
# → This is the default command

# 실행 2: 사용자 입력이 CMD를 대체(" is the custom CMD " 가 CMD의 자리를 대체함)
> docker run --rm test-image " is the custom CMD "
# → This  is the custom CMD
```
ENTRYPOINT인 `echo This`는 항상 고정이고, CMD는 사용자 입력으로 교체되는 구조임.

### 파일/레이어 vs 컨테이너 실행 설정 정보 요약
Dockerfile 명령어는 역할에 따라 두 종류로 나뉨.
이미지 레이어를 생성하는 명령어 (읽기 전용 레이어 / RootFS.Layers):
| 명령 | 설명 |
| --- | --- |
| `RUN` | 패키지 설치, 소스코드 빌드, 스크립트 실행 등 명령어 실행 결과로 생성·변경된 파일들을 새 레이어로 저장 |
| `COPY` | 호스트 머신(빌드 컨텍스트)의 파일이나 디렉토리를 이미지 내부로 복사하여 새 레이어 생성 |
| `ADD` | COPY와 유사하지만 압축 파일(tar) 자동 해제 및 원격 URL 파일 다운로드를 추가로 수행 |
컨테이너 실행 설정 명령어 (container config.json에 저장):
`ENTRYPOINT`, `CMD`, `ENV`, `WORKDIR`, `EXPOSE`, `USER`, `VOLUME`, `LABEL` 등이 해당하며, 이미지에 레이어를 추가하지 않고 컨테이너 실행 환경을 구성하는 메타정보를 설정함.

### 컨테이너에 Persistent Volume 연결하기
컨테이너는 언제든 삭제될 수 있는 일회성(Ephemeral) 환경임. 컨테이너가 종료·삭제된 후 재실행되더라도 데이터를 보존하려면 외부 볼륨을 컨테이너 내부 경로에 마운트해야 함.

Dockerfile의 COPY 명령어로 이미지 레이어에 복사된 파일(`/app`, `/temp`, `main.py` 등)은 컨테이너 삭제 시 함께 사라짐. 이를 보완하기 위해 호스트 머신의 외부 볼륨(디렉토리)을 컨테이너 내부 경로와 연결하는 방식을 사용함.
---
### 볼륨 타입
Docker 볼륨은 세 가지 방식으로 분류됨.

| 타입 | 설명 | 저장 위치 | 컨테이너 삭제 후 |
| --- | --- | --- | --- |
| Named Volume | Docker가 관리하는 이름 있는 볼륨 | `/var/lib/docker/volumes/<name>` | 유지됨 |
| Bind Mount | 호스트의 임의 경로를 컨테이너 경로에 직접 연결 | 사용자가 지정한 호스트 경로 | 지정 경로에 유지됨 |
| Anonymous Volume | 이름 없이 임시 생성 (Dockerfile의 `VOLUME` 명령어) | Docker가 자동 생성한 랜덤 해시 경로 | `docker volume prune`으로 정리됨 |
---
### 볼륨 타입 : Named Volume
Docker가 `/var/lib/docker/volumes/` 하위에 볼륨을 직접 생성·관리하는 방식임. `-v <볼륨명>:<컨테이너 경로>` 형식으로 지정함.
```bash
docker run -it --name busybox -v demo:/usr/share busybox
```
컨테이너 내부에서 마운트 상태를 확인하면 `/dev/vda1`이 `/usr/share`에 마운트된 것을 볼 수 있음.
```bash
/ # mount | grep /usr/share
/dev/vda1 on /usr/share type ext4 (rw,relatime,discard)
```
`docker inspect`로 마운트 정보를 JSON으로 확인할 수 있음.
```bash
docker inspect busybox --format '{{json .Mounts}}' | jq
```
주요 필드:
- `Type`: `volume` (Named Volume임을 나타냄)
- `Source`: `/var/lib/docker/volumes/demo/_data` (호스트 실제 경로)
- `Destination`: `/usr/share` (컨테이너 내부 경로)
- `Driver`: `local` (기본값; nfs, aws efs 같은 외부 드라이버도 지정 가능)
---
### 볼륨 타입 : Bind Mount
호스트의 특정 디렉토리를 컨테이너 내부 경로에 직접 마운트하는 방식임. 경로를 사용자가 직접 제어함.
```bash
docker run -it --name busybox -v $(pwd):/usr/share busybox
```
macOS 기준으로 컨테이너 내부에서 마운트를 확인하면 `/run/host_mark/Users` 경로가 `/usr/share`에 연결된 것을 볼 수 있음. 컨테이너 내부에서 파일을 생성하면 호스트의 연결된 경로에도 그대로 반영됨.
```bash
/ # touch /usr/share/bind-mount.txt
/ # exit
> ls bind-mount.txt   # 호스트에서도 확인 가능
```
`docker inspect` 결과에서 `Type`이 `bind`이고, `Source`는 호스트의 실제 절대 경로로 표시됨. Named Volume과 달리 `Propagation`이 `rprivate`로 설정됨.

### \[실습\] MariaDB에 Bind Mount로 볼륨 연결
MariaDB 컨테이너 실행 시 `-v $(pwd)/db-data:/var/lib/mysql` 옵션으로 DB 데이터 디렉토리를 호스트 로컬에 마운트함. 컨테이너를 삭제해도 `db-data` 디렉토리 안에 MariaDB 데이터 파일이 남아 데이터가 보존됨.
```bash
docker run -d \
  --name mariadb \
  -e MYSQL_ROOT_PASSWORD=password \
  -e MYSQL_DATABASE=skala \
  -e MYSQL_USER=user \
  -e MYSQL_PASSWORD=password \
  --network skala \
  -p 3306:3306 \
  -v $(pwd)/db-data:/var/lib/mysql \
  mariadb:latest
```
컨테이너 실행 후 `ls ./db-data`를 확인하면 MariaDB가 생성한 데이터 파일들(`ibdata1`, `mysql`, `skala` DB 디렉토리 등)이 호스트에 직접 나타남을 볼 수 있음.

### Python 실행 컨테이너 만들기
기존에 빌드한 `linux-container:1.0` 이미지를 사용해 Bind Mount로 `mydata` 디렉토리를 공유하는 컨테이너를 실행함.
```bash
mkdir -p ./mydata

docker run -d \
  --name linux-container \
  -p 8080:8080 \
  -p 8888:80 \
  -v $(pwd)/mydata:/mydata \
  linux-container:1.0
```
실행 후 터미널 두 개를 나눠 작업함.
- 터미널 1 (컨테이너 내부): `docker exec -it linux-container /bin/bash`로 접속 후 `/mydata` 디렉토리를 확인하면 처음엔 비어 있음
- 터미널 2 (호스트): `cp webserver.py ./mydata`로 파일을 복사하면, Bind Mount를 통해 컨테이너 내부에서도 즉시 동일 파일이 보임

### Python 실행 컨테이너 만들기 — webserver.py 실행
컨테이너 내부에서 python3를 설치한 뒤 마운트된 경로의 스크립트를 실행함.
```bash
apt-get update
apt-get install -y python3 python3-pip

cd /mydata
python3 /mydata/webserver.py
# Starting server on port 8080...
# Access the server at http://localhost:8080/login
```
호스트에서 `http://localhost:8080`으로 브라우저 접속이 가능해짐. 이 과정은 이후 Dockerfile로 자동화함.

### \[실습\] 파이썬 웹서버용 Dockerfile 만들기
앞서 수동으로 구성했던 환경(python3 설치 → `webserver.py` 복사 → 실행)을 Dockerfile에 명령어로 작성해 이미지 빌드 시 자동으로 처리되도록 함.
```docker
# 기존 nginx 관련 라인은 주석 처리
# WORKDIR /var/www/html
# COPY index.html .

RUN apt-get install -y python3 python3-pip

WORKDIR /app
COPY webserver.py .

# CMD ["nginx", "-g", "daemon off;"]
CMD ["python3", "webserver.py"]
```
빌드 후 컨테이너를 실행하면 `http://localhost:8080`으로 브라우저 접속이 가능함.
```bash
docker build --tag linux-container:1.0 .
docker run -d --name linux-container -p 8080:8080 linux-container:1.0
```
