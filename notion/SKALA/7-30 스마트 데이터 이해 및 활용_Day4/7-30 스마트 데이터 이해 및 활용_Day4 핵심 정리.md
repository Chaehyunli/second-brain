## 함수와 Stored Procedure

### 역할의 차이

| 구분 | Stored Procedure | 함수(Function/UDF) |
| --- | --- | --- |
| 중심 역할 | 여러 SQL 문을 묶어 수행하는 작업 절차 | 계산 결과를 반환하는 연산 도구 |
| 반환 | 있을 수도, 없을 수도 있음 | 결과값을 반환 |
| 호출 | `CALL` 또는 `EXEC` | 보통 `SELECT fn_함수()` |
| 주 사용처 | 데이터 변경, 트랜잭션, 배치 | 조회 안의 계산·변환 |
| 트랜잭션/DML | 제어·변경 작업 가능 | 원문 기준 읽기·계산 중심으로 사용 |

핵심 판단은 “하나의 값을 계산해 돌려줄 것인가, 여러 SQL을 묶어 업무 단위를 처리할 것인가”이다. 함수가 `SELECT` 안에서 행마다 호출될 수 있으므로, 데이터 변경을 섞으면 조회 중 데이터 일관성이 깨질 수 있다는 점을 원문은 주의점으로 든다.

### DBMS별 함수 선언의 의도

`fn_vat(amount)`처럼 같은 입력에서 부가세를 계산하는 함수라도 DBMS마다 결과 안정성을 선언하는 방식이 다르다.

```sql
-- MySQL / MariaDB: 같은 입력에 같은 결과라는 선언
CREATE FUNCTION fn_vat(amount DECIMAL(10,2))
RETURNS DECIMAL(10,2) DETERMINISTIC
BEGIN RETURN amount * 0.1; END;

SELECT order_id, fn_vat(total_amount) AS vat FROM orders;
```

```sql
-- PostgreSQL: 입력만으로 결과가 정해지는 함수
CREATE OR REPLACE FUNCTION fn_vat(amount NUMERIC)
RETURNS NUMERIC LANGUAGE sql IMMUTABLE
AS $$ SELECT amount * 0.1 $$;

CREATE INDEX idx_tax ON orders ((fn_vat(total_amount)));
```

- PostgreSQL `IMMUTABLE`: 입력만으로 결과가 확정되며 함수 기반 인덱스나 상수 폴딩에 활용할 수 있다.
- `STABLE`: 같은 트랜잭션 안에서는 결과가 고정될 수 있으나 설정·현재 정보 등을 참조할 수 있다.
- `VOLATILE`: 호출마다 결과가 달라질 수 있는 기본 성격이다.
- SQL Server는 성능이 중요한 경우 스칼라 함수보다 인라인 테이블 함수(iTVF)를 우선 검토한다. 옵티마이저가 본문을 쿼리와 함께 최적화할 수 있기 때문이다.
- Oracle `RESULT_CACHE`는 동일 입력의 계산 결과를 재사용하는 선택지다.

선언을 실제 성질과 다르게 강하게 하면 결과 불일치가 생길 수 있으므로, `IMMUTABLE`·`DETERMINISTIC`은 단순한 성능 힌트가 아니라 함수 계약으로 다뤄야 한다.

### 프로시저와 권한 컨텍스트

`sp_top_customers(p_year)` 예시는 연도별 매출을 집계해 상위 고객을 반환한다. `JOIN → GROUP BY → 정렬 → 상위 N개`라는 논리는 공통이지만, MySQL은 `DELIMITER`, PostgreSQL은 `plpgsql`, SQL Server는 `TOP`·`GO` 등 선언 문법이 다르다.

프로시저·함수에는 내부 SQL을 누구 권한으로 실행할지도 중요하다.

- **DEFINER**: 객체 작성자/소유자 권한으로 실행한다. 호출자에게 테이블 직접 권한을 주지 않고 인터페이스만 제공할 수 있다.
- **INVOKER**: 실제 호출자 권한으로 실행한다.
- `DEFINER`는 잘못 쓰면 권한 상승 경로가 된다. PostgreSQL `SECURITY DEFINER` 함수는 `search_path`를 명시적으로 고정하고, 동적 SQL·입력 검증을 특히 주의해야 한다.
- Oracle PL/SQL에서는 역할(ROLE)이 아니라 직접 `GRANT`된 권한이 필요한 상황이 있다는 점도 원문에서 강조한다.

## 트리거와 트랜잭션 설계

### 트리거의 구성

트리거는 `INSERT`·`UPDATE`·`DELETE` 같은 이벤트에 자동 반응하는 DB 코드다. 사람이 직접 부르는 프로시저와 달리 이벤트가 발생하면 실행된다.

- 타이밍: `BEFORE`(검증·값 보정), `AFTER`(감사·파생값 갱신), `INSTEAD OF`(뷰의 DML 대체)
- 범위: 행 단위(`FOR EACH ROW`)와 문장 단위(statement-level)
- 변경 전후 데이터: PostgreSQL/MySQL/Oracle은 `OLD`·`NEW`, SQL Server는 `deleted`·`inserted`

트리거는 감사 로그, 기본값·유효성 보강, 데이터 무결성 강제에는 적합하다. 반면 외부 API 호출, 오래 걸리는 작업, 순서 의존 트리거 연쇄, 대량 DML의 행 단위 처리에는 부적합하다. 외부 호출 실패가 원래 DML 트랜잭션까지 지연·실패시킬 수 있기 때문이다.

### Row-level과 statement-level

PostgreSQL의 행 단위 감사 트리거는 `NEW`를 `to_jsonb()`로 변환해 각 행의 변경을 기록할 수 있다. 대량 삽입에는 `REFERENCING NEW TABLE AS new_table`와 `FOR EACH STATEMENT`를 이용해, 한 번의 호출에서 변경 행 집합을 처리하는 방식이 유리하다.

| 구분 | Row-level | Statement-level + transition table |
| --- | --- | --- |
| 호출 횟수 | 영향 행마다 | DML 문장당 1회 |
| 접근 대상 | `NEW` / `OLD` | `new_table` / `old_table` |
| 적합한 경우 | 행별 서로 다른 로직 | 대량 DML·일괄 감사 |
| 반환 | 보통 `NEW` 또는 `OLD` | 보통 `NULL` |

DBMS별 차이도 설계에 영향을 준다. MySQL은 행 단위 중심이고 같은 테이블을 재수정하면 제약이 있다. SQL Server는 `inserted`/`deleted` 집합을 전제로 작성해야 다중 행 작업에서 정확하다. Oracle은 row trigger에서 발생하는 mutating table 제약을 compound trigger로 우회할 수 있다.

### 이벤트를 트랜잭션 밖으로 분리하기

원문은 트리거에서 외부 API를 직접 호출하지 않고, 트리거는 로그 테이블·outbox·메시지 채널에 이벤트를 기록하는 데 그치며 비동기 소비자가 후속 처리를 맡는 구조를 권장한다.

- PostgreSQL: `LISTEN` / `NOTIFY`, `pg_notify()`
- CDC: MySQL binlog, PostgreSQL WAL logical decoding 등을 Debezium 같은 소비자와 연결
- Outbox: DML과 이벤트 기록을 같은 트랜잭션에 넣고, 워커가 이후 발행
- 배치: MySQL Event Scheduler, `pg_cron` 또는 OS cron, SQL Server Agent, Oracle `DBMS_SCHEDULER`

Outbox 소비자는 같은 이벤트를 여러 번 받아도 결과가 바뀌지 않도록 멱등성 키를 가져야 한다.

## DB 운영·분석 아키텍처

### 배포 모델과 선택 기준

| 모델 | 특징 | 주요 트레이드오프 |
| --- | --- | --- |
| On-Prem | 서버·스토리지·운영을 조직이 직접 통제 | 자유도는 높고 운영 책임·초기 투자도 큼 |
| DBaaS | RDS·Cloud SQL처럼 관리형 기존 DBMS 제공 | 인프라 운영은 줄지만 스키마·쿼리·보안은 여전히 사용자 책임 |
| Cloud-Native DB | Aurora·Spanner처럼 클라우드용 구조 | 자동화·분산성이 높고 공급자 종속·제약도 고려 |

DBaaS도 인덱스·스키마·파라미터·권한·비용 SLO·메이저 업그레이드 호환성 검증을 대신하지 않는다. 선택은 규제·데이터 주권, 팀 운영 역량, 트래픽 변동과 다지역 일관성, 그리고 인스턴스 비용뿐 아니라 egress·IOPS·백업까지 포함한 TCO를 기준으로 한다.

### OLTP와 OLAP

| 구분 | OLTP | OLAP |
| --- | --- | --- |
| 목적 | 주문·결제·재고 같은 실시간 거래 | 대량 집계·리포팅·분석 |
| 워크로드 | 짧은 읽기/쓰기, 낮은 지연 | 넓은 스캔·집계, 높은 처리량 |
| 설계 | 정규화·트랜잭션·포인트 조회 | 스타/스노우플레이크·컬럼 저장·파티션 |
| 최적화 | 인덱스·조인·트랜잭션 | 파티션/컬럼 프루닝·벡터화 |

분석 DB 성능은 필요한 파티션만 읽는 **partition pruning**, 필요한 열만 읽는 **column pruning**, 묶음 단위 CPU 처리를 하는 **vectorized execution**을 연결해 이해할 수 있다. BigQuery·Snowflake·DuckDB·ClickHouse 등의 비용·성능 판단에서도 `SELECT *`를 피하고 필요한 열과 범위를 명시하는 습관이 중요하다.

### 분산·특수 목적 DB

- **NewSQL**: CockroachDB·TiDB처럼 SQL/트랜잭션과 수평 확장을 함께 지향한다. 강한 일관성·분산 합의의 지연과 운영 복잡도도 함께 평가한다.
- **시계열 DB**: TimescaleDB는 PostgreSQL 생태계 위에 hypertable·연속 집계·보존 정책을 더한다. InfluxDB는 고속 수집·보존에 특화된다.
- **벡터 DB/RAG**: `pgvector`, Pinecone, Weaviate는 임베딩 유사도 검색을 제공한다. 벡터 검색은 의미 유사성에, 키워드 검색은 정확한 고유어에 강점이 있어 하이브리드 검색을 사용한다.
- **MSA 데이터 패턴**: Database per Service, Saga, CQRS, Outbox, Event Sourcing은 서비스 경계·일관성·재처리 비용을 함께 설계해야 한다.

## DB 보안·복구·관측

### 보안의 다층 구조

원문은 인증, 인가, 입력 검증/파라미터 바인딩, 전송·저장 암호화, 감사 로그를 서로 보완하는 다섯 층으로 정리한다. 최소 권한 원칙에 따라 역할에 권한을 묶고 사용자에게 역할을 부여한다.

- SQL은 문자열 결합이 아니라 prepared statement/파라미터 바인딩을 사용한다.
- 컬럼명·정렬 방향처럼 바인딩할 수 없는 부분은 화이트리스트로 제한한다.
- PostgreSQL RLS는 같은 테이블에서도 테넌트·사용자별 행 접근을 제한한다.
- TLS, 저장 암호화/TDE, 민감 컬럼 암호화는 서로 다른 위협을 다룬다.
- VIEW는 테이블 전체를 직접 노출하지 않고 필요한 행·열만 제공하는 안전한 경계가 될 수 있다.

### 백업·HA·모니터링

백업은 full, incremental, differential, PITR, 논리/물리 백업처럼 복구 목표와 운영 비용이 서로 다르다. PostgreSQL PITR은 base backup과 WAL archive를 조합하며, streaming replication은 동기식(RPO를 낮춤)과 비동기식(지연·성능 균형) 선택지가 있다.

관측에서는 TPS/QPS/latency, CPU, 연결 수, 복제 지연, 남은 스토리지를 기본으로 보고, `EXPLAIN`·슬로우 쿼리·CloudWatch/Cloud Monitoring 등의 근거로 원인을 좁힌다. 알람 임계값은 평균만이 아니라 지속 시간과 사용자 영향, RPO/RTO 목표와 연결해 정한다.
