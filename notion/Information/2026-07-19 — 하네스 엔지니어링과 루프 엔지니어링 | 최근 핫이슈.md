## 2. 먼저 용어를 분리하기
### 하네스 엔지니어링
하네스는 모델 자체를 제외한 실행 시스템 전체다. 즉 프롬프트, 프로젝트 지식, 도구, 권한, 샌드박스, 메모리, 훅, 서브에이전트, 검증, 실패 복구를 묶어 모델을 실제 에이전트로 만드는 층이다.
[Addy Osmani의 설명](https://addyosmani.com/blog/agent-harness-engineering/)은 이를 “모델이 아닌 코드·설정·실행 로직 전체”로 정의한다. 핵심 습관은 **에이전트의 실제 실패를 규칙·테스트·도구 제약으로 영구 반영**하는 것이다.
```plain text
코딩 에이전트 = 모델 + 하네스
하네스 = context + tools + permissions + state + verifier + recovery
```
예시:
```plain text
실패: 에이전트가 테스트를 주석 처리한 채 PR을 완료함
→ 하네스 보완:
  1) AGENTS.md에 테스트 삭제/주석 금지 규칙 추가
  2) pre-commit hook이 주석 처리된 test를 차단
  3) reviewer 서브에이전트가 diff에서 해당 패턴 검사
  4) typecheck·test 실패를 에이전트 루프에 되돌려 재수정
```
### 루프 엔지니어링
루프 엔지니어링은 사람이 매번 다음 프롬프트를 직접 쓰는 대신, 목적·완료 조건·상태를 주고 시스템이 다음 작업을 반복 선택하도록 만드는 일이다. [Addy Osmani의 설명](https://addyosmani.com/blog/loop-engineering/)처럼 “사람이 프롬프트하는 역할을, 프롬프트를 만드는 시스템으로 대체”하는 접근이다.
대표 구성은 다음과 같다.
1. 스케줄 기반 발견·분류(automation)
2. 격리된 병렬 작업(worktree/sandbox)
3. 프로젝트 지식·절차(skills)
4. 외부 도구 연결(MCP·plugin)
5. 실행·검증 역할 분리(sub-agent)
6. 대화 밖의 상태 저장(Markdown·이슈·보드)
```plain text
while backlog has eligible work:
  task = discover_and_prioritize()
  result = executor_agent(task, isolated_worktree)
  verdict = independent_verifier(result)
  persist_state(task, result, verdict)
  if verdict == pass: merge_or_queue_review()
  else: feed_specific_failure_back_and_retry_with_limit()
```

## 5. 사람들의 반응에서 반복되는 쟁점
### 긍정: 모델 교체보다 작업 시스템 개선이 더 실무적
실패 유형을 프로젝트 지식, 도구 선택, 검증 훅, 상태 관리에 반영하면 모델의 일회성 성능 편차를 줄일 수 있다는 기대가 크다. 하네스 관련 반응은 모델 스위칭, 브라우저 실행, C/C++ 디버거·sanitizer 연결처럼 구체적 도구 통합으로 나타난다.
### 경계: “자동화 = 무감독”은 아님
루프는 사람을 없애는 장치가 아니라, 사람의 역할을 **목적 설정·승인 경계·검증 규칙·예외 처리**로 옮긴다. Osmani도 “루프는 일을 바꾸지, 당신을 지우지 않는다”고 결론짓는다.
### 비용·폭주
재시도·서브에이전트·긴 컨텍스트가 쌓이면 품질보다 토큰·시간 비용이 먼저 폭주할 수 있다. 따라서 시도 횟수, 예산, wall-clock 시간, 외부 쓰기 권한에 상한이 필요하다.
### 안전·책임 소재
파일 삭제, 배포, 고객 데이터 변경처럼 되돌리기 어려운 행동은 샌드박스·최소권한·승인 게이트·독립 검증을 둬야 한다. “테스트 통과”만으로 보안·요구사항 적합성까지 보장되지 않는다.
## 6. 실무 도입 순서
1. **하네스부터:** 단일 반복 작업 하나에 read-only 도구, 명시적 완료 조건, lint/test 검증, 실패 로그를 붙인다.
2. **실패를 규칙화:** 실제 실패가 생길 때만 skill·hook·check를 추가한다. 처음부터 거대한 프롬프트·규칙 묶음을 만들지 않는다.
3. **루프는 좁게:** 새 이슈 분류, 문서 정합성 점검, 테스트 실패 triage처럼 되돌리기 쉬운 큐부터 스케줄화한다.
4. **상한과 승인:** retry·비용·시간·병렬성 한도와 merge/deploy/삭제의 인간 승인을 분리한다.
5. **측정:** 완료율뿐 아니라 재시도 수, 비용, 사람의 수정량, escaped defect를 함께 기록한다.
## 7. 최종 판단
하네스 엔지니어링은 **에이전트가 잘못될 때 어떻게 더 안전하고 재현 가능하게 만들지**에 대한 엔지니어링이고, 루프 엔지니어링은 **그런 에이전트를 언제·어떤 순서로·어디까지 자율 운영할지**에 대한 운영 설계다. 현재 신호는 “더 큰 모델 하나”보다 컨텍스트·도구·검증·상태·권한을 설계하는 역량이 중요해진다는 쪽이다. 다만 루프는 자율성을 늘리는 만큼 비용·오작동·책임 경계도 함께 키우므로, 사람의 검토를 제거하는 것이 아니라 고위험 지점에 집중시키는 방식이 현실적이다.
