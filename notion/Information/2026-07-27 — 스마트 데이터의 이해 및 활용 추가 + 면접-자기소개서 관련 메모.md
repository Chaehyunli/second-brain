## SQL 조회와 성능

### CTE와 VIEW

- **CTE**는 `WITH`로 정의하고 현재 SQL 문 안에서만 사용하는 이름 있는 결과 집합이다. 복잡한 쿼리의 단계 분리와 재귀 처리에 사용한다.
- **VIEW**는 `CREATE VIEW`로 DB에 저장하는 쿼리 정의다. 일반 VIEW는 결과 데이터를 별도로 저장하지 않고 참조 시 정의 쿼리를 실행한다.
- 성능은 CTE·VIEW 형식만으로 판단하지 않고 실제 데이터에서 `EXPLAIN (ANALYZE)`로 확인한다.

### 인덱스와 조건 처리

- B-Tree는 동등·범위 비교와 정렬에 폭넓게 쓰는 기본 인덱스다. Hash 인덱스는 동등 비교에 적합하며, 복합 인덱스는 컬럼 순서가 중요하다.
- 인덱스는 실제 `WHERE`·`JOIN`·`ORDER BY`·`GROUP BY` 패턴을 기준으로 설계하고, 조회 이득과 데이터 변경·저장 비용을 함께 비교한다.
- `WHERE`는 그룹화 전 개별 행을 줄이고, `HAVING`은 그룹화 뒤 집계 결과를 거른다. 집계와 무관한 조건은 가능한 한 `WHERE`에서 먼저 적용한다.
- `SELECT *` 대신 필요한 컬럼을 명시해 읽기·전송량을 줄이고 조회 계약을 분명히 한다.

### 실행 계획과 이식성

- 실행 계획에서는 Scan 방식, Join·Sort·Aggregate, 추정 행 수와 실제 행 수의 차이, 인덱스 변경 전후를 본다. `Seq Scan`은 작은 테이블 또는 대부분의 행을 읽어야 할 때 합리적일 수 있다.
- `EXPLAIN ANALYZE`는 실제 실행하므로 변경 쿼리는 트랜잭션 안에서 검사한 후 `ROLLBACK`으로 되돌린다.
- PostgreSQL·SQL Server·Oracle·MySQL 사이의 쿼리 이식 시 행 제한, 문자열 결합, 자동 증가, UPSERT 문법뿐 아니라 `NULL`, 시간대, 정렬, 함수 반환값도 테스트한다.

## RFP와 데이터 아키텍처

- RFP는 문제 배경, 목표·성공 기준, 요구사항·범위, 제약, 제안·PoC, 평가·검증을 정리한다. 기술을 먼저 선택하기보다 사용자·업무 흐름·데이터·성공 기준으로 요구사항을 읽는다.
- 제안의 기술·가격 배점은 공고마다 다르므로 특정 비율을 일반화하지 않고 해당 공고의 평가표를 우선 확인한다.
- 논리 아키텍처는 구현 도구보다 데이터가 생성되어 어떤 책임 계층을 거치고 누가 어떤 판단에 쓰는지 설명한다.

```plain text
Source System
  → Data Pipeline(수집·검증·정제·변환·적재)
  → DW Area(공통 기준과 이력 통합)
  → 대시보드·보고서·분석
  → 담당자의 실제 조치와 의사결정
```

통합 포털은 차트를 모은 화면이 아니라, 누가 어느 시점에 어떤 정보를 보고 다음 행동을 할지 연결해야 한다. 의사결정 결과는 다시 원천 시스템에 기록되어 다음 판단을 개선한다.

## 면접·자기소개서·AX 진로 메모

- 자기소개서에서 의사결정 경험을 쓸 때는 `상황 → 비교한 대안 → 선택 기준·근거 → 결정 → 실행·검증 → 회고` 흐름으로 설명할 수 있어야 한다.
- 사용한 기술을 적었다면 어떤 문제에서 어떻게 사용했고 한계는 무엇이었는지 질문을 받을 수 있으므로, 경험의 근거를 준비한다.
- AX 지원 동기는 전공과 무관하게 자신의 도메인 경험을 어떤 업무 문제로 확장할지 설명하는 방식으로 준비한다.
- AX 적용은 AI 기능부터 붙이는 것이 아니라 업무의 반복·지연·오류 장면, 필요한 데이터·문서·규칙, 사람 검토·권한·예외 처리를 먼저 설계하고 처리 시간·오류율·사용률·결과 품질로 검증한다.
- 진로 탐색 단계에서는 전체 논리 아키텍처의 흐름을 넓게 이해한 뒤 관심 분야를 좁히고 깊게 학습하는 방향을 제안한다.
