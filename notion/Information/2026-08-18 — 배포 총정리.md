## 배포란?
쉽게 말하면 **배포**는 내가 만든 웹서비스를 내 PC에서만 실행하는 것이 아니라, **인터넷에 연결된 서버에 올려서 다른 사람도 접속할 수 있게 만드는 것**이다.
예를 들어 내 컴퓨터에서 Spring Boot를 실행하면 보통
```plain text
http://localhost:8080
```
으로 접속한다.
이 상태에서는 기본적으로 내 컴퓨터에서만 사용할 수 있다. `localhost`는 "내 컴퓨터 자신"을 가리키는 주소이기 때문에, 같은 와이파이를 쓰는 옆자리 동료조차 이 주소로는 내 서비스에 들어올 수 없다.
하지만 배포하면
```plain text
https://myservice.com
```
처럼 인터넷을 통해 다른 사람도 접속할 수 있게 된다.
<br>\<배포난이도 비교\>
그런데 배포를 공부하다 보면 **Nginx, Apache, Vercel, Render, Cloudflare, AWS** 같은 이름이 계속 나오는데, 이것들은 모두 같은 종류가 아니다. 어떤 것은 "서버에 직접 설치하는 프로그램"이고, 어떤 것은 "서버 자체를 대신 빌려주고 관리해 주는 플랫폼"이고, 어떤 것은 "사용자와 서버 사이에서 트래픽을 걸러주는 존재"다. 이 차이를 모르고 이름만 외우면 나중에 헷갈리기 쉽다.

## 1. Nginx
Nginx(엔진엑스)는 서버에 설치하는 **웹서버 프로그램**이다.
특히 Spring Boot 같은 백엔드 서버의 앞단에서 많이 사용한다.
예를 들어 Spring Boot가 서버에서 `8080` 포트로 실행되고 있다고 해보자.
```plain text
사용자
  ↓
https://myservice.com
  ↓
Nginx : 443
  ↓
Spring Boot : 8080
```
사용자는 Spring Boot의 `8080` 포트에 직접 접근하는 것이 아니라 Nginx에 요청을 보낸다. 그러면 Nginx가 요청을 Spring Boot로 전달한다.
이것을 \*\*리버스 프록시(Reverse Proxy)\*\*라고 한다.
예를 들면 설정은 이런 식이다.
```plain text
server {
    listen80;

    server_namemyservice.com;

    location / {
        proxy_passhttp://localhost:8080;
    }
}
```
그래서 실무에서 다음과 같은 구조를 많이 볼 수 있다.
```plain text
AWS EC2
 ├ Nginx
 └ Spring Boot
```
Nginx는 단순히 요청 전달만 하는 것이 아니라 여러 역할을 할 수 있다.
```plain text
HTTPS 처리
도메인 연결
리버스 프록시
정적 파일 제공
로드 밸런싱
요청 제한
캐싱
```
이 중에서도 특히 자주 쓰이는 이유를 조금 더 풀어보면, HTTPS 인증서(SSL) 처리를 Nginx가 대신 맡아주면 뒤에 있는 Spring Boot는 암호화를 신경 쓰지 않고 순수하게 로직에만 집중할 수 있다. 또 서버가 여러 대일 때 Nginx가 트래픽을 나눠주는 **로드 밸런싱**을 담당하면, 특정 서버 한 대에 요청이 몰려 죽는 상황을 막을 수 있다.
쉽게 비유하면 Nginx는 **건물 입구의 안내 데스크**와 비슷하다.
```plain text
사용자
  ↓
Nginx
  ↓
어디로 보내야 하지?
  ↓
Spring Boot / FastAPI / Node.js
```

## 2. Apache
Apache(아파치)도 Nginx와 비슷한 **웹서버 프로그램**이다.
Apache는 1995년부터 사용되어 온, 웹서버 중에서도 가장 오래되고 대표적인 웹서버다.
```plain text
사용자
  ↓
Apache
  ↓
웹 애플리케이션
```
특히 PHP 환경에서 많이 사용되었다.
```plain text
Apache
+
PHP
+
MySQL
```
예전 웹서비스에서는 이런 구성을 매우 자주 볼 수 있었다(흔히 **LAMP 스택**이라고 불렸다: Linux + Apache + MySQL + PHP).
Nginx와 Apache를 아주 단순하게 비교하면 다음과 같다.
```plain text
Apache
→ 전통적인 웹서버
→ 기능과 설정이 풍부함
→ 프로세스/스레드 기반으로 요청마다 처리
→ PHP / 레거시 환경에서 많이 사용

Nginx
→ 이벤트 기반으로 동작해 가볍고 동시 접속 처리에 강함
→ 리버스 프록시로 많이 사용
→ Spring Boot / Node.js / FastAPI 앞단에서 많이 사용
```
조금 더 풀어보면, Apache는 요청이 들어올 때마다 프로세스나 스레드를 새로 만들어 처리하는 방식이라 설정이 유연하고 `.htaccess` 같은 파일로 세밀한 제어가 가능하다는 장점이 있지만, 동시 접속자가 아주 많아지면 상대적으로 자원을 더 많이 소모한다. 반면 Nginx는 이벤트 기반(event-driven) 구조라 적은 자원으로도 많은 동시 연결을 처리하는 데 유리해서, 최근의 API 서버 앞단에는 Nginx가 더 많이 채택되는 편이다.
Spring Boot를 배포하면서 둘 중 하나를 접한다면 요즘은 Nginx를 더 자주 볼 가능성이 크다.

## 3. Vercel
Vercel은 Nginx처럼 서버에 직접 설치하는 프로그램이 아니다.
Vercel은 웹 애플리케이션 배포를 쉽게 해주는 **플랫폼**이다.
특히 **Next.js**와 궁합이 매우 좋다(Vercel은 Next.js를 만든 회사이기도 하다).
예를 들어 GitHub에 Next.js 프로젝트를 올려놓았다고 해보자.
```plain text
내 코드
  ↓
GitHub
  ↓
Vercel
  ↓
자동 Build
  ↓
자동 Deploy
  ↓
https://내사이트.vercel.app
```
GitHub와 연결하면 코드가 변경될 때 자동으로 다시 배포하는 것도 가능하다.
직접 서버를 구성한다면 보통 이런 작업을 해야 한다.
```plain text
Linux 서버 준비
Node.js 설치
웹서버 설정
HTTPS 설정
도메인 설정
배포 스크립트 작성
```
하지만 Vercel은 이런 부분을 상당 부분 대신해준다.
그래서
```plain text
Next.js
React
Vue
정적 웹사이트
```
같은 프론트엔드 서비스를 배포할 때 매우 편하다. 특히
```plain text
Next.js
  ↓
Vercel
```
조합은 매우 흔하다.
Vercel은 프론트엔드 호스팅뿐 아니라 **서버리스 함수(Serverless Functions)** 기능도 제공해서 가벼운 API 로직 정도는 처리할 수 있고, PR(Pull Request)마다 미리보기 주소를 만들어주는 **프리뷰 배포** 기능도 유용하다. 다만 요청이 오래 걸리는 작업이나 상시로 떠 있어야 하는 백엔드 서버 용도로는 적합하지 않다.
다만 일반적인 **Spring Boot 서버를 계속 실행하는 서버**로 Vercel을 이해하면 안 된다.

## 4. Render
Render 역시 서버와 애플리케이션을 쉽게 배포할 수 있게 해주는 **클라우드 배포 플랫폼**이다.
Vercel이 프론트엔드와 Next.js 쪽에 특히 강하다면, Render는 일반적인 백엔드 서버도 쉽게 올릴 수 있다.
예를 들어 Spring Boot 프로젝트가 GitHub에 있다면
```plain text
Spring Boot 프로젝트
  ↓
GitHub
  ↓
Render
  ↓
Gradle Build
  ↓
Spring Boot 실행
  ↓
인터넷 공개
```
형태로 배포할 수 있다.
FastAPI도 가능하다.
```plain text
FastAPI
  ↓
GitHub
  ↓
Render
  ↓
pip install
  ↓
uvicorn 실행
  ↓
서비스 공개
```
그래서 다음과 같은 프로젝트라면
```plain text
React
Spring Boot
PostgreSQL
```
이런 식으로 구성할 수 있다.
```plain text
React / Vue
  ↓
Vercel

Spring Boot
  ↓
Render

PostgreSQL
  ↓
Render PostgreSQL
```
Render는 웹 서버뿐 아니라 정해진 시간마다 실행되는 **Cron Job**, 백그라운드에서 계속 도는 **Background Worker**, 관리형 **PostgreSQL/Redis** 같은 데이터베이스도 함께 제공해서, 하나의 플랫폼 안에서 서비스 구성 요소 대부분을 해결할 수 있다는 장점이 있다.
처음 배포를 공부할 때는 AWS EC2에 직접 서버를 만드는 것보다 훨씬 쉽다. 서버 운영체제나 방화벽, HTTPS 인증서를 직접 다루지 않아도 되기 때문이다.

## 5. Cloudflare
Cloudflare는 조금 성격이 다르다.
Cloudflare는 주로 **사용자와 실제 서버 사이의 앞단**에 위치한다.
예를 들어
```plain text
사용자
  ↓
Cloudflare
  ↓
AWS 서버
  ↓
Nginx
  ↓
Spring Boot
```
같은 구조다.
Cloudflare가 대표적으로 제공하는 기능은 다음과 같다.
```plain text
DNS
CDN
HTTPS
DDoS 방어
캐싱
방화벽
봇 차단
```
### CDN이란?
예를 들어 실제 서버가 한국에 있다고 생각해보자.
미국 사용자가 한국 서버에 매번 직접 접속하면 거리가 멀기 때문에 느릴 수 있다.
Cloudflare를 사용하면 이미지, CSS, JavaScript 같은 콘텐츠를 전 세계 여러 지역 서버에 캐싱할 수 있다.
```plain text
        한국 원본 서버
             ↓
       Cloudflare CDN
      ↙      ↓      ↘
   미국     일본     유럽
```
그러면
```plain text
미국 사용자
→ 미국 근처 Cloudflare 서버

일본 사용자
→ 일본 근처 Cloudflare 서버

유럽 사용자
→ 유럽 근처 Cloudflare 서버
```
에서 콘텐츠를 받을 수 있다.
그래서 속도도 빨라지고 실제 서버의 부담도 줄어든다.
Cloudflare에는 Workers, Pages 같은 기능도 있어서 단순히 CDN만 제공하는 것이 아니라 코드나 웹사이트를 실행하는 기능도 제공한다. 또한 DDoS 공격처럼 짧은 시간에 트래픽이 폭증하는 공격을 사용자와 서버 사이에서 미리 걸러주기 때문에, 원본 서버는 그런 공격을 직접 받지 않고 방어할 수 있다는 것도 큰 장점이다.

## 6. AWS
AWS는 앞의 서비스들과 규모 자체가 다르다.
AWS는 하나의 배포 프로그램이라기보다 **서버, 데이터베이스, 파일 저장소, 네트워크, CDN 등 클라우드 인프라 대부분을 제공하는 종합 클라우드 플랫폼**이다.
쉽게 비교하면
```plain text
Vercel
→ 프론트엔드 배포를 쉽게

Render
→ 백엔드 배포를 쉽게

Cloudflare
→ DNS / CDN / 보안을 쉽게

AWS
→ 서버, DB, 파일, 네트워크 등을 원하는 구조로 직접 구성
```
이라고 보면 된다.
### AWS EC2
Spring Boot를 AWS에 처음 배포할 때 가장 많이 접하는 서비스가 **EC2**다.
EC2는 아주 쉽게 말하면
```plain text
인터넷에 연결된 컴퓨터 한 대를 빌리는 것
```
이다.
내 컴퓨터에서는
```plain text
Spring Boot
  ↓
localhost:8080
```
이었다면 EC2에서는
```plain text
인터넷
  ↓
AWS EC2
  ↓
Spring Boot
```
형태가 된다.
실제로는 보통 Nginx도 같이 사용한다.
```plain text
사용자
  ↓
AWS EC2
  ↓
Nginx
  ↓
Spring Boot : 8080
```
예를 들어 Spring Boot 쇼핑몰을 만든다면 이런 구조도 가능하다.
```plain text
사용자
  ↓
Route 53 DNS
  ↓
CloudFront CDN
  ↓
Load Balancer
  ↓
EC2
  ↓
Nginx
  ↓
Spring Boot
  ↓
RDS PostgreSQL
```
이미지 파일은 별도로 S3에 저장할 수 있다.
```plain text
Spring Boot
  ↓
S3
  ↓
상품 이미지 / 첨부파일
```
즉 서버 안에 모든 파일을 저장하는 것이 아니라 역할별로 분리할 수 있다.
여기서 나온 서비스들을 짧게 풀어보면, **Route 53**은 도메인과 DNS를 관리하는 서비스, **CloudFront**는 AWS의 CDN, \*\*Load Balancer(ELB)\*\*는 여러 대의 EC2로 트래픽을 나눠주는 서비스, **RDS**는 관리형 데이터베이스(MySQL, PostgreSQL 등), **S3**는 이미지·동영상 같은 파일을 저장하는 스토리지다. AWS는 이런 부품들을 필요한 만큼 골라서 직접 조립하는 방식이기 때문에 자유도가 가장 높은 대신, 처음 배우는 입장에서는 Vercel이나 Render보다 설정할 것이 훨씬 많다.

## 프론트엔드와 백엔드를 나눠서 보면
React + Spring Boot 프로젝트라면 가장 쉽게
```plain text
사용자
  ↓
Vercel
  ↓
React
  ↓
API 요청
  ↓
Render
  ↓
Spring Boot
  ↓
PostgreSQL
```
형태로 사용할 수 있다.
조금 더 AWS 중심으로 가면
```plain text
React
  ↓
Vercel 또는 S3 + CloudFront

Spring Boot
  ↓
AWS EC2
  ↓
Nginx

Database
  ↓
AWS RDS PostgreSQL

파일
  ↓
AWS S3
```
형태가 될 수 있다.
정리하면, 공부 초반이라 빠르게 배포 경험을 해보고 싶다면 **Vercel(프론트) + Render(백엔드/DB)** 조합이 설정이 적고 가장 편하다. 반면 트래픽이 커지거나 인프라를 세밀하게 직접 통제하고 싶다면, EC2·RDS·S3·CloudFront·Route 53처럼 AWS의 개별 서비스를 조합해서 구성하는 쪽으로 넘어가게 된다. Nginx는 이 두 경우 모두에서, 특히 EC2처럼 서버를 직접 다룰 때 Spring Boot 앞단을 지켜주는 역할로 계속 등장하고, Cloudflare는 어떤 조합을 쓰든 도메인 앞단에 한 겹 더 씌워서 보안과 속도를 보완해주는 존재로 이해하면 된다.
