## 2. ① 프롤로그 — 문제를 고르는 능력을 시험하고 싶었다
**원문:** [AX 인재전쟁 프롤로그: 문제를 고르는 능력을 시험하고 싶었다](https://bogyie.com/blog/ax-war-prologue/)  
**게시일:** 2026-07-26 · **작성자 표기 읽기 시간:** 5분
### 글이 말하는 출발점
- 작성자는 AX 인재전쟁이 이미 주어진 문제를 빠르게 푸는 대회라기보다, **무엇을 문제로 볼지부터 참가자가 정하는 구조**였다고 해석했다.
- 최대 세 개의 기업 트랙을 고를 수 있었지만, 자기 보고상 **무신사 트랙 하나만 선택**했다. 합격 확률을 넓히는 대신 문제 정의의 판단력을 더 분명하게 시험하려는 선택이었다.
- 여기서 `Taste`는 화면을 보기 좋게 만드는 감각이 아니라, 가능한 문제·솔루션·주장 가운데 **무엇을 선택하고 무엇을 버릴지 정하는 기준**으로 정의한다.
### 작업 방식으로 정리한 핵심
1. **넓게 탐색** — 기업·산업·사용자·업무·제약을 먼저 살핀다.
2. **좁게 결정** — 한 사람의 한 가지 결정 시점까지 범위를 줄인다.
3. **근거를 남김** — AI 설명, 코드 계산, 화면 결과가 같은 사실·규칙에서 출발하도록 연결한다.
### 중요한 태도
- AI를 사용했다는 이유만으로 최종 제품에 챗봇·예측 모델을 억지로 넣지 않는다.
- AI는 조사·반론 탐색·구현·검증 비용을 낮추는 수단이고, 최종 사용자 문제에 필요한 기능만 결과물에 남긴다.
- 아직 검증하지 못한 효과를 성과처럼 쓰지 않는 것을 원칙으로 둔다.
### 이 글에서 이후 3편을 읽는 관점
이 프롤로그는 이후 예선과 본선에서 반복되는 기준을 미리 제시한다. 즉, 결과물의 기능 수가 아니라 **문제 선택의 근거, 범위의 절제, 증명 가능한 주장**이 중심 평가 대상이라는 작성자의 해석이다.

## 3. ② 예선 — 공개 근거에서 실행 가능한 문제를 찾기
**원문:** [AX 인재전쟁 예선: 공개 근거에서 실행 가능한 문제를 찾기](https://bogyie.com/blog/ax-war-qualifying/)  
**게시일:** 2026-07-26 · **작성자 표기 읽기 시간:** 9분
### 작성자가 설명한 과제 조건
작성자 자기 보고에 따르면 예선은 다음 조건이었다.
- 참여 기업이 겪는 문제를 **공개 자료로 검증**해 정의한다.
- 이를 해결하는 **Codex 플러그인**을 만든다.
- 실행 결과물 외에 원본 AI 대화 로그와 다섯 문항 설명을 함께 제출한다.
- 기업 내부 데이터나 개인 경험만으로는 근거를 삼지 않는다.
> 이 과제 조건은 해당 후기의 서술을 요약한 것이며, 이 문서에서는 공식 공고 원문으로 재확인하지 않았다.
### 문제를 고르는 과정
- AI가 처음 제시한 후보를 곧바로 채택하지 않고, 무신사 공식 사이트·파트너 가이드·뉴스룸·채용 자료와 소비자 관점 자료·법령·공공기관 자료를 다시 조사했다고 적었다.
- 자기 보고상 공식 사이트 46건, 채용·구성원 자료 44건, 소비자 관점 자료 31건, 공개 프로필 자료 31건을 수집했다. 중요한 것은 152건이라는 양보다, **출처 → 관찰 사실 → 지지하는 주장 → 가능한 추론 → 해서는 안 되는 추론**으로 분해한 방식이었다.
- 후보 선택은 `근거 강도`, `플러그인 적합성`, `시연 명확성`, `구현 가능성`, `전달력`의 다섯 기준으로 비교했다.
### 최종 문제 정의와 결과물
작성자는 상품 등록 자료에서 다음 둘을 나눠 넘기는 업무를 병목으로 잡았다.
- **파트너 보완 요청**: 혼용률·사이즈표·증빙 링크처럼 자료만으로 보완 대상을 비교적 명확히 판단할 수 있는 항목
- **내부 검토 요청**: 친환경·정품·캐시미어·반품 보장처럼 정책·법무·근거 충족 여부를 사람이 판단해야 하는 표현
이에 따라 자기 보고상 `상품등록 보완요청서` Codex 플러그인을 구현했다. 이 결과물은 “상품 설명을 검사하는 AI”보다, 한 입력을 담당자별 후속 행동으로 분기하고 근거를 검수 기록으로 남기는 데 초점을 둔다.
```plain text
상품 등록 자료
  → [코드] 입력 형식 검증·정규화·이슈 분류
  → [Codex] 파트너/내부 담당자별 문서 작성
  → [코드] 출력 계약 검증·검수 기록 저장
```
### 재현 가능한 설계 원칙
- **사실 판정과 문서 작성을 분리**: 형식 검증·고정 규칙·분류는 코드가 담당하고, Codex는 구조화된 결과를 사람이 읽기 쉬운 문서로 바꾼다.
- **경계 사례를 먼저 본다**: 정상 입력에서만 그럴듯한 결과가 아니라, 근거 부족·애매한 표현·보완과 내부 검토가 섞인 경우를 나눠 본다.
- **실행한 것과 가정한 것을 분리**: 목업 저장·규칙 기반 분류·제출물로 검증한 범위와 실제 회사 내부 적용 효과를 구별한다.
### 한계
이 후기는 공개 자료에서 관찰한 신호를 바탕으로 한 프로토타입 설명이다. 실제 무신사 내부의 작업량, 해당 프로세스의 현업 정확도, 도입 효과는 원문도 확정 사실로 주장하지 않는다.

## 4. ③ 본선 — 세 시간 안에 문제를 좁히고 증명하기
**원문:** [AX 인재전쟁 본선: 세 시간 안에 문제를 좁히고 증명하기](https://bogyie.com/blog/ax-war-final/)  
**게시일:** 2026-07-26 · **작성자 표기 읽기 시간:** 10분
### 작성자가 설명한 본선 과제·결과
- 후기의 자기 보고상 무신사 트랙 문제는 **패션·뷰티 트렌드를 먼저 포착해 시장을 주도할 방법**을 설계하는 것이었다.
- 별도 데이터가 주어지지 않았고, 핵심 메커니즘 하나는 실제로 작동시켜야 했으며, 제출까지 3시간이었다고 적었다.
- 작성자는 무신사 트랙 **1등** 결과를 받았다고 기록한다. 이는 이 후기에 기반한 자기 보고이며, 이 문서에서 수상 결과를 별도 공식 발표로 재검증하지 않았다.
### 문제를 바꾼 결정: 예측을 포기하고 검증 기회 배정으로
작성자는 세 시간과 공개 데이터만으로 미래 판매·트렌드 예측의 정확도를 증명하는 것은 불가능하다고 판단했다. 그래서 “무엇이 유행할까?”를 맞히는 시스템 대신 아래처럼 범위를 바꿨다.
```plain text
트렌드 예측·매입 추천
  → 이미 입점한 후보 중
    → MD가 작은 큐레이션/검증 기회를 줄 대상을
      → 행동·보류·미배정으로 가르는 결정 지원
```
이는 예측 성공을 주장하는 대신, 다음 정보를 얻기 위한 **작은 검증 자원 배정**을 돕는 문제로 축소한 것이다.
### 현장 전 준비와 시간 배분
- 작성자는 정답이나 특정 솔루션을 미리 만들기보다, 기업·산업·조직·브랜드 전략을 이해하기 위한 조사 구조와 작업 환경을 준비했다고 한다.
- 자기 보고상 본선 직전 37분 36초 동안 URL 283개를 확인해 정상 271건·접근 차단 9건·의도된 404 2건·타임아웃 1건으로 분류했고, 241장의 출처 카드를 만들었다.
- 입력 형식이 정해지지 않은 상태에서도 파일 목록·스키마·품질을 확인할 Python 분석 워크벤치와 Electron App 뼈대를 준비했으며, 합성 데이터 기준 67개 테스트를 통과한 상태였다고 기록한다.
- 문제 공개 뒤에는 실제 사용자와 결정 시점부터 확인하고, 구현보다 문제 정의에 시간을 쓰며, 한 시간 내 핵심 메커니즘을 증명할 범위로 제한했다.
### 데이터와 규칙을 다루는 방식
- 서로 다른 공개 신호를 한 점수로 무리하게 합치지 않고, 각 신호가 **말할 수 있는 것과 말할 수 없는 것**을 먼저 적었다.
- 결과를 본 뒤 기준을 맞추는 것을 피하려고, 결과 확인 전에 판단 게이트를 잠갔다고 설명한다.
- 데모는 성공 후보만 보여주는 대신, 같은 규칙으로 **행동·보류·미배정**이 모두 나오는 반례를 포함했다.
### 결과물의 핵심 의미
후기에 따르면 App은 시각화 자체가 목적이 아니라, MD가 “어떤 후보에 제한된 검증 슬롯을 줄 것인가”를 판단할 때 입력·규칙·출력 상태를 추적할 수 있게 하는 증명 장치였다. 즉, 넓은 전략 주장을 작동하는 한 개의 의사결정 메커니즘으로 압축한 사례다.

### AI 활용의 핵심 경고: 생산량은 검토 부채가 될 수 있다
- 작성자는 AI로 조사·구현을 병렬화하면 자료와 결과물이 빠르게 늘지만, 그만큼 검토해야 할 출처 중복·단위 불일치·근거 오독 위험도 커진다고 회고한다.
- 첫 분석의 오류를 찾는 데도 더 많은 생성 작업보다, 완료된 결과를 의심하도록 맡긴 **감사 역할**이 중요했다고 적었다.
- 다음 작업에서는 각 조사에 `바꿀 결정`, `필요한 최소 근거`, `멈출 조건`, `결과 부재/불일치 시 남길 상태`를 미리 붙이겠다고 한다.
### 결정 기록의 역할
- 예선의 작업 Wiki와 본선의 기준서는 AI 세션 간 문맥 전달용 메모만이 아니라, 정한 범위를 몰래 넓히거나 결과에 맞춰 임계값을 고치는 일을 막는 제약 장치로 기능했다는 설명이다.
- 작성자는 이전에 통과했다고 기록한 Electron E2E 주장을 최신 번들 검사에서 되돌린 사례를 들어, 기록이 있으면 주장·오류·정정 근거를 함께 남길 수 있다고 말한다.
- 장황한 문서 대신 다음 여섯 항목이 한 화면에 있는 최소 기준서를 다음 작업 방식으로 제안한다: `현재 질문`, `사용자와 결정 시점`, `포함/제외 범위`, `입력·근거`, `결과 상태·실패 기본값`, `증명/비증명 주장`.
### 수상 결과가 증명하지 않는 것
작성자는 트랙 1등이 대회 조건 안에서의 평가일 뿐 실제 현업 효과를 검증한 결과는 아니라고 명시한다. 이 구분은 포트폴리오·공모전 기록에서 특히 중요하다. **프로토타입의 작동·심사 결과**와 **현업 도입 효과·정확도·매출 영향**을 같은 주장으로 섞지 않아야 한다.

## 8. 글별 핵심 흐름·절차 요약
아래는 각 글을 읽고 “이 사람이 실제로 어떤 순서로 판단·조사·정의·구현·검증했는가”만 다시 압축한 것이다. 수상·수치·과제 조건은 모두 원문 작성자의 자기 보고 범위다.
### ① 프롤로그 — 문제를 선택하는 기준을 먼저 세움
```plain text
AX 인재전쟁 발견
  → 이미 주어진 문제를 푸는 대회가 아니라는 점에 주목
    → 여러 트랙으로 합격 확률을 넓히는 대신 무신사 한 트랙 선택
      → AI 시대의 Taste를 ‘무엇을 만들까’보다 ‘무엇을 버릴까’의 기준으로 정의
        → 이후 예선·본선 공통 운영 원칙 확정
           : 넓게 탐색 → 한 결정으로 좁힘 → 근거를 남김
```
- **출발 판단**: 문제 풀이 능력보다 문제 정의 능력을 시험하고 싶었다.
- **선택 기준**: 익숙한 산업이라서가 아니라, 공개 근거로 기업·산업을 해석하고 문제를 좁힐 수 있는지 검증하기 위해 무신사 트랙 하나를 골랐다.
- **AI 활용 원칙**: AI를 조사·대안·반론·구현 보조로 쓰되, 결과물에 AI 기능을 넣는 것은 사용자 문제에 필요할 때만 한다.
- **이 글의 산출물**: 구현물보다 이후 모든 선택에 적용할 문제 정의·근거·범위 절제의 기준이다.
### ② 예선 — 공개 자료를 업무 흐름으로 바꾸고 Codex 플러그인으로 증명
```plain text
과제 조건 확인
  → AI가 제시한 초기 문제 후보를 보류
    → 기업 공식 자료·파트너 가이드·뉴스룸·채용·소비자 관점·법령 자료를 출처 유형별로 수집
      → 각 자료를 ‘사실 / 지지하는 주장 / 가능한 추론 / 해서는 안 되는 추론’으로 분해
        → 후보를 근거 강도·플러그인 적합성·시연 명확성·구현 가능성·전달력으로 비교
          → 상품 등록 자료의 ‘보완 요청과 내부 검토 분기’ 업무를 최종 문제로 정의
            → 코드와 Codex의 책임을 분리한 플러그인 구현
              → 경계 사례·출력 계약·검수 기록으로 결과를 검증
```
#### 세부 절차
1. **근거 수집을 솔루션보다 먼저 수행**
	- AI가 먼저 낸 후보를 그대로 문제 정의로 쓰지 않았다.
	- 회사가 직접 밝힌 사실, 외부에서 관찰한 신호, 아직 추론에 불과한 내용을 나눠 기록했다.
	- 같은 보도자료를 반복한 기사들은 별도 근거 여러 개가 아니라 하나의 근거 묶음으로 취급했다.
2. **문제를 ‘상품 정보 검사’에서 ‘업무 분기’로 재정의**
	- 상품 자료에는 자료만으로 보완할 수 있는 항목과, 정책·법무·근거 판단이 필요한 항목이 섞여 있다고 봤다.
	- 그래서 문제를 “오류를 많이 찾는 AI”가 아니라, **한 자료를 파트너 보완 요청과 내부 검토 요청으로 나누고 기록까지 남기는 흐름**으로 정의했다.
3. **최종 결과물의 처리 흐름 설계**
```plain text
입력: 상품 등록 자료
  → 코드: 입력 형식 검사·정규화·고정 규칙 분류
    → Codex: 분류 결과를 담당자별 한국어 요청 문서로 변환
      → 코드: 출력 계약 검사·MCP 목업에 검수 기록 저장
```
#### 4. 검증 범위를 통제
- 코드가 담당한 분류와 Codex가 담당한 문서 작성의 책임을 분리했다.
- 정상 사례만으로 끝내지 않고 근거 부족, 모호한 표현, 두 유형이 섞인 입력을 경계 사례로 점검했다.
- 실제 현업 적용 효과가 아니라, 공개 근거 기반 프로토타입의 작동·분기·기록까지를 증명 범위로 제한했다.
### ③ 본선 — 열린 ‘트렌드’ 문제를 MD의 작은 검증 슬롯 배정으로 압축
```plain text
문제 공개 전: 회사·산업·조직·브랜드 전략을 조사하고 작업 환경만 준비
  → 문제 공개 뒤: 실제 사용자와 그 사용자가 내릴 결정을 질의응답으로 확인
    → ‘트렌드 예측’은 짧은 시간·공개 데이터로 정확도를 증명할 수 없어 포기
      → ‘어떤 후보에 작은 검증 기회를 줄 것인가’라는 MD 결정으로 재정의
        → 공개 신호의 의미·한계를 분리하고 결과 전 판단 게이트를 고정
          → 행동 / 보류 / 미배정을 같은 규칙으로 가르는 App 구현
            → 성공 후보뿐 아니라 반례를 포함해 데모·발표
```
#### 세부 절차
1. **답이 아니라 작업 환경을 미리 준비**
	- 특정 솔루션을 미리 만들지 않고, 문제를 받은 뒤 빠르게 근거를 찾을 조사 구조·출처 카드·분석 워크벤치·Electron App 뼈대를 준비했다.
	- 원문 자기 보고상 URL 접근 상태까지 분류해 쓸 수 있는 근거와 쓸 수 없는 링크를 분리했다.
2. **사용자와 결정부터 확정**
	- 문제 문구를 그대로 구현하지 않고, 누가 실제로 어떤 결정을 해야 하는지를 먼저 확인했다.
	- 사용자·결정 시점·제출 후 증명 범위를 기준 문서로 잠가, 기능이 그 범위를 벗어나지 않게 했다.
3. **예측 주장을 검증 가능한 행동으로 전환**
	- 미래 판매·트렌드 정확도를 주장하는 대신, 이미 입점한 후보에 제한된 큐레이션·검증 자원을 줄지 결정하는 문제로 좁혔다.
	- 이는 “유행을 맞혔다”가 아니라 “다음 정보를 얻기 위한 작은 실험을 할 후보를 고른다”는 주장으로 범위를 바꾼 것이다.
4. **데이터·규칙·화면을 하나의 의사결정 장치로 연결**
	- 신호를 무조건 합산하지 않고, 각 신호의 의미와 한계를 구분했다.
	- 결과를 보고 기준을 고치는 일을 막기 위해 판단 게이트를 결과 전에 정했다.
	- App은 예쁜 차트가 아니라 입력·규칙·결론·보류 사유를 보여 주는 의사결정 증명 장치로 만들었다.
### ④ 회고 — 버린 선택, 검토 부채, 결정 기록을 운영 원칙으로 정리
```plain text
예선·본선의 실제 선택을 다시 대조
  → 결과를 안 뒤 만든 설명과 당시 기록을 구분
    → 버린 선택과 남긴 선택을 근거·검증 가능성·반복 가능성·설명 가능성으로 비교
      → AI 병렬 작업이 만든 생산량과 검토 비용을 분석
        → 결정 기록·감사 역할·최소 기준서로 다음 작업 방식을 보완
```
- **버린 선택을 핵심 결과로 봄**: AI가 처음 낸 문제 후보, 유행 예측·매입 추천, AI 최종 판정, 기능이 많은 데모를 버렸다.
- **대신 남긴 것**: 공개 근거로 설명 가능한 업무, 다음 검증 기회 배정, 사전에 잠근 규칙·코드, 대표·보류·실패가 모두 보이는 한 흐름이다.
- **AI 생산량에 대한 경고**: 조사·구현이 빨라질수록 중복 출처·단위 불일치·근거 오독을 검토하는 비용도 함께 커진다. 이 상태를 ‘검토 부채’로 해석했다.
- **개선 절차**: 각 작업에 ‘바꿀 결정’, ‘최소 근거’, ‘조사를 멈출 조건’, ‘결과가 없거나 어긋날 때의 상태’를 미리 정한다.
- **결정 기록의 목적**: AI에게 맥락을 전달하는 메모를 넘어, 범위 확장·임계값 사후 조정·검증하지 않은 완료 선언을 막는 제약 장치로 사용한다.
<callout icon="⚠️" color="gray_bg">
	**읽는 방법**: 위 흐름은 네 원문에서 작성자가 설명한 작업 기록을 구조화한 것이다. 따라서 재현할 때는 ‘수집 건수’나 ‘사용 도구’를 복제하기보다, 문제 정의 → 주장 가능 범위 → 고정 규칙 → 경계 사례 → 한계 기록의 순서를 가져가는 편이 핵심이다.
</callout>
