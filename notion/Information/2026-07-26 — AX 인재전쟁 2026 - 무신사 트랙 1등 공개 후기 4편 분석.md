## 1. 프롤로그: 문제를 고르는 기준

- 작성자는 대회를 이미 주어진 문제를 빨리 푸는 방식보다, 무엇을 문제로 볼지부터 정하는 구조로 해석했다.
- `Taste`는 화면 미감이 아니라 가능한 문제·솔루션·주장 중 무엇을 선택하고 버릴지 정하는 기준으로 정의한다.
- 작업 원칙은 넓게 탐색한 뒤 한 결정 시점까지 범위를 줄이고, AI 설명·코드·화면이 같은 사실과 규칙에서 출발하도록 근거를 남기는 것이다.
- 검증하지 못한 효과를 성과처럼 쓰지 않고, AI는 조사·반론 탐색·구현·검증 비용을 낮추는 수단으로만 둔다.

## 2. 예선: 공개 근거에서 실행 가능한 문제를 찾기

후기에서 설명한 예선의 문제 정의는 상품 등록 자료를 단순 검사하는 AI가 아니라, 자료만으로 보완 가능한 항목과 정책·법무 판단이 필요한 항목을 **후속 담당자별 행동으로 분기하고 기록하는 흐름**이다.

```plain text
상품 등록 자료
  → 코드: 입력 형식 검증·정규화·이슈 분류
  → Codex: 파트너/내부 담당자별 문서 작성
  → 코드: 출력 계약 검증·검수 기록 저장
```

작성자가 제시한 설계 원칙은 다음과 같다.

1. 출처·관찰 사실·지지하는 주장·가능한 추론·해서는 안 되는 추론을 분리한다.
2. 사실 판정과 문서 작성을 분리한다. 고정 규칙과 분류는 코드가, 구조화 결과의 문서화는 Codex가 맡는다.
3. 정상 입력뿐 아니라 근거 부족·모호한 표현·혼합 사례를 먼저 확인한다.
4. 공개 자료 기반 프로토타입의 작동·분기·기록만을 증명 범위로 제한하고, 실제 현업의 작업량·정확도·도입 효과는 확정 사실로 주장하지 않는다.

## 3. 본선: 예측 대신 검증 기회 배정

작성자는 짧은 시간과 공개 데이터만으로 트렌드·판매 예측의 정확도를 증명할 수 없다고 보고, 문제를 이미 입점한 후보 중 MD가 제한된 큐레이션 또는 검증 기회를 줄 대상을 고르는 결정으로 좁혔다.

```plain text
트렌드 예측·매입 추천
  → 이미 입점한 후보 중
    → MD가 작은 검증 기회를 줄 대상을
      → 행동 / 보류 / 미배정으로 가르는 결정 지원
```

- 공개 신호를 하나의 점수로 무리하게 합치기보다, 각 신호가 말할 수 있는 것과 말할 수 없는 것을 기록한다.
- 결과를 본 뒤 기준을 바꾸지 않도록 판단 게이트를 결과 확인 전에 잠근다.
- 데모에는 성공 사례뿐 아니라 같은 규칙에서 보류·미배정이 나오는 반례도 포함한다.
- 후기의 수상·URL 수집·테스트 통과 수치 및 과제 조건은 작성자 자기 보고이며, 이 동기화본은 공식 발표으로 재확인하지 않는다.

## 4. 회고: 생산량과 검토 부채

- AI로 조사와 구현을 병렬화하면 결과물은 빨리 늘지만 출처 중복·단위 불일치·근거 오독을 검토할 비용도 증가한다. 후기는 이를 검토 부채로 설명한다.
- 다음 작업의 최소 기준서로 `현재 질문`, `사용자와 결정 시점`, `포함/제외 범위`, `입력·근거`, `결과 상태·실패 기본값`, `증명/비증명 주장`을 제안한다.
- 기록은 AI 세션 간 문맥 전달 메모를 넘어 범위 확장, 임계값 사후 조정, 검증하지 않은 완료 선언을 막는 제약 장치로 사용된다.
- 수상 결과는 대회 조건 안의 평가일 뿐 실제 현업 효과·정확도·매출 영향을 증명하지 않는다는 한계를 명시한다.
